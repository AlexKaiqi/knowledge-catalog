内部立项材料 · MVP · 2026-08

让业务口径从「找人确认」，变成可复用、可追溯的组织资产。

今天的问题不是搜不到资料，而是搜到后仍要找人确认：哪个口径有效、谁负责、何时改过。 结果是同一问题反复对齐、报表口径不一致、故障排查依赖熟人，Agent 也只能复述材料，无法引用可信结论。 本项目提供一个 Knowledge Workbench 和一棵 Workspace VFS：知识方维护发布，开发者接入 Connector，人和 Agent 像使用文件系统一样按版本使用并追溯。

请求批准 启动 Knowledge Workbench + Workspace VFS MVP，先在数仓域验证「接入—维护—发布—使用—追溯」闭环，再决定规模化投入。

业务问题

组织一直在为「无法复用已经知道的事」付费

表、文档和聊天都在，但可信结论没有成为资产。每次决策、排障和交接，都要重新确认一遍。

效率损失

同一问题反复找人

  • 指标含义、表用途、异常原因散落在 Wiki、目录和群聊。
  • 业务分析、研发和值班每次都要重新找负责人确认。
  • 专家时间耗在重复解释，响应速度取决于「谁在线」。
经营风险

同名指标，各说各话

  • 报表拿到的是不同时间、不同负责人的解释。
  • 一次采集或编辑可能覆盖业务认可的口径。
  • 出错后说不清使用了哪一版，复盘和回退没有抓手。
规模瓶颈

人和 Agent 都无法放心复用

  • 搜索能返回相似文字，却不能证明谁认领、哪一版有效。
  • 新人、跨团队协作和 Agent 都依赖浅层拷贝。
  • 知识消费越多，错误越难追到源头，自动化不敢放大。

根因：业务拥有高质量口径，却缺少一个可控的交付方式——写了不被覆盖，改了有版本，用了能追到。

解决路径

把「发一段说明」升级为「发布一版知识资产」

底座不替业务判断口径，而是把责任、变更和使用串成闭环，让已经形成的共识可以安全复用。

1 · 明确责任

谁对事实负责，谁维护对应知识

  • 平台对表、作业、血缘等源系统事实负责。
  • 业务 steward 对指标、维度和口径负责。
  • 采集不再冒充语义，业务也不必接管技术元数据。
2 · 保护共建

各写各的分区，互不覆盖

  • 采集更新结构，不能覆盖业务定义。
  • 谁能写、谁能审、谁能发布，按治理边界划清。
  • 变更先提案、再发布，正在编辑的内容不影响线上使用。
3 · 稳定交付

消费方使用业务发布的一代

一次任务开始时固定所需知识版本；任务进行中不跟随最新修改。报表、人和 Agent 得到同一套可重放上下文。

4 · 闭环改进

每次使用都带回对象、版本和来源

用对了可以复用，用错了可以定位到具体资产和版本，再由负责人修订、发布。质量改进不再靠重新搜索和口头广播。

每个角色都能少付一笔重复协作成本

MVP 不要求所有人换一套工作方式；它在现有采集、治理和消费链路之间补上可信知识交付。

角色 今天怎么干 为何不共建 / 共建了也会坏 本系统怎么托住
业务 / steward 口径写在 Wiki、表格、口头约定。真正的定义不敢放进「平台」。 写了被采集覆盖；改了说不清版本；谁用过哪一版找不到。交出去等于失去控制。 语义仓只给 steward 写口径；发布权单独授；历史和来源可查。
数仓 / 平台 持续采集表、作业、血缘。目录越来越全。 采得到结构，采不到语义。越采越全，质量不涨。一次运行的残缺 SQL 还会改掉作业定义。 采集只写物理仓分区；实例走追加，不许覆盖作业定义；改名不断对象身份。
治理 / 安全 表权限在 Ranger / Unity；知识侧几乎没有边界，或误做成表 GRANT。 业务不敢把敏感口径放进来。看见知识被当成能查数据。 知识仓有自己的写/发权。SELECT 仍问 Ranger。两套授权不合成一条。
消费方 · 人与 Agent 搜门户、搜向量库、问同事。拿到的是没人认领的浅层拷贝。 用错了无法回到对象和版本，返工只能再搜一轮。优化没有稳定抓手。 读已发布的一代；引用带对象、版本、来源；对账对准这一条再改。

对人

检出成可编辑的组合树

用熟悉的编辑器、搜索和开发工具工作。各 mount 是自己的 Git worktree，修改后按路径分别写回。

对 Agent

直接挂成标准文件系统

通过 HTTP VFS 暴露 list/read/write/edit，无需在磁盘物化整棵树；现有 Agent Harness 只需替换文件系统 Provider。

对治理

易用不等于绕过边界

无权 mount 不出现或写入被拒；只读路径不能改；过期 base 不覆盖并发提交；跨仓逐仓报告，不伪装事务。

找知识 × 用知识

同一份知识，既要容易找到，也要能稳定使用

Q&A 运行时边界

一个问题分三路：知识读文件，实时状态问 MCP，外部动作按 Skill 执行

Knowledge Catalog 不冒充实时系统或执行平台。它保存可版本化的文件，包括口径、Runbook 和 Skill；Agent 在任务现场再选择知识读取、实时观测或受保护动作。

1 · 已沉淀知识

「GMV 的业务口径是什么？」

走 Workspace VFS / SEARCH / READ，读取已发布文件和对象；回答带文件路径、对象、版本和来源。

知识系统负责可重放

2 · 变化快的状态

「今天 GMV 作业现在成功了吗？」

走 MCP 现场观测调度、数据库或指标平台的实时状态。不能拿仓里昨天的快照冒充“现在”。

MCP 观测外部当前态

3 · 会改变外部状态

「把已审批的 GMV 发布到指标平台」

Agent 加载受治理的发布 Skill，按步骤检查版本、审批和权限，再调用 MCP/API；外部系统当场执行和强制授权。

执行后如何回到闭环

结果可以沉淀，但不能倒置权威

系统负责什么明确不负责什么
Knowledge Catalog文件、版本、所有权、发布代、来源、Skill 与历史 receipt不声称外部系统“此刻”的状态，不直接强制外部动作
MCP任务现场读取外部实时状态；向 Agent 暴露受控工具不替代组织知识版本，不把瞬时返回自动变成长期真相
Skill版本化的工作流文件：教 Agent 如何观测、校验、发布和恢复不是后台进程，不是凭证，不是授权源，也不是副作用本身
外部系统保存实时业务状态，并最终执行、拒绝或确认受保护动作不替代知识资产的主人、版本与来源治理

市场上已有的「Catalog」并不解决这件事

它们能展示、能检索、能管表权限。几乎都不能让业务把口径当资产来维护。

产品 它真正在做 在不在查询路径 缺什么
Unity / WeData Catalog Lakehouse 运营目录：名字、元数据、GRANT、临时凭证 在。引擎先问它再读存储 采集与注释易互相覆盖；不是业务共建的资产账本
WeData 资产目录 + Unity Semantics 发现门户 + 指标语义层 / headless BI 门户不在；语义层是查询产品 语义层是查询产品，不是口径资产仓
Google Knowledge Catalog 发现 + AI 上下文图（Entry / Aspect） 不在 发现与上下文图，不是业务维护资产的账本
DataHub / Atlas / 文档 Wiki 元数据湖或给人看的页面 不在 默认最新一份；难谈主人、版本、来源
RAG / 向量库 相似检索 不在 能搜到相似，不能认领。没有版本和来源，质量无法迭代

运营目录、语义查询、发现门户都该继续存在。缺的是下面这一层：业务肯共建的知识资产底座。底座不坐查询路径，也不替代 SELECT 强制。

这是什么，不是什么

写清楚，立项才不会被收成「再做一套 WeData」或「再做一个企业搜索」。

是

面向知识工作的 Workbench

  • 给知识维护者、Connector 开发者、治理者和消费方一个共同工作面。
  • 把口径登记成有主人、有版本、有来源的资产。
  • 协议只补存储给不了的三样：身份、来源、写边界。
  • 业务发布哪一代，读者就读哪一代。
  • 协议与存储解耦：本地起步，规模化换引擎，语义不变。
  • 第一场景是数仓知识，不是数仓引擎。
不是

不要立项成这个项目

  • 不是检索应用，不是用模型生产口径。
  • 不是 Unity / WeData 运营目录，不进 SQL 查询路径。
  • 不是指标查询引擎 / 问数产品。
  • 不是通用本体、通用 PATCH、跨库事务。
  • 不是把 Ranger 表权限搬进知识仓。

一间 Catalog · 多仓 三种写入：生效 / 提案 / 事件 发布 = 钉死一代 不跟随 latest 索引不是权威 组合不发权

MVP 产品形态

一个 Knowledge Workbench，服务四类角色完成同一条知识链路

Workbench 不是把所有知识收归平台。它提供维护、接入、发布和消费界面；知识仍留在各自负责的仓和写入分区里。

角色 在 Workbench 里能做什么 系统在背后提供什么 角色得到什么
知识维护者
业务 owner / steward		 查看自己负责的指标、维度和说明；直接编辑；比较变更；发起提案；审核并发布；查看历史、来源和旧版本。 按 Repository 和 Aspect 保护写入范围；候选与已发布版本隔离；每次变更保留版本和来源。 这里可以成为日常维护知识的地方。Connector 盖不掉定义，组合到 Workspace 也不会转移所有权。
Connector 开发者
平台 / 源系统团队		 基于稳定 JSON、HTTP/CLI 接口开发 Connector；声明只允许写的 Scope；预览新增、更新、删除；确认后提交；检查同步结果和来源。 提供 Address 对账 kit、ChangeSet 契约、Schema 与 Scope 校验、冲突检测、幂等提交和来源信封。 可以接任何外部权威系统，但不必把源 SDK、密钥和调度塞进 Workbench；Connector 独立开发、独立部署。
治理与平台管理员 登记知识仓；分配写入/发布权限；定义 Workspace；配置发布门禁和通知；查看变更记录；退役 Workspace 或归档仓。 Catalog 只组合不复制；权限、Gate、Hook 与仓历史分开生效；知识权限不越权为数据 SELECT。 能划清「谁负责、谁能改、谁能发布」，并接入现有审批、内控和通知系统。
知识消费者
分析师 / 应用 / Agent		 选择 Workspace；通过页面、API 或 VFS 浏览、glob、grep、精确读取；查看对象、版本和来源；把结果或反馈写回有权限的路径。 一次任务固定各仓版本；路径自动路由目标仓；CAS 防止覆盖并发修改；索引命中后回读权威原文。 人和 Agent 面对同一棵树和同一代上下文，不需要理解多仓拓扑，也不会把搜索摘要当成事实。
维护面

知识属于维护者

维护者决定定义和发布时间。Workbench 提供编辑与协作，不把知识变成平台可随意改写的公共页面。

扩展面

Connector 是开放接缝

任何语言都可以产出 ChangeSet 或调用 HTTP。系统管写入契约和边界，开发者保留连源、映射、调度与 checkpoint。

消费面

Workspace 只组合，不夺权

物理事实、业务口径和个人知识仍在各自仓中。Workspace 每次只钉版本并联合读取，不复制、不覆盖。

Workbench 在上，可信知识服务在下

用户面对的是角色工作台；CLI、HTTP、Connector 和 Agent 调用的是同一套底层语义，不会出现页面一套、自动化另一套。

下图朱线是底层闭环：接入 → 维护 → 检索 → 消费 → 反馈回写。点框看这一层承诺什么。

源系统只提供当前态。采集对账后写入物理仓，运行实例追加到观测仓。采集不是主人，不能写口径。

谁能负责，谁就维护

不按组织架构复制三套仓。第一刀两套权威：平台对源负责，组织对口径负责。一起被看见时，钉死各仓那一代，并存、带来源。

为什么要分

平台只能对「源里当时是什么」负责，组织才能对「我们认什么口径」负责。放进同一份可互相覆盖的文档，高质量的人就不会写。

联合不是覆盖

读者同时需要表和口径，靠钉死的配方拼在一起看。系统不宣布哪边压过哪边。

个人放在哪

未发表的理解可以有自己的仓，那是后置。要进组织：在组织仓提案，来源指向个人钉死的版本。不拷贝，也不把个人仓直接挂进共享 Workspace。

核心矛盾怎么落到系统上

每一条都能当场核对。不是再做一个目录或搜索。

前面说的问题 本系统的做法 落在哪一环
高质量只有业务有；越采越全，质量不涨 采集只同步结构，不生产口径。语义仓留给 steward。没有人写，就不空造一层。 采集 ≠ 维护
每接一个新源，都要平台改内核或堆一次性脚本 Workbench 暴露稳定 ChangeSet / HTTP 接缝和对账 kit。开发者独立实现 Connector，只声明它能写的 Scope，先预览再提交。 开放扩展
业务不敢写：一入库就被覆盖 知识方在自己的仓和定义分区中维护、审核、发布。采集改 structure，动不了 definition；Workspace 组合后仍不转移所有权。 所有权
提案、已发布、一次失败运行混在同一处 三种承诺分开：生效、提案、只追加的事件。合入主干不等于对外。 写面
值班读到正在改的草稿 每个读者任务开始时解析 Workspace selector，命令内固定 pin。新任务看到已合入的新 commit，旧 pin 仍可重放。 发布
用错了只能再搜一轮；优化没有坐标 引用带走对象、版本、来源。对账对准这一条再改。派生钉死输入版本和算法。 可溯源
看见知识被当成能查表 仓管谁能写、谁能发。SELECT 仍问 Ranger。底座不坐查询路径。 边界

用例把最硬的几刀演一遍：口径不被覆盖、改了先发布、对数能追到。

MVP 交付范围

MVP 交付的是可工作的 Workbench，不只是一组底层接口

底层协议已经证明能跑。MVP 要把它变成角色可以直接完成任务的产品面，并保留 Connector 和 Agent 的开放接入能力。

Workbench 模块 主要用户 可以完成的具体任务 底座服务
1. 知识维护台 业务 owner / steward 按自己负责的对象查看当前定义；编辑单个知识分区；保存候选；查看 diff、历史和来源；发起审核。 稳定对象身份、分区写入、版本历史、来源信封、越权拒绝。
2. Connector 开发与接入台 源系统 / 平台开发者 查看接入契约与示例；为源数据映射对象和 Aspect；声明 Scope；执行 dry-run；预览 ChangeSet；提交并核对同步结果。 Connector Preview kit、JSON ABI、HTTP/CLI 写入、Schema/Scope 校验、CAS 与幂等。
3. 审核与发布台 steward / reviewer 预览候选对共享 Workspace 的影响；运行校验；收集业务审批证据；合入发布；必要时回看或回退旧版本。 Proposal、Preview、Gate、Validation、Merge；候选与已发布版本隔离。
4. Workspace 消费台 分析师 / 应用 / Agent 选择公司、团队或个人 Workspace；浏览、搜索和读取发布知识；查看引用、来源和版本；把引用交给下游结果。 多仓组合、一次任务固定 pin、索引定位后回读权威、精确读与溯源。
5. Workspace VFS 人 / Agent / 开发工具 把多个 mount 当一棵树执行 list、glob、grep、read、write、edit、remove；本机可 checkout，外部 Harness 可直接挂虚拟文件系统。 路径唯一归属、权限裁剪、固定 pin、RouteMount 写回、CAS、幂等与逐仓结果。
6. Agent Q&A 运行时 Agent / 应用开发者 稳定问题读取知识文件；变化快的问题调用外部 MCP；发布类动作加载 Skill 后调用 MCP/API；执行结果按需沉淀 receipt。 Knowledge Catalog 治理 Skill 文件与版本；外部 MCP 提供实时状态，外部系统最终执行和授权。
7. 治理配置台 Catalog 管理员 登记仓；定义 Workspace；给角色授权；配置发布门禁和出站通知；查看 Catalog 变更；退役或归档。 Catalog、Repository ACL、Workspace 配方、Gate、Hook、审计历史。
8. 开放服务接口 Connector / Agent / 现有平台 通过同一组 HTTP/CLI 动词写入、读取、检索、发布和查询来源；把能力嵌入现有门户、流水线与 Agent。 统一错误信封、命令幂等、版本坐标和稳定契约；Workbench 与自动化使用同一语义。
知识方的承诺

能维护，但不会失去所有权

知识方控制自己的仓、定义分区和发布权。Connector 只能写被授权的 Scope；Workspace 只组合；索引只定位。任何一层都不能把知识变成平台的可覆盖副本。

开发者的承诺

能扩展，但不被锁进插件宿主

Connector 可以独立选语言、SDK、调度和部署方式，只需遵守 ChangeSet 与 Scope 契约。Workbench 提供预览和提交入口，不接管源凭证与 checkpoint。

本期边界：不替换 WeData、Ranger、查询引擎和 Wiki；不做通用本体、自然语言问数、全量生产灾备，也不让 Agent 自动发布业务口径。

用例：业务肯写之后，系统怎么托住

三刀对准核心矛盾：口径不被覆盖、改了先发布、对数能追到。第四条是后置：草稿如何进入组织仓。

知识资产 · 数仓第一落地 步骤 1

机制讲到能拍板

协议只补三样：身份、来源、写边界。加上发布。不做，信任立刻收回。细节见设计文档。

身份

对象身份嵌在内容里，不等于路径。维护单元是「对象 + 分区」：采集和 steward 各写各的，互不覆盖。权限按仓划。

来源

每个值带着来源信封：从哪来、谁写的、是否派生。派生必须钉死输入版本和算法。评测对准这条链，才能一版一版改。

写边界

一次写入只选一个仓、一种承诺：生效、提案、或只追加事件。业务钉死的一代才对外；读者不跟主干。

业务 / 采集 / 提案各按权限写入
→
写面生效 · 提案 · 事件
→
知识仓资产 · 版本 · 记录
→
发布业务认领的一代
→
读者人与消费 Agent · 带走引用
→
主动控制派维护 Agent · 候选回写

检索只用来定位，命中后必须回读原文。这是和「再做一个搜索」的分界。

第一落地：数仓三个仓，不合成假权威

按谁是权威拆仓，不按文件夹拆。物理层可以先采；语义层必须等业务肯写。

物理层仓

表、列、作业、列血缘。来自 Hive / 调度等源系统，正式写入。列因血缘需要独立身份，不嵌回表里当路径。

语义层仓

指标、维度、语义模型、术语。这是业务的资产仓：口径由 steward 认领和维护。没有人愿意写，就不空造一层。

观测仓

质量、用量、作业实例。只追加，不覆盖定义。一次失败运行不得改掉作业权威 SQL。

表名、目录路径、指标编码都是源系统键，不是对象身份。 Schema 也是知识：入库走同一写面，草稿不进项目 git。

业务验收

MVP 是否有价值，用八个真实动作验收

不以收录条数、页面数量或搜索命中率替代价值。只看业务是否愿意交付、消费是否稳定、出错是否能闭环。

验证场景 通过标准 可观察的业务价值
业务交付口径 steward 能在不修改采集代码的情况下，认领、修改并发布一条指标定义。 口径从聊天和熟人依赖，转成可交接资产。
开发者接入新源 开发者不修改 Workbench 内核，基于 Connector 契约完成映射、Scope、dry-run、预览和一次真实提交。 新来源可以由最懂源系统的团队独立接入，平台扩展不再依赖核心版本发布。
平台再次同步 源表结构更新后，业务定义保持不变；Connector 越过 Scope 的写入被拒绝。 知识所有权不因接入和组合而变化，业务敢持续维护，平台也能继续自动采集。
人和 Agent 消费 同一任务读取固定发布代，并能带出对象、版本和来源。 跨团队协作与自动化建立在同一份可核对上下文上。
Agent 通过 VFS 工作 Agent 不接收 Repo 路由即可跨 mount list/read/grep；写反馈时自动落入目标仓。只读、无权和 stale base 均被稳定拒绝。 现有 Agent 和开发工具无需学习 Catalog API，就能安全进入、使用并维护知识。
实时问答与外部发布 同一任务中，Agent 从固定版本知识回答口径、用 MCP 读取当前作业状态；发布请求必须加载已发布 Skill，并由外部系统再次鉴权。 既能回答“我们认什么”，也能回答“现在怎样”，还能安全完成动作，且三者不会混成一份过期知识。
口径发生变更 新版本发布前不影响线上；发布后新任务读新版本，旧任务仍可重放。 变更可控，减少报表前后不一致和线上争议。
发现使用偏差 能定位到具体资产和版本，查看差异与来源，形成修订提案。 复盘从「再搜一轮、再问一圈」变成对准问题修复。

立项后的直接收益：减少重复确认和口径争议，降低关键知识对个人的依赖；为后续 Agent 规模化使用业务知识建立可追溯的信任边界。

底层已经能跑，立项重点是把它做成 Workbench

不是批准「研究一下 Catalog」。协议、CLI/HTTP 和数仓代表旅程已有证据；本期把它们收成角色可直接工作的产品面。

已具备

  • Go 参考实现：写面、读面、多仓 Workspace、提案审核与发布。
  • Connector 入站契约与对账 kit；真实 MySQL 结构同步、增量事件、幂等与 checkpoint 旅程已跑通。
  • Workspace mount、checkout 与 HTTP VFS 已具备；DSH FileSystem 已实际走通跨 mount list/read/write/edit、CAS 和权限拒绝。
  • Skill 可以作为 Workspace 中的版本化文件被真实 DSH Agent 加载；知识发布、权限拒绝和六角色闭环已有模型证据。
  • 本地权威用 Git，检索投影用 SQLite；可换引擎。
  • 一致性测试覆盖身份、冲突拒绝、整批原子、命令可重试、来源约束、发布指针。
  • CLI 与 HTTP 使用同一套动词；公司三仓、两 Workspace、四类角色的工作台旅程已验证。

MVP 要补成产品的

  • 知识维护台：对象列表、编辑、diff、历史、来源、提案、审核与发布。
  • Connector 开发与接入台：契约示例、Scope 配置、dry-run、ChangeSet 预览和同步结果。
  • Workspace 消费台：浏览、搜索、精确读取、版本与来源引用。
  • VFS 产品面：树结构、mount 来源与读写状态可见；提供本机 checkout 和 Agent Harness 接入指引。
  • Q&A 运行时：给试点 Agent 配置外部 MCP，验证“知识文件 + 实时观测 + Skill 编排外部动作”的三路分流。
  • 治理配置台：仓、角色权限、Workspace、Gate、Hook 与收场动作。
  • 接试点真实源与业务口径，并把版本/来源带入一个真实消费应用或 Agent。
  • 满足试点所需的持久、多进程、恢复和基础运维，不把参考实现直接包装成生产承诺。

留到 MVP 之后

  • 通用本体、任意图查询、全库自然语言查仓。
  • 跨仓假事务、运行时跟随最新主干。
  • 指标查询运行时、统一 Connector 插件宿主、托管所有源 SDK。
  • 主动控制自动调度维护 Agent；即使后续建设，也只生成候选，不自动发布业务口径。

风险与边界，写在立项里反而更可信

承认的限度

  • 一致性测试证明的是协议语义，不等于生产级持久、并发和灾备认证。
  • 参考实现尚未提供通用 MCP 网关；实时观测和外部动作由 Agent Application 连接现有 MCP/API，Knowledge Catalog 只治理其 Skill 与结果文件。
  • 知识正确性仍取决于源系统与 steward；底座不自动裁决语义冲突。

组织侧依赖

  • 按治理边界拆仓，而不是按团队文件夹拆仓。
  • 应用必须把版本和来源传到最终引用；丢掉这一跳，溯源中断，质量改进失去坐标。
  • 表级 SELECT 继续由源系统强制。项目成功不表现为「Catalog 能授权查数」。

需要达成的共识

申请批准 MVP 的范围与成功标准

本期只验证可信知识闭环是否成立；通过业务验收后，再讨论规模化存储、更多领域和主动维护。

  1. 业务目标：把至少一条真实数仓口径从认领、发布走到稳定消费和问题追溯，证明知识可以跨人、跨团队复用。
  2. MVP 产品：一个 Workbench 加一棵可挂载的 Workspace VFS，面向知识维护者、Connector 开发者、治理者和消费方，覆盖接入、维护、审核发布、联合读取、文件式使用与追溯；试点 Agent 同时接入外部 MCP，并从 Workspace 加载受治理的 Skill 文件。
  3. 责任边界：平台维护物理/观测，组织维护语义；采集同步结构，不生产或覆盖口径。
  4. 所有权承诺：知识仍由各仓和负责人控制；Connector 受 Scope 限制，Workspace 只组合，索引只定位。
  5. 系统边界：不替换 WeData、Ranger、Wiki 和查询引擎；Knowledge Catalog 只治理文件、版本与所有权，实时状态由 MCP 观测，外部动作由目标系统执行和授权。
  6. 通过标准：业务愿意写，采集盖不掉，Agent 能通过 VFS 安全工作；知识回答带版本与来源，实时问题不读取旧快照，发布动作必须经已发布 Skill 编排和外部系统鉴权。
  7. 后续投入门槛：MVP 通过真实业务验收后，再扩更多数据源、领域、生产级运维和主动维护能力。
