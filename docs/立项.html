内部立项材料 · 2026-08

知识要成为资产，业务得愿意写进来。

核心矛盾：高质量口径只在业务手里，现有系统却让他们不敢入库。 采集越全，真东西越留在聊天里——写了被覆盖，改了没版本，用了追不到。 立项要买的是共建条件，不是又一个目录或 RAG。

请求批准 建设组织级知识资产底座，第一落地数仓域（物理表/列/作业/血缘 + 语义层指标/维度）。

要解的不是缺系统

越采越全，真口径越不敢入库

组织不缺 Wiki、数据目录、向量库。缺的是业务肯认领的知识。系统越全，高质量越留在聊天里。

表象

像是缺统一入口

  • 口径、说明、血缘散落在 Wiki、目录、群聊。
  • 值班和 Agent 只能搜到「很像」的段落。
  • 于是继续加采集、加检索、加模型总结。
实质

是不敢把真东西交出来

  • 口径只有业务写得出，采集永远采不到。
  • 一入库就失控，所以真东西不进系统。
  • 入口再统一，资产还是空的。

高质量做不出来，只能共建出来

采集、检索、模型都不产生口径。立项买的是业务肯写、肯改的条件：写了不被覆盖，改了有版本，用了能追到。

做不到的事

用采集和模型生产高质量

  • Metastore 知道表有哪些列，不知道这张表在业务上代表什么。
  • 作业日志知道跑过什么 SQL，不知道哪一句才是权威定义。
  • Wiki 和向量库能堆材料，不能让人对其中一句负责。
要成立的事

让业务愿意把口径写进来、改下去

  • 写进去的分区，采集覆盖不了。
  • 谁能看、谁能改、谁能发布，说得清。
  • 改了有版本；用了能回到对象、哪一版、从哪来。优化才有坐标。

今天的税：不是缺系统，是没人肯把真东西放进来

角色不同，根因就一句：真东西放进去会失控。高质量只能留在聊天里。

角色 今天怎么干 为何不共建 / 共建了也会坏 本系统怎么托住
业务 / steward 口径写在 Wiki、表格、口头约定。真正的定义不敢放进「平台」。 写了被采集覆盖；改了说不清版本；谁用过哪一版找不到。交出去等于失去控制。 语义仓只给 steward 写口径；发布权单独授；历史和来源可查。
数仓 / 平台 持续采集表、作业、血缘。目录越来越全。 采得到结构，采不到语义。越采越全，质量不涨。一次运行的残缺 SQL 还会改掉作业定义。 采集只写物理仓分区；实例走追加，不许覆盖作业定义；改名不断对象身份。
治理 / 安全 表权限在 Ranger / Unity；知识侧几乎没有边界，或误做成表 GRANT。 业务不敢把敏感口径放进来。看见知识被当成能查数据。 知识仓有自己的写/发权。SELECT 仍问 Ranger。两套授权不合成一条。
消费方 · 人与 Agent 搜门户、搜向量库、问同事。拿到的是没人认领的浅层拷贝。 用错了无法回到对象和版本，返工只能再搜一轮。优化没有稳定抓手。 读已发布的一代；引用带对象、版本、来源；对账对准这一条再改。

所以口径留在聊天里

业务问「GMV 怎么算」。难的不是找不到文字，是没人肯把认领过的口径放到改了能回退、用了能追到的地方。

今天

真知识不入库

  1. 平台采到表和作业，口径仍在群聊和 Wiki。
  2. 有人试着写进目录，下次采集把注释盖掉。
  3. 提案、已发布、一次失败运行混在同一处。
  4. 引用了一段文字，问不出是谁的、哪一版、从哪来。
→
立项后

业务肯写，因为托付得起

  1. 口径作为语义层资产入库，有主人、有发布。
  2. steward 的定义和采集的结构不在同一写入单元。
  3. 作业定义与一次运行分开。
  4. 每次使用能回到对象、版本、来源。返工对准同一条知识。

市场上已有的「Catalog」并不解决这件事

它们能展示、能检索、能管表权限。几乎都不能让业务把口径当资产来维护。

产品 它真正在做 在不在查询路径 缺什么
Unity / WeData Catalog Lakehouse 运营目录：名字、元数据、GRANT、临时凭证 在。引擎先问它再读存储 采集与注释易互相覆盖；不是业务共建的资产账本
WeData 资产目录 + Unity Semantics 发现门户 + 指标语义层 / headless BI 门户不在；语义层是查询产品 语义层是查询产品，不是口径资产仓
Google Knowledge Catalog 发现 + AI 上下文图（Entry / Aspect） 不在 发现与上下文图，不是业务维护资产的账本
DataHub / Atlas / 文档 Wiki 元数据湖或给人看的页面 不在 默认最新一份；难谈主人、版本、来源
RAG / 向量库 相似检索 不在 能搜到相似，不能认领。没有版本和来源，质量无法迭代

运营目录、语义查询、发现门户都该继续存在。缺的是下面这一层：业务肯共建的知识资产底座。底座不坐查询路径，也不替代 SELECT 强制。

这是什么，不是什么

写清楚，立项才不会被收成「再做一套 WeData」或「再做一个企业搜索」。

是

组织级知识资产底座

  • 把口径登记成有主人、有版本、有来源的资产。
  • 协议只补存储给不了的三样：身份、来源、写边界。
  • 业务发布哪一代，读者就读哪一代。
  • 协议与存储解耦：本地起步，规模化换引擎，语义不变。
  • 第一场景是数仓知识，不是数仓引擎。
不是

不要立项成这个项目

  • 不是检索应用，不是用模型生产口径。
  • 不是 Unity / WeData 运营目录，不进 SQL 查询路径。
  • 不是指标查询引擎 / 问数产品。
  • 不是通用本体、通用 PATCH、跨库事务。
  • 不是把 Ranger 表权限搬进知识仓。

一间 Catalog · 多仓 三种写入：生效 / 提案 / 事件 发布 = 钉死一代 不跟随 latest 索引不是权威 组合不发权

共建所要求的能力

信任是业务可以核对的四件事

内容对不对仍靠业务和源系统。底座只保证共建可核对。做不到，信任立刻收回。

可治理

有权限，有边界

谁能写哪一块、谁能发布，按仓划清。采集是写入者，不是主人。看见知识不等于能查表。

可维护

有版本，有写面

正式生效、候选提案、只追加的事件，三种承诺分开。对象身份不跟路径走，改名不断引用。采集和 steward 各写各的分区，互不覆盖。

可观测

有记录，能回放

谁在何时对哪条知识做了什么，留在仓的历史上，而不是散落在聊天和工单里。审批、回退、追责有同一本账。

可溯源

知来处，才能稳定优化

从哪来、谁写下、用的哪一版，必须能问回来。评测和返工对准这一条，质量才能一版一版改。

架构全景

朱线是闭环：采集 → 维护 → 检索 → 消费 → 反馈回写。点框看这一层承诺什么。

源系统只提供当前态。采集对账后写入物理仓，运行实例追加到观测仓。采集不是主人，不能写口径。

谁能负责，谁就维护

不按组织架构复制三套仓。第一刀两套权威：平台对源负责，组织对口径负责。一起被看见时，钉死各仓那一代，并存、带来源。

为什么要分

平台只能对「源里当时是什么」负责，组织才能对「我们认什么口径」负责。放进同一份可互相覆盖的文档，高质量的人就不会写。

联合不是覆盖

读者同时需要表和口径，靠钉死的配方拼在一起看。系统不宣布哪边压过哪边。

个人放在哪

未发表的理解可以有自己的仓，那是后置。要进组织：在组织仓提案，来源指向个人钉死的版本。不拷贝，也不把个人仓直接挂进共享 Workspace。

核心矛盾怎么落到系统上

每一条都能当场核对。不是再做一个目录或搜索。

前面说的问题 本系统的做法 落在哪一环

用例：业务肯写之后，系统怎么托住

三刀对准核心矛盾：口径不被覆盖、改了先发布、对数能追到。第四条是后置：草稿如何进入组织仓。

知识资产 · 数仓第一落地 步骤 1

机制讲到能拍板

协议只补三样：身份、来源、写边界。加上发布。不做，信任立刻收回。细节见设计文档。

身份

对象身份嵌在内容里，不等于路径。维护单元是「对象 + 分区」：采集和 steward 各写各的，互不覆盖。权限按仓划。

来源

每个值带着来源信封：从哪来、谁写的、是否派生。派生必须钉死输入版本和算法。评测对准这条链，才能一版一版改。

写边界

一次写入只选一个仓、一种承诺：生效、提案、或只追加事件。业务钉死的一代才对外；读者不跟主干。

业务 / 采集 / 提案各按权限写入
→
写面生效 · 提案 · 事件
→
知识仓资产 · 版本 · 记录
→
发布业务认领的一代
→
读者人与消费 Agent · 带走引用
→
主动控制派维护 Agent · 候选回写

检索只用来定位，命中后必须回读原文。这是和「再做一个搜索」的分界。

第一落地：数仓三个仓，不合成假权威

按谁是权威拆仓，不按文件夹拆。物理层可以先采；语义层必须等业务肯写。

物理层仓

表、列、作业、列血缘。来自 Hive / 调度等源系统，正式写入。列因血缘需要独立身份，不嵌回表里当路径。

语义层仓

指标、维度、语义模型、术语。这是业务的资产仓：口径由 steward 认领和维护。没有人愿意写，就不空造一层。

观测仓

质量、用量、作业实例。只追加，不覆盖定义。一次失败运行不得改掉作业权威 SQL。

表名、目录路径、指标编码都是源系统键，不是对象身份。 Schema 也是知识：入库走同一写面，草稿不进项目 git。

立项要买下的价值

不是元数据更全，也不是 Agent 少幻觉。是让口径成为可共建的资产，质量改进有坐标。

组织侧

  • 口径从聊天变成可交接的资产。
  • 业务肯写：写了不被覆盖，改了有版本，用了能追到。
  • 平台不再用采集冒充语义。WeData / Ranger / 调度继续做自己的事。

质量与消费

  • 用错了能回到对象、哪一版、从哪来。优化对准改，不靠重采碰运气。
  • 人和 Agent 读业务发布的一代，不读正在改的草稿。
  • 本地跑通闭环；规模化换存储，不必重做领域模型。

不是从零画架构。协议与参考实现已经在

立项不是批准「研究一下 Catalog」。是把已可跑的协议推进到数仓：接真源、业务能认领、消费能溯源。

已具备

  • Go 参考实现：写面 / 读面 / 组合发布 / 提案合入。主动控制尚未做成产品能力。
  • 本地权威用 Git，检索投影用 SQLite；可换引擎。
  • 一致性测试覆盖身份、冲突拒绝、整批原子、命令可重试、来源约束、发布指针。
  • 本机命令行与 HTTP 门面可走通挂仓、写入、钉发布、按发布读。

立项要补的

  • 数仓场景：源系统对账入库（表/作业/口径），接调度与 metastore。
  • 与 Ranger / 内控并行：权限快照可进仓，放行不进仓。
  • 生产存储与运维保证（持久、多进程、恢复）——参考实现尚未声称这些。
  • 业务侧工作台：让 steward 写口径、看历史、发发布，不必先懂协议动词。
  • 消费约定：引用必须带到对象、版本、来源，主动控制才接得上。
  • 主动控制：按消费反馈出候选，经写面回知识；不直写仓，不自动发布。

故意不做

  • 通用本体、任意图查询、全库自然语言查仓。
  • 跨仓假事务、运行时跟随最新主干。
  • 指标查询运行时、采集器框架做进协议根。
  • 用提案流做无人值守同步；自动同步走正式写入。

风险与边界，写在立项里反而更可信

承认的限度

  • 一致性测试证明的是协议语义，不等于生产级持久、并发和灾备认证。
  • 跨进程幂等与 MCP 网关尚未做；HTTP 门面是同一套动词，不是另一套产品。
  • 知识正确性仍取决于源系统与 steward；底座不自动裁决语义冲突。

组织侧依赖

  • 按治理边界拆仓，而不是按团队文件夹拆仓。
  • 应用必须把版本和来源传到最终引用；丢掉这一跳，溯源中断，质量改进失去坐标。
  • 表级 SELECT 继续由源系统强制。项目成功不表现为「Catalog 能授权查数」。

需要达成的共识

立项要对齐的几件事

不求批准一份功能清单。先就核心矛盾对齐，后面的范围才有依据。

  1. 核心矛盾：高质量口径只在业务手里，却不敢入库。立项买共建条件，不是再做运营目录或 RAG。
  2. 采集同步结构，不生产口径。底座先赢得共建，再谈人和 Agent 怎么读。
  3. 第一落地是数仓域：物理层、语义层（有口径源再上）、观测。读者跟发布代，不跟主干。
  4. 知识平面和数据平面分开。仓管谁能写、谁能发；SELECT 仍由 Ranger / 引擎决定。底座不进查询路径。
  5. 协议在底座，采集在场景。源系统对接留在数仓落地，不把采集器做进通用命令行。
  6. 按谁能负责拆仓。第一刀：平台维护物理/观测，组织维护语义。同一对象先分区。个人仓是后置发表路径，不是第三套必建产品。
