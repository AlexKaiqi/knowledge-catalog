# 索引控制

知识已经发布，不代表检索已经能回答；索引曾经就绪，也不代表重启后它还在。
索引控制负责把持续变化的服务需求收敛到可核对的派生状态。它拥有后台维护与恢复，
查询只消费结果，Writer 只负责知识发布。它是派生对账面，不是采集写面：业界所称的
ingestion control 只作对照名词，本系统的叙述继续使用投影控制、Collector、Observer 与
Retriever，不因目录产品惯用 ingestion 就把对账面写成采集写面或让它接收变更写入。

## 先确定应当服务什么

维护目标不能只有源仓最新版本。系统还要服务当前 Dataset 固定的来源版本，以及这些版本
声明下仍承诺提供的动态值。源 HEAD 前进，不意味着旧服务版可以回收。

| 目标 | 对账依据 | 不能推导出的承诺 |
|---|---|---|
| Snapshot 最新投影 | 已发布版本与提供方实际投影 | 完成工作账不证明物理索引仍存在 |
| Dataset 服务版投影 | 当前发布记录中的固定来源版本 | 不自动为全部历史版本永久托管搜索 |
| 动态 State 投影 | 固定声明、来源观察与有效服务需求 | 声明版本没变不证明外部值没变 |
| 其它 Snapshot 消费者 | 自身策略与实际派生状态 | 正文预热完成不授予搜索就绪 |

应用服务从 Catalog 恢复服务需求，经窄端口交给控制器；索引组件不导入 Catalog，也不在
查询到来时才登记必须维护的目标。同一来源版本可以被多个 Dataset 共享，授权和文件范围
仍在消费时执行；动态观察还须满足相容的来源授权与共享边界。

动态 State 投影采用完整 object 文档：一篇文档同时携带 Snapshot 字段与已成功观察的
State 字段，静态条件与动态条件因此能在同一文档上求 AND，首版无需跨两个提供方的候选集
求交。代价是静态字段变化时动态文档要整体重拼，generation 等控制元数据独立维护，
观察更新只改写动态侧字段。

## 通知缩短延迟，对账保证恢复

Snapshot 推进和外部变化通知只表示“值得检查”。重复、乱序、丢失或工作账中途未保存，
都不能造成永久不再追赶。启动与周期对账重新比较期望目标、派生介质的实际依据和工作进度。

已完成进度是调度信息，不是权威。即使工作账仍在，也要发现被删除的索引、重启丢失的缓存
或已经不适用的提供方配置。恢复派生物不推进知识仓，不重发 Dataset，也不重新授权。

Writer 接受提交后只交出推进提示，不等待引擎。控制器只在长寿命服务中运行；打开一次
客户端或进行一次搜索不能暗中启动全库恢复。显式同步保留为管理与排障能力，不成为通知
丢失后的唯一救济方式。

State 就绪后仍需继续核对来源。只有最新值的来源，可以枚举固定声明下已知身份后重取；
有可靠增量能力的来源，可以在有效检查点上续读。断档时回到来源支持的恢复方式，不能把
通知序号当成已完整取值的证据，也不能凭源不再发通知继续承诺新鲜。

## 只有解释连续，才允许增量

安全增量需要旧投影确实对应变化起点，逻辑声明和物理规则仍相容。依据断开、初次构建或
规则改变时重建；已到达相同目标则避免重复写入。控制器不能凭一个状态名称决定这些事实。

普通内容变化先定位受影响知识身份，再按相应版本重新解释与编译。删掉某个 Aspect 不等于
删除整个对象；只改未参与检索的正文不必重写物理文档。Schema、资源声明等间接依赖变化
则必须扩大影响范围，不能只重编声明文件自身。

全量构建和增量更新复用同一解释与编译路径，结果应等价。不能给动态观察另开一条直接
拼装引擎 JSON 的捷径，否则精确读取与搜索会对同一知识产生不同解释。

增量约束覆盖取值、观察存取、摘要计算、编译和物理写入的整条路径。只减少外部请求，
仍为单对象变化复制全部观察或重建整库，不能算增量。首次构建和断档恢复可以有界分批
遍历，但需能与日常增量工作区分，不能藏在一次消费请求中。

用「投影内容摘要未变」跳过物理写入时，摘要必须覆盖全部会影响检索的内容并保留数值
精度；漏掉字段或丢失精度会把真实变化误判为无变化，造成查不到的静默漏检。这是 no-op
判定的正确性条件，不只是减少写入的技巧。

## 发布必须保持候选与正文一致

准备中的派生内容不能混进已发布查询依据。新版本可服务之前，旧版本仅在仍满足本次请求
条件时继续交付；不能把旧候选和新正文拼成一个虚假的一致版本。当前授权仍独立求值，
不能因为内容依据固定而冻结权限。

增量发布推进可见版本前，必须证明本批全部写入涉及的变更均已可检索；只等最后一批刷新，
不能证明前批涉及的分片已经就绪。该证明要在不引入一次全索引 count 或 refresh 的前提下
成立，与稳态禁止全索引操作的约束同时满足。

动态索引发布前，要先保存能按该观察依据回读的完整值。观察保存与索引发布之间可以失败，
失败留下待恢复工作，不能留下查得到却读不回的公开命中。已经发布的旧观察是否还能使用，
分别取决于声明兼容、来源授权、保留期限和时效要求。

同依据的观察丢失时不能回退最新值；分页所用投影不再可解释时，应明确终止并要求重新查询。
提供方更新与候选读取之间的竞态也必须遵守这一要求，不能靠“返回部分结果”掩盖依据错误。

## 独立进度、失败隔离与退出

每个消费者、来源和维护目标保留自己的进度和失败结果。一个来源超时不能阻塞其它独立任务，
但查询若依赖这个来源，仍不能虚报完整。所有消费者不共用一个完成水位；调度共用不等于
语义上的进度共用。消费者需要稳定、可区分实现或配置变化的身份，恢复时才能判断旧进度
是否仍适用；一个进程重新创建实例不表示出现了一项全新的服务需求。

重试、每轮工作量和缓存预热要有界，不能在每次周期对账时无条件全库扫描。后台访问来源
使用独立服务身份，不能借用最近请求或通知的用户凭证。

Dataset 退役、服务版切换、runtime 退出和观察过期各自发生。仍被承诺服务的依据不得提前
回收；无法继续维护时要暴露不可用。没有消费者依赖后是否仍为历史检索保留投影，由明确的
服务政策决定，不从源版本存在推导无限保留。

## 取舍与待决边界

选定后台对账与可丢通知、读取端口与维护端口分离、固定版本共享投影；承担延迟和恢复工作，
换取写入与消费路径清晰。否决查询现场建索引、按 Dataset 或主体复制索引、用工作账代替
实际状态，以及通过投影成功反推写入成功。

State 的默认时效、恢复预算、观察保留和服务需求退出政策仍需公开合同承接；多副本调度
不由本篇凭空承诺。现有实现的静态审阅差距记录在 TASK，不能将这些应然保证写成已验收能力。

## 方向性用例

### U1：提交已成功，搜索引擎离线

发布者仍拿到可复核的知识回执。搜索明确报告未就绪，恢复引擎后后台自行追赶；
不能撤销源提交，也不能返回成功的零命中。

### U2：大量对象中只有一个 State 变化

系统只重取、编译和写入受影响部分，观察保存与摘要维护也满足增量要求。
另一来源失败时独立工作继续，依赖故障来源的查询仍如实报告限制。

### U3：通知全部丢失，随后替换进程

系统仅凭权威版本与服务需求恢复搜索及其它消费者。旧工作账显示完成而物理索引丢失时，
仍应恢复；不要求用户先进行一次查询或手工重发通知。

### U4：HEAD 已前进，Dataset 仍服务旧声明

Snapshot 和动态 State 都按各自有效目标维护。旧服务版不会因 HEAD 前进失去投影，
也不会偷偷改用新声明取值；服务依赖退出后才能按保留政策回收相应维护结果。

### U5：观察已保存，索引发布中途失败

消费者仍使用先前可解释的依据，或得到明确不可用。后台恢复后不会混合两轮观察，
也不会通过重新取最新值假装恢复了原查询。

### U6：新增正文预热消费者

预热可以独立失败、恢复和限量运行，不要求实现搜索提供方；预热成功不能改变检索就绪。
删除缓存后同版本读取仍可回源，不改变知识与 Dataset 发布记录。
