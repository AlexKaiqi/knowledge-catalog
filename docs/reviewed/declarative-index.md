# 声明式索引

## Goal

让接入方说明「这份知识允许怎样被查询」，而不必知道搜索引擎怎样建表：把这个意图变成
可检查、随知识版本固定的逻辑访问合同。物理索引、后台就绪和一次查询的执行计划各有
自己的责任，不能被一个「已建索引」混在一起。

## Non-Goals

- 不拥有物理索引、后台就绪或查询执行；它们分别由索引控制与检索承担。
- 词表不扩成第二套查询语言：具体词表由协议维护，prefix、range 属查询算子而非声明。
- 声明不是授权：「这个字段可过滤」不表示任何主体可以用它查询。
- 不另造一套 Schema 迁移制度；业务兼容性由知识写入边界判断，本文只解释检索影响。
- 不把「各家都这样做」当作决定依据；行业参照只用于说明取舍方向，可定位调研来源保留在
  研究资料中。

## 声明放在知识里，物理选择留给部署

Schema 是经 Writer 发布的知识。字段的逻辑类型与访问意图跟随 Schema 版本，能被接入方
和消费方查看、评审与复核。当前公开合同支持全文匹配、类型化过滤和排序；具体词表由
协议维护，不在设计书扩成第二套查询语言。

词表保持 text、filter、sort 三类是有意的：keyword、lexical 之类新增会混淆整值匹配与
全文发现，prefix、range 属于查询算子而不是声明；provider、stored、summary、分片数或
分析器名称是部署与物理信息，不进入业务访问声明。关系定位由关系知识查询承担，不塞进
字段声明。访问声明还在 Schema 发布时与逻辑类型联合校验：复合正文可以保留为知识，但
没有定义标量解释的复合值不能声明 text、filter 或 sort 标量访问；已有多值标量与引用
列表沿用各自既有语义。

声明的是允许怎样问，不能写搜索引擎名称、索引实例、分词器或物理列布局。否则换引擎会变成
修改领域知识，部署优化会迫使所有发布者重发 Schema。代价是部署必须独立说明自己能实现
哪些声明，无法满足时明确拒绝，不能将声明翻译成一个语义相近但未经证明的实现。

声明也不是授权。“这个字段可过滤”不表示任何主体可以用它查询；尤其不能把外部权限快照
的正文自动混入全文检索。哪些信息允许成为发现线索，需要发布者在设计 Schema 时明确选择。

## 三次决定，三种变化原因

| 决定 | 依据与产物 | 为什么独立 |
|---|---|---|
| 逻辑编译 | 固定知识版本中的 Schema，得到 AccessSpec | 解释字段身份与允许的访问方式，不依赖引擎 |
| 物理实现 | 逻辑合同与提供方配置，得到投影方案 | 调整引擎或物理配置可以重建派生物，不修改知识 |
| 查询规划 | 本次表达式、范围、版本、能力和预算，得到 RetrievalPlan | 有某种索引不证明它能正确执行任意查询 |

逻辑声明一致，不表示物理实现没变；物理投影存在，也不表示指定知识版本已经就绪。
两类变化分别留下可核对的依据，控制器据此决定复用、增量或重建。使用者能分清缺声明、
提供方不支持和后台尚未完成，不把三者都归为“没有结果”。

## 字段身份必须保留语义上下文

同一个字段路径可能出现在不同 Schema、Aspect 或实体中，类型与含义并不相同。
字段必须在完整声明上下文中识别；简写只有在无歧义时才可解析，不能由加载顺序选中一个。

写入单元与候选单元也不同。维护一个 Aspect 或 Member 后，应按 Knowledge 的解释重新
形成所属对象的检索内容，不能把每个文件都当成新对象。Member 中的字段按成员值解释，
不会因数组位置变化而改变知识身份。

“字段适用但缺值”与“这个对象根本不使用该声明”要区分。缺值查询不能命中另一种 Schema
的所有对象；动态值取回失败也不能被解释成业务缺值。文本、数字、时间等保持逻辑类型，
不能为方便物理存储一律转字符串后仍宣称比较等价。

三种访问能力在声明层面互相独立：只声明文本发现，不隐式要求整值匹配或排序索引。
后端的词项长度、物理字段大小等限制不能通过静默漏值或截断改变发现、存在性或完整性
结果；部署无法满足声明时明确拒绝。多值字段上的条件保持既有的存在语义；「同一复合
成员满足多个条件」的成员作用域匹配只在真实场景提出要求时显式评审，不悄悄改变既有
AND 语义。

AspectSelector 只属于显式读取：检索文档的形状由 Schema 访问声明编译决定，查询端不能
用选择器重裁命中集；选择器解决的是读取组装，不是检索过滤。

Relation 的端点与方向可支持关系定位，业务属性仍遵循自身 Schema 声明；不能因为对象是
Relation 就绕开字段合同。命中坐标最终仍交给 Knowledge 回读，投影不成为第二份正文。
Schema 对象本身可以被读取、解析和溯源，但业务检索只用 Schema 解释字段：字段定义不作为
业务正文混入候选，Schema 发现走专门的类型浏览入口；将来若要搜索 Schema 对象，必须先
建立明确的检索合同。

## 声明演进必须有明确影响范围

只修改未参与检索的说明，通常不需要重写全部索引文档；改变字段访问方式、类型或解释，
会影响引用它的对象，不能只更新 Schema 对象本身。索引控制必须识别这种间接依赖。

旧 Dataset 固定旧版本的声明。新声明发布后不能让旧查询按新解释读取旧值，也不能复用
物理上看似相同、逻辑依据却不同的投影。替换分词或提供方时，新的物理实现先准备好，
再交给查询选择；不会因为 Schema 没改就跳过检查。

Schema 的业务兼容性由知识写入边界判断；本文只解释检索影响，不另造一套 Schema 迁移制度。

## 硬性约束 / Invariants

- 字段必须在完整声明上下文中识别；简写只有无歧义时才可解析，不能由加载顺序选中。
- 逻辑类型保持到候选与回读：不能为方便物理存储一律转字符串后仍宣称比较等价。
- 三种访问能力在声明层面互相独立；后端限制不能通过静默漏值或截断改变发现、存在性或
  完整性结果，部署无法满足声明时明确拒绝。
- 组合范围等标识不进入知识正文、编译产物或投影 mapping；否则修改组合配方会重写知识投影。
- AspectSelector 只属于显式读取；查询端不能用选择器重裁命中集。
- 命中坐标最终交给 Knowledge 回读，投影不成为第二份正文；业务检索只用 Schema 解释字段，
  字段定义不作为业务正文混入候选。
- 旧 Dataset 固定旧版本的声明；新声明发布后不能让旧查询按新解释读取旧值，也不能复用
  物理相似、逻辑依据不同的投影。

## 选定方案 / 被否决方案

选定 Schema 中的显式声明，避免按字段名、文件类型或正文样例猜测所有可查询能力。
选定逻辑编译与物理实现分开，承担能力探测和重建成本，换取发布语义稳定。选定词表保持
text、filter、sort 三类；否决 keyword、lexical 之类混淆整值匹配与全文发现的新增，也否决
provider、stored、分片数或分析器名称等部署信息进入业务访问声明。

否决在 Schema 中直接写引擎 mapping、将全部 JSON 默认开放查询，或把成功精确读取当成
能够搜索的证明。向量召回的声明与查询保证已选定并展开在检索篇；本篇只约束向量投影是
派生物，不是第四种字段访问声明。模型派生字段等扩展须先说明声明、版本和查询结果应保持
什么保证，再进入公开合同；不能只增加一个索引插件就把新语义视为已有能力。

## 方向性用例

### U1：发布者让说明可搜索、日期可排序

发布者通过 Schema 表达意图。消费者能了解有哪些合法字段；部署不支持其中一种能力时，
相应查询明确失败，不能退回字符串包含或本机扫描。

### U2：两个声明都有同名字段

消费者使用简写遇到歧义，系统要求明确上下文。不能因某个仓先被加载，就把数字条件
应用到另一个声明的文本字段。

### U3：调整检索声明，旧 Dataset 继续服务

新版本触发受影响对象的维护，旧 Dataset 仍按原声明查询。新投影未就绪时不借用旧版本
冒充新能力；旧版本也不被新字段解释污染。

### U4：只升级搜索提供方

知识与 Schema 不需要重发，物理投影可以重建。消费仍要重新证明能力、就绪和同依据回读，
不能仅凭逻辑声明摘要未变而跳过物理兼容检查。

### U5：对象不适用字段，或动态取值失败

缺值查询只表达声明适用范围内的业务缺值。无关 Schema、未观察与取值失败不得一起落入
“字段缺失”，避免把技术故障变成业务答案。
