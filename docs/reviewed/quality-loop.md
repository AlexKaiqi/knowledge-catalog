# 工程质量闭环

本文沉淀「控制代码质量」的长期方法论：质量控制在哪些层、观测结果往哪里去、
agent 协作下腐化为什么更快、各层权威归谁。它是工程过程文档，不定义协议形状、
字段或不变量 ID；本文的「门禁」「债」「信号」都是过程用语，不是协议对象，
协议名词以 [术语表](terminology.md) 为准。

## 1. 前提：腐化是趋势问题，不是单点检查问题

「每次开发完提交前检查」只覆盖最窄的一层。提交前检查拦得住明确违规（编译、类型、
契约、守卫），拦不住合规但变烂的 diff：复制粘贴式重复、绕过既有抽象的新特例、
迎合实现的断言、只增不减的分支与参数。业界方法论的共同形状是**反馈闭环**，
其中两个机制直接针对「慢慢烂」：

- **增量门禁（ratchet）**：质量门只对新增/变更代码生效，指标基线只紧不松，收紧必须
  人工显式确认。存量不追，增量不欠——腐化是趋势问题，控制趋势比清理存量便宜且可持久。
- **热点观测**：注意力跟着「变更频率 × 复杂度」走。复杂但常年不动的代码优先级低；
  又复杂又频繁变更的文件才是腐化实际发生的地方。单信号报警常是设计使然或误报；
  组合信号（churn × 复杂度）和方向（是否持续增长）比单点数值可信。

| 层 | 回答的问题 | 本仓权威位置 |
|---|---|---|
| 防（设计先行） | 这次改动要保持什么、明确不做什么 | [AGENTS.md](../../AGENTS.md)「交付」与各 owner 设计文档（Goal / Non-Goals / 不变量 / 选定与否决） |
| 拦（提交前自动检查） | 明确违规有没有 | [AGENTS.md](../../AGENTS.md) 工作方式与红线；检查体系由 [验证体系](test-catalog.md) 拥有 |
| 闸（增量门禁） | 这次有没有比上次更烂 | 方法论归本文；自动基线与指标尚未立项，立项前其唯一去处是 TASK.md 认领条目 |
| 审（语义复核） | 合规的 diff 是不是坏 diff | 信号采集与逐条判定流程由 [`.dsh/skills/code-signals-review.md`](../../.dsh/skills/code-signals-review.md) 拥有 |

- 协议 Gate / Hook（[Hook 与 Gate](hooks-and-gates.md)）是知识写面的
  证据门与出站扩展，与代码质量门禁无关；本文不借用、不改动它们的语义。
- 可采样的运行遥测归 [服务边界](service.md)；
  本文是工程过程，不是产品遥测。
- 不变量 ID 注册表归 [架构不变量](architecture-invariants.md)；
  本文不新增、不改写不变量。

## 3. 三出口：观测必须闭环

复核（真问题 / 设计使然 / 误报）之后的每个信号只有三个合法出口：

1. **当场修**：本变更范围内能安全修掉的，不留给下轮。
2. **登记为债**：条目形状 = 位置 / 信号 / 判定 / 处置 / 触发条件（什么情况必须回来
   处理）。登记位置尚未立项前，过渡期记 TASK.md 或交付说明，不允许「看到了但没记录」。
3. **升级为自动检查**：同类信号出现两次以上，就该变成守卫断言、契约或脚本，
   而不是继续靠人记。

判定本身是闭环的核心：

- **误报** → 回喂成更准的信号或显式豁免，否则规则越积越多，最后被整体绕开；
- **设计使然** → 写回对应 owner 文档，成为下次会话可发现的上下文；
- **真问题** → 走出口 1 或 2。

没有三出口，观测会退化成监控表演：信号越采越多，行为不变，腐化照旧。

## 4. agent 协作下腐化为什么更快

来源说明的机制见 §6：AI 辅助代码中复制粘贴式代码上升、移动/重构式改动下降、
重复代码块显著增多；AI 采用提升吞吐但与交付稳定性负相关。本仓据此作出的推论与对策：

1. **agent 没有跨会话记忆** → 不知道已有实现 → 重复造轮子。对策：写下来的合同与文档
   就是 agent 的外部记忆——这是「防」层（先写 Goal / Non-Goals / 不变量并引用 owner）
   对 agent 比对人更重要的原因。
2. **局部目标**（让当前任务通过）→ 绕抽象、加特例、断言迎合实现。对策：契约 /
   conformance / 架构守卫不可削弱、不用 skip 换绿（AGENTS.md 红线）；断言先红后绿。
3. **写速度远超审查带宽** → 审查被稀释。对策：小 diff 纪律；提交前先做一轮信号复核，
   把审查注意力集中在真信号上，而不是平均用力。
4. **agent 对硬门禁的服从度远高于口头约定** → 能自动化的信号尽快走出口 3，
   把约定变成门禁，而不是指望每次会话都记得。

## 7. 耦合与分层的计算方法

分层不只做布尔守卫（internal/arch），还要有程度度量与趋势。四个层次：

| 层 | 指标 | 数据源 | 本仓状态 |
|---|---|---|---|
| 布尔边界 | import 方向、闭集、无环 | internal/arch 守卫与闭集表面 | 已有 |
| 标量结构 | Ce、Ca、Instability=Ce/(Ce+Ca)、传播成本 | `go list -json` import 图 | `scripts/coupling`；首测基线 2026-09-23：23 单元、传播成本 38.74% |
| 行为耦合 | co-change 率（改 A 的提交同时改 B 的归一化比率） | git 历史 | 方法已验证；本仓历史由大提交构成，样本不足，不据此下结论 |
| 抽象/内聚（扩展） | 主序列 D=\|A+I−1\| 的抽象度 A、公开面密度、LCOM | go/types 解析 | 未实现 |

读法约定：

- 边缘单元（cmd / cli / home）Instability 接近 1 是正确形态；领域核心（knowledge /
  snapshot / kernel）低且被依赖也是正确形态。依赖方向必须从高不稳定指向低不稳定。
- 不设普适阈值：以 `scripts/coupling/baseline.json` 为基线，只紧不松；盯离群单元、
  传播成本与 Instability 的突变（工具报告 drift ≥ 0.05 的单元）。
- 已知局限：import 图按当前工具链平台解析构建约束（linux-only 的 FUSE 文件不计入），
  跨平台对比前需固定 GOOS；co-change 需按 commit 精确切分并做 follow-up 归一化后才有结论。
- 耦合报告是只读观测，不构成 `make quality` 的失败条件；升格为硬门禁须先立 TASK.md
  条目并显式确认基线。
