# Dataset：文件路径组合与版本交付

Dataset 按文件路径组合来源：从不同仓的确定版本选择文件或子目录，把它们映射到一棵新的
交付目录树。消费者按目标路径枚举和读取，取得对应来源文件的原始字节。

这里停在文件层。文件名、扩展名和目录名不决定知识含义，组合不解析对象、Aspect、Schema
或文件内部引用，也不要求先建立知识索引。文本、图片、代码和知识格式文件使用同一种
路径映射；知识解释是上层使用这些文件时的另一项能力。

Catalog 管来源登记与组合发布记录，源仓保存文件字节。Dataset 是独立、命名且版本化的
交付对象；其基本职责是选择来源路径、安排目标路径、固定版本和限定可交付范围。

## 一个 Dataset 的产品含义

维护者把已有来源中的文件选出来，以一个名称发布给消费者。发布版本不可改写，新的发布
推进当前服务版；消费者平时按名称采用当前版本，需要复核时按已接受的历史记录找回原范围。
使用者不必自己保存一份来源 commit 清单，仍能知道一次消费到底采用了哪些版本。

每个交付文件保留来源仓、来源版本和原路径；目标路径只是消费者看到的位置。
组合不拼接文件内容，不改写文件内的标识或相对引用，也不把目标路径当成知识身份。
内部仍存在 KnowledgeSet 等公开类型名，但类型名不意味着这一层需要知识解释。

## 选择来源，重新组织交付目录

Dataset 不仅选择“包含哪些内容”，还决定“这些内容交付到哪里”。维护者可以从多个仓选择
所需部分，按消费任务组织一棵新的目录树，不要求来源仓修改自己的目录布局。

例如，给一个项目交付文件：

| 来源中的目录 | 交付目录 |
|---|---|
| 仓 A 的 `handbook/policies/` | `reference/policies/` |
| 仓 B 的 `reports/metrics/` | `data/metrics/` |
| 仓 A 的 `docs/guides/` | `reference/guides/` |

消费者看到的是统一的 `reference/` 与 `data/` 目录，仍可追溯每份内容的原仓、版本和路径。
目录映射只改变交付位置，文件字节保持原样，也不根据目标目录名改变授权。
未选中的相邻文件不能随读取或枚举被补进来。

目录选择保持其内部相对布局，单文件选择则应能明确指定交付位置。多个来源可以共享一个
组织用的父目录，但同一个目标文件必须只有一个明确来源；冲突不得按挂载顺序覆盖。
单文件条目是组合目录中的文件，不要求把每个文件做成一个独立宿主挂载点。

目录结构也是发布内容。只调整交付路径，同样需要发布新版，不能让旧视图中的路径悄悄
改变；同一来源的多个片段继续使用一致的固定版本。文件级选择的发布与目录交付，需要
公开合同完整承接，不能仅凭类型中存在文件条目就宣称全链路可用。

## 登记、发布和源修改是三件事

供给新仓、连接已有仓属于应用管理面。Catalog 接入只承认该来源，并持久保存成员关系；
不能因为创建了存储就推导它已进入所有 Catalog，更不能推导用户已获权。

Dataset 发布时固定来源版本和文件范围。之后源仓继续提交，不会改变已发布 Dataset。
维护者再次发布，新的请求才采用新的服务版；已经打开的视图和挂载仍保留原依据。

文件发布不要求先解释知识或准备查询投影。应用若另行承诺知识搜索，可以在应用层安排
能力准备与发布采用；这些附加条件不成为 Dataset 文件组合的固有前置。

## 发布是可恢复的采用决定

发布先固定候选来源版本，检查文件范围、路径映射、冲突与发布权限，再接受不可变记录并
切换当前指针。消费者只能看到已接受记录，不能看到准备到一半的清单。
不解析文件正文，也不以能否解释其中的知识决定文件组合是否成立。

两位维护者并发发布时，不能覆盖同名历史版本或让当前指针悄悄退回旧版。发布中途失败，
源仓的提交仍成立，已有 Dataset 服务版也继续成立；再次尝试需依据实际已接受记录恢复，
不能靠客户端自报的成功摘要补造历史。恢复未完成的准备工作也不能把临时结果当成已发布。

跨仓固定的是明确的版本向量，不是各来源同时发生的一个全局事务。需要多个来源同时满足
业务约束时，发布者先取得合适版本，再作为同一份 Dataset 范围接受；平台不伪造跨仓提交。

## 不复制、不覆盖、不隐式发权

Dataset 保存来源引用，文件字节仍在来源仓。同一个目标文件路径不能按来源顺序覆盖；
不同仓中的同名文件可以放在不同目标位置，也可以显式改名后交付。
一个消费范围不是新的可写仓，修改来源文件仍需选定唯一目标仓。
有效发布仍引用的来源版本需要保留，不能在清理源数据时让已承诺的文件范围失去依据。

消费授权针对 Dataset 的已发布文件范围，维护授权针对 Repository。拥有 Dataset 读权
不获得整仓读取、写入或清单外路径；拥有仓权也不自动获得另一个 Dataset 的消费权。
发布方必须有权选入来源内容，Dataset 发布本身不扩大其分享权限。

这个区分源于资源不同，不是第二套对象 ACL。身份、政策求值与撤权由权限体系解释，
Catalog 不通过组合自动发权。

## 固定范围与生命周期

一次请求只解析一次 Dataset 版本，之后文件读取、目录枚举和分页都使用同一范围与来源版本。
客户端提供的 pin 或摘要只是坐标，不是授权凭证；当前撤权仍生效。

空文件清单不是整仓别名。目标路径解析与来源路径访问都受发布范围约束；路径规范化之后
仍须处于选定子树内，不能用父目录跳转、原仓路径或客户端自报的来源扩大范围。

来源版本的保留决定已发布文件能否继续读取；旧版本不可用时明确报告，不能自动改读最新
版本。退役 Dataset、移除 Catalog 成员和删除源文件是不同操作，不能互相代替。

Catalog 自身的登记历史保存在独立 Snapshot。进程重启恢复已有状态，不重新扫描本机目录
推导成员，也不把缺失状态当成首次创建。

## 文件交付与上层使用

挂载是固定只读视图的交付方式。打开的挂载不自动漂到下一个 Dataset 版本，写入仍要
选定唯一目标仓；不从消费路径反向推断写入目标。更新采用是显式决定，原项目文件不能
被挂载或版本切换覆盖。隐藏界面入口也不能暗中修改挂载或授权。

上层知识服务可以解释交付范围内的文件，但必须继承来源坐标、版本和文件范围。文件组合
成功不保证其中的知识可解释、可搜索，也不触发外部资源取值。这些能力的准备、失败和
保留由上层负责，不改变 Dataset 作为文件视图的含义。

## 为什么这样取舍

选定按路径引用原始字节，Dataset 可以在没有知识层的环境独立使用，代价是不会自动修复
文件内的相对链接或补齐依赖。交付方需要自行选择合适布局，内容变更仍由来源发布承担。

选定不可变发布，代价是管理来源版本保留，收益是相同版本可复核；选定冲突即拒绝，避免
用来源顺序偷偷决定哪份文件获胜。否决依赖知识 Schema 才能组合文件、已发布版本跟随
分支、Dataset 作为写入目标，以及客户端 pin 充当访问凭证。

## 方向性用例

### U1：把两个来源组合给消费者

发布者选择两个仓的文件，消费者只得到选中范围。同名文件映射到不同目标位置并保留
各自来源；没有选入的相邻文件不能通过补读出现。

### U2：源更新之后发布新 Dataset

源仓已经更新，但消费者仍读取旧服务版。新布局冲突、来源版本不可用或发布未被接受时，
继续保留旧版；成功接受新发布后，新请求采用新版本，已有视图不漂移。

### U3：撤权以后继续使用旧 pin

消费者保留了旧文件清单和版本坐标。撤权后的新读取必须拒绝，不能因版本不可变而绕过
当前授权；已经交付到客户端的字节不能承诺被远程收回。
可执行用例已补在 [交付测试](../../cli/dataset_file_delivery_test.go)：授权→发布→pin 内
枚举/读取通过→经管理面撤权→同一 pin 的 mounts、目录枚举、挂载相对与交付寻址读取全部
拒绝，且其它主体授权不受影响；见验证目录 B-24。

### U4：退役与来源保留

维护者停用 Dataset 或移除某来源登记，系统按当前生命周期拒绝后续不再允许的消费，
但不因此偷偷删除源仓内容或改写它的历史。

### U5：两个发布者并发采用更新

其中一次发布被接受后，另一方不能覆盖同名版本、回退当前版本或让消费者看见半份清单。
准备工作可以重试，已经接受的发布事实必须保留。

### U6：只发布目录中的部分文件

目录里有公开说明和未选中的内部文件。消费者只能枚举和读取选中内容，即使某个已交付
文件引用内部文件，也不自动补齐；路径中部的父目录跳转同样不能越过范围。

### U7：没有知识层也能交付文件

来源只有普通文本、图片或代码，没有知识声明，也没有查询投影。发布和文件读取仍然成立，
交付字节保持原样；即使文件里包含 URL 或声明文本，读取也不触发解析、外部请求或内容改写。

### U8：把 Dataset 接入已有项目

消费者获得明确版本的只读视图，原项目文件保持原状。新发布到来后，既有挂载继续原版；
采用更新、隐藏 UI 与撤销权限分别体现为不同操作结果。

### U9：从多个仓挑选子目录，交付统一目录树

维护者按上述映射发布 Dataset，消费者在新目录位置枚举并读取所选内容。一个仓的两个
不同片段可以出现在不同位置，来源身份与版本仍可追溯。上游其它目录不可见，源布局不变。
调整交付路径后发布新版，已经打开的旧视图继续按旧路径工作。

对应可执行用例已补在 [目录交付测试](../../cli/dataset_directory_delivery_test.go)：经 Server
发布两仓三个子树，枚举并读取新路径；再分别检查新旧布局与字节隔离、目标冲突发布失败后
仍可读取已接受版本。路径中部的上跳拒绝用例已随路径校验收紧（清理后的结果必须仍落在所选
子树内）执行通过；执行记录与覆盖范围见验证目录 C-17–C-21，执行结果按 run 保存。

### U10：挑选零散文件放到同一个交付目录

维护者从不同仓选择几个文件，分别指定目标文件名。消费者只看到选中的文件，不附带来源
文件夹里的其它内容；目标冲突明确拒绝。这个方向要求发布、目录枚举、文件读取与授权
一起成立，不能用底层存在一个文件条目类型代替完整实现证据。
端到端用例已补：重命名、跨仓混排、独立于任何挂载的目标目录、目标冲突拒绝、交付寻址
读取与授权范围一致，以及 `kc dataset clone` 把交付目录树物化为普通本地目录的公开 argv
旅程；见验证目录 C-20。不能用 U9 的目录前缀映射代替逐文件选择、改名与混排的证据。

`TestDatasetUILoadsBuildHintWithoutExposingAuthority`；壳是 vendored lakeFS webui，
账本仍在 Catalog，不新增服务端路由。
路径布局、清单字段、公开动作和版本转换以这些协议及其测试为准，本文不再重画状态机。
目录映射的公开定义见 [来源与目标路径](../../catalog/definition.go) 和
[路径路由](../../catalog/mount.go)，文件条目见 [Dataset 协议](../../catalog/dataset.go)。

逐文件交付的公开合同由 [Dataset 协议](../../catalog/dataset.go)（文件条目、目标唯一与祖先
互斥校验）、[来源与目标路径](../../catalog/definition.go) 与

证据；后续改动不得用子目录映射替代逐文件语义，也不得削弱目标唯一与祖先互斥约束。
