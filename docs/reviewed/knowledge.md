# 知识读写

## Goal

Knowledge 在固定版本上解释知识，并控制知识怎样改变：身份、校验和来源解释跨存储介质、
入口与组合方式保持一致，Schema 作为知识约束单仓发布。它不拥有仓登记、检索引擎或外部
运行时；这些能力可以独立变化，而知识身份、校验和来源解释应保持一致。

## Non-Goals

- 不拥有仓登记、检索引擎或外部运行时；采集写面与检索随后独立维护。
- 不强迫消费方按碎片阅读：维护粒度在写入侧，Reader 按请求组装完整对象。
- 业务 Schema 不写成 Go 源码中的名单；具体类型、匹配规则和兼容性算法归公开协议，本文不复制。
- 不承担跨仓事务、外部数据采集，也不在发布中运行模型。

## 身份与维护单元

Entity 是知识对象；Aspect 把同一对象的不同切面分别维护，Member 进一步支持集合中的独立
单元。写入粒度不强迫消费方也按碎片阅读，Reader 可以按请求组装完整对象。

Relation 是有自己身份的对象，通过引用连接端点，不是某个 Entity 的附属字段。端点可以在
其它仓，但关系写入只修改关系所在仓，不因此访问、校验或授权端点仓。规模压力下，包含型
关系可以采用有界的分组对象（如每表两条 Relation、端点数设上限、超限按稳定 bucket 分片并
把 bucket 编进关系身份）；跨过阈值是显式的模型迁移，不是存储层的身份折叠。拥有独立审核
或来源生命周期的关系仍是一边一对象。

身份由仓与对象确定，文件路径只是位置。身份放在内容而不是独立的地址映射里，是因为身份
与内容随同一次 Snapshot 原子演化；路径索引可以随时扫描重建，不会成为需要单独条件提交的
第四份权威状态。移动文件、换存储适配器、改变对象拼装方式，都不能
悄悄改写已有引用。结构、来源性质、集合组织与访问方式分别解释；被保存的断言或推导结果
不会仅因进入 Canonical 就变成未经限定的客观事实。

跨仓引用的治理语义保持克制：引用升级不修改引用方所在的仓，也不触发跨仓合并；Fork 创建
新的知识身份，只有 Fork 同步做三方比较；Vendor 引用保留精确来源 pin，本地编辑必须先转成
Fork。普通仓内容错误用新提交或显式回退提交修正并保留历史——回退是新的可审计发布，
不是抹掉过去；只有派生投影错误才用重建解决，两类动作不能混成一套“统一回滚”。

读取历史回答“当时保存了什么”；来源回答“这份内容依据什么产生”。两者不能互相代替。
Git 作者不属于外部来源，sourceRefs 也不是 Reader 自动爬取的证据图；声明由模型或脚本
推导内容时，DERIVATION 必须固定输入版本与算法信息，否则生成内容无法复现其依据。
跨仓组合也必须保留来源，不能把多个对象揉成无法归责的一份值。

仓的自描述同样作为知识发布、读取与发现；Catalog 库存只说明哪些来源已登记，
不再保存另一份容易漂移的内容说明。每仓至多一份约定路径的 README：缺失时平台与模型
都不得代写，也不得因此把仓从库存抹掉——可发现不依赖 README 存在。README 对象不进入
owner、领域分类、质量门槛、Schema 列表或请求时拼装的投影热缓存；claims 是库存证据，
不是仓内对象。没有按知识协议声明的普通文件也不会自动成为知识对象。

## Schema 是知识，约束发布

系统发布协议所需的基础 Schema；接入方通过 Writer 发布领域 Schema。Schema 与实例使用
同一版本语境解释，批内声明与批内实例可以一起校验。业务 Schema 不写成 Go 源码中的名单。

声明决定知识的逻辑结构和允许的访问方式，不决定某个引擎的存储参数。兼容修改应继续解释
已有实例，不能只验证新写入的那一个对象；检查经 schema 反向依赖索引定位受影响实例，
用有界的原生读取完成，不在消费请求中遍历文件树；反向索引缺失时失败关闭，不退化为
全仓扫描。删除被引用的声明必须被拒绝。破坏性变化需要
显式演进与迁移，不能让旧身份在无说明的情况下突然改变含义。

具体类型、匹配规则和兼容性算法归公开协议。是否允许同一 Schema 身份下携完整证据执行
破坏性迁移，仍是待选设计问题；不以重写本文代替该决定。

## 系统 Schema 与启动信任根

系统 Schema 由平台发布，不是普通接入方知识。系统仓对已认证主体默认可发现、可读——
这是「已认证主体默认可读」声明的第一个使用者，由授权声明解释，而不是保留标识带来的
特权；它默认进入发现名单，但不是业务组合的隐式成员。运行时 Writer 不能写系统仓：
只有平台版本发布能更新它，这是不可变的发布面，不是授权特例；发布固定的版本与摘要不
跟随业务仓内容变化。

Server 二进制内置 Meta Schema 的标识、版本与规范摘要：启动时校验系统仓内对象与内置
摘要一致，Writer 使用内置同版本校验器。理由是信任根不能自我解释——用仓内的 Meta Schema
校验它自己会形成循环启动，也让可篡改的仓内容变成信任根。目标仓发布自身 Schema 时，
必须携带与系统出版物一致的 Schema 副本，不得在相同对象标识上私自演进。

## Writer 与治理各做什么

Writer 接受一次明确的单仓变更，承担 Schema、来源、并发前置条件和幂等语义。它不采集外部
数据，不在发布中运行模型，不自动推断全仓删除，也不承担跨仓事务。已提交的知识在这里
结束写入，检索与缓存随后独立维护。采集写面的节奏决定提交频率：每个源事务或逻辑表变化
立即形成提交，不设固定 batching 间隔，也不用周期扫描换吞吐；只有队列已经积压时才允许
零等待合并，且合并必须保留全部事件标识与源版本证据，不能以固定时间窗口通过吞吐门槛。

Repository 的领域生命周期终点是归档：归档保留历史与身份，产品面不暴露领域级 DELETE；
物理删除属于保留或合规流程，必须显式审计，不伪装成普通知识操作。

网络中断不等于提交失败。重试要恢复原命令的结果，不能换一个命令身份再写一次；并发基点
失效则重新读取、核对和形成变更，不能关闭冲突保护。

需要评审的修改先进入固定候选，由治理检查证据后再请求推进发布目标。Writer 继续负责
知识校验和并发保护；治理编排不成为第二个写面。应用动作的出站扩展也不能修改变更内容
或撤销已接受提交。精确预览、证据失效、Hook 时机与投递恢复在 Hook/Gate 设计中展开。

恢复历史知识时，先在固定历史版本读取值及其 Schema，与当前版本比较，再按当前 Schema 与
治理约束形成新的 Writer 变更：恢复是一次新的可审计发布，不倒退权威历史。恢复产生的
知识经新的 pin 采用；历史 pin 的读取仍受仓可用性、版本保留与当前授权约束。

接入方的采集与人工修改最终遵守同一发布校验。业务仓可以有自己的开发工具，
不能据此让未经校验的内容被解释成已经过 Writer 保证的知识。

## 读取只解释请求允许的范围

Reader 在固定版本上读取并组装，不负责搜索候选。Dataset 只发布部分文件时，缺少的
Aspect 就是该视图未包含的内容，不能自动从源仓补全。公开消费面没有对象实例列举：
全 Snapshot 遍历只属于显式维护入口（重建、迁移、导出、一致性检查），读取与搜索不得
以它为兜底；这些维护入口的工作量受变更与目标规模约束，点读与变化识别按两固定版本的
差异进行，不做双全量比较。
Schema 或其它解释依赖缺失时，由知识读取报告解释限制，不反过来认定文件组合无效。
Dataset 目标路径只是交付位置；Reader 仍按来源身份与版本解释文件，不从目标目录生成对象身份。

逻辑读取可能通过 Serving 取得动态值，同时保留声明与观察两种依据。固定文件读取则只看
版本化字节，不因为读到了状态声明就访问外部源。动态取值与保留由外部资源访问设计说明。

## 硬性约束 / Invariants

- 身份由仓与对象确定，放在内容而不是独立的地址映射里；移动文件、换存储适配器、改变对象
  拼装方式都不能悄悄改写已有引用。
- Relation 是有自己身份的对象；关系写入只修改关系所在仓，不因此访问、校验或授权端点仓。
- 兼容修改必须继续解释已有实例，不能只验证新写入的对象；反向依赖索引缺失时失败关闭，
  不退化为全仓扫描；删除被引用的声明必须被拒绝。
- 运行时 Writer 不能写系统仓；Server 二进制内置 Meta Schema 标识、版本与规范摘要，启动时
  校验系统仓一致——信任根不能自我解释。
- 每仓至多一份约定路径的 README：缺失时平台与模型都不得代写，也不得把仓从库存抹掉；
  README 对象不进入 owner、领域分类、质量门槛、Schema 列表或投影热缓存。
- 网络中断不等于提交失败：重试恢复原命令的结果，同一命令身份不能携另一份内容；并发基点
  失效时重新读取核对，不能关闭冲突保护。
- 归档保留历史与身份，产品面不暴露领域级 DELETE；回退与恢复都是新的可审计发布，不倒退
  权威历史。
- Reader 在固定版本上读取并组装；公开消费面没有对象实例列举，全量遍历只属于显式维护入口。
- Dataset 目标路径只是交付位置；Reader 仍按来源身份与版本解释文件，不从目标目录生成对象身份。

## 选定方案 / 被否决方案

- 选定身份放内容、路径索引随时扫描重建；否决让独立地址映射成为需要单独条件提交的第四份
  权威状态。
- 选定采集写面按每个源事务或逻辑表变化立即提交、队列积压时才零等待合并且保留全部事件
  标识与源版本证据；否决固定 batching 间隔，也否决用周期扫描换吞吐。
- 选定包含型关系在规模压力下采用有界分组对象（端点数上限、超限按稳定 bucket 分片并把
  bucket 编进关系身份，跨阈值是显式模型迁移）；否决存储层的身份折叠。
- 选定系统 Schema 信任根为「Server 内置摘要 + 平台发布面」；否决用仓内 Meta Schema 校验
  它自己的循环启动。
- 选定需要评审的修改先进入固定候选、治理检查证据后再推进；否决治理编排成为第二个写面，
  也否决应用出站扩展修改变更内容或撤销已接受提交。
- 选定仓自描述作为知识发布、读取与发现；否决 Catalog 保存另一份容易漂移的内容说明。

## 方向性用例

### U1：首次发布领域知识

接入方读取系统 Schema，发布自己的声明与实例，再按回执版本读回身份、内容和来源。
可以一次发布互相匹配的声明与实例；声明不合法时整批不生效，不留下半份知识。

### U2：修改一个切面

维护者只修改某对象的说明切面。其余切面保持原值，身份不变；消费者仍能选择完整对象或
这个切面阅读。文件改名不应被解释成删除旧对象并创建无关对象。

### U3：Schema 演进影响已有实例

接入方修改一个被多份实例引用的声明。系统应说明是否兼容，并对受影响实例保持一致校验。
不能只因声明自身格式正确就接受破坏已有知识的发布；未选定的迁移方式不能伪装可用。

### U4：审批之后源仓又被修改

维护者评审固定预览后，另一个人推进了目标仓。旧证据不能批准未经评审的新组合；
需重新建立有效的预览与证据，原已发布版本不因失败被改写。

### U5：提交成功但响应丢失

接入方用原命令重试，得到同一已接受结果；同一命令身份不能携另一份内容。
无法确认是否已提交时暴露待恢复事实，不重复发布或制造假失败。

### U6：建立跨仓关系

作者在有写权的仓发布关系，端点指向另一仓。发布不写端点仓、不扩大读权；
消费关系时保留存储来源，目标对象是否存在或可读由当前消费范围判断。

### U7：从只包含部分文件的 Dataset 读取知识

文件交付已经成立，调用方随后请求知识解释。Reader 只能组装范围内的切面，缺少 Schema
或其它依赖时明确报告；不能为了得到完整对象而补读清单外文件，也不能因交付路径改变
而重新赋予知识身份。

解释与写入见 [Reader](../../knowledge/reader/README.md)、
[Writer](../../knowledge/writer/README.md) 和 [Conformance](../../knowledge/writer/conformance_test.go)。
治理入口见 [ControlPlane](../../controlplane/README.md)、[Gate](../../gate/README.md)、
[Hook](../../hook/README.md)。字段、错误码和状态转换只在这些合同中维护。

Schema 原位破坏性迁移、外部发布如何复用 Writer 校验仍按现有待办决策；本次文档合并没有
增加或取消这两项能力。持续运行不押注单个 commit graph 无限增长：活动仓分代有界、旧代
只读归档，旧坐标仍可显式挂载读取。但跨代切换成为操作合同之前必须先解决身份延续——
知识引用包含仓，新仓中相同的对象标识、值与摘要不等于原知识身份；既有引用、关系端点、
Schema 引用、来源坐标与按仓授权如何延续或显式迁移仍然未决，不能把候选迁移顺序当成
方案。
