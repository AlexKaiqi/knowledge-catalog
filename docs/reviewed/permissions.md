# 权限体系

## Goal

分别回答：谁在请求、能对哪种资源做什么、能收到哪些内容，以及能否使用外部资源。
认证、授权和交付各有责任；不能用登录成功、知道版本坐标或后台读到了数据代替其它判断。

## Non-Goals

- 不引入对象级 ACL、自动继承或隐式委托；边界落在仓与已发布 Dataset 范围。
- 组和角色属于外部身份系统，知识协议不另造一组角色对象。
- 发现与读取只对已认证主体开放，不提供匿名访客通道；平台不托管申请或审批队列。
- 不把登录成功、版本坐标或后台可见当成其它判断的替代；访问证据与运行日志不代替强制检查。
- 进一步按仓可见性裁剪发现范围、历史与来源动作的统一，仍是待 review 的政策，不在文档
  整理中悄悄选定。

## 身份先于权限，身份绑定需要耐久

认证器验证实际调用主体，授权基于该主体执行。用户、代表用户工作的 Agent 和服务账号
可以使用不同证明，但 Agent 不能把被代理用户冒充成自己；代理关系用于可信来源与证据，
不能自行变成权限合并或继承。

公开用户名应绑定可信身份系统中稳定、不可重新指派的身份。同名的新用户不能接管旧授权；
改名、迁移或关联另一身份来源需要显式处理。登录只恢复经过验证的身份，不补回被撤销的权。

所有产品请求经 Server 认证，包括本机 CLI。客户端自报名字、Git 作者或保存的本地目录
不是产品身份；受控夹具的身份模式也不能在生产配置缺失时成为默认回退。
凭证按 Server 隔离，资源方的部署密钥不充当调用方身份。

认证无会话：Server 不创建会话资源，每个业务请求自带凭证，pin 不绑定身份。未配置可用
认证器时，裸 Bearer 也不能被接受为开发身份——它不是「local 夹具回退」之外的又一条后门。
principal 与代理关系的含义由本系统拥有：认证 adapter 只把外部 claim 映射进这套语义，
替换 Taihu、Gitea 或 local 认证器不改变授权求值。

## 三种平台资源，三类外部边界

| 平台资源 | 授权回答什么 | 不隐含什么 |
|---|---|---|
| Catalog | 能否发现库存、管理登记和组合 | 库存可见不表示成员正文可读 |
| Repository | 能否维护或消费仓中的知识与历史 | 外部 Store 管理员身份不自动映射成 KC 权限 |
| Dataset | 能否消费这个发布范围、管理它的发布 | 消费权不开放整仓、清单外文件或知识写入 |

Store 门禁保护底层介质；KC 授权保护产品动作；外部业务系统保护真正的数据访问与执行。
三者可由部署协调，但不能相互推导。能读“某张表允许谁查询”的知识，不等于能 SELECT
那张表；观察到的外部授权快照也不能反向成为 KC 的访问策略。
授权语义不依赖具体 Store 的概念，Store 替换后语义保持。部署可以把 Store 自身的 ACL
与 KC 授权同向使用（仓默认私有、Server 以服务账号拉取对象），但那仍是介质门禁；
Agent 一旦持有成员仓 clone，对象级只读失去意义；CODEOWNERS 属于评审路由，不是读隔离。

创建来源、登记来源、发布 Dataset 和发权是不同事实。部署可以对创建者配置明确的窄授权，
但它仍需可审计、可撤销，重放创建和重启不能恢复已撤销规则。发布者只能在当前获准选取、
分享的范围内发布，不能通过组合把自己没有的能力授予他人。

## 仓是维护边界，Dataset 是受限交付范围

Repository 的版本图、历史、来源与维护形成一致的安全边界。真正不同的读者集合、历史
可见性、写权威或发布节奏，通常需要分仓；仅因文件类型或消费者不同，不必拆仓。
写入可以受更细的目标约束，但不因此引入 Aspect 级正文读 ACL。

按仓而不是按对象划界的理由：Repository 是完整 Snapshot 图，对象或文件级 ACL 会迫使
每次历史读取、索引、备份和迁移都做正确裁剪，而 clone 一旦发生无法隐藏部分历史。边界
落到仓之后，授权退化为 principal×action×repository，知识集按成员仓逐仓求值，复杂度
随治理边界数而不是对象数增长。业界同构也支持这一层选择：目录型产品的安全边界同样落在
集合级（Purview 的 collection、Unity Catalog 的隔离单元），Dataplex 以 attach 引用而不
复制数据；Unity 把隔离单元与表特权分开，对应外部 GRANT 不进入平台 allow；Atlas/Ranger
把元数据与业务强制分成两个系统，对应权限知识与实时强制分开；DataHub 的细粒度过滤伴随
查询时授权与继承成本；Solid 式资源级 ACL 的复杂度不适合作为默认模型；dbt Mesh 的经验
是经常需要协同修改说明边界划得过细。拆仓另有三条经验判据：两仓经常必须在同一次变更中
一起修改，说明治理边界可能划错，考虑合并；两仓只是对同一主题各自断言，保持独立、读侧
并存；同一对象存在真正的敏感信息差，在受限仓写另一条知识并引用公共对象，而不是引入
Aspect 级读 ACL。

Dataset 发布一份确定的文件选择。消费方取得该 Dataset 的读权后，可以读取已发布范围，
不要求把所有来源仓的读权一并交出去。这个受限视图不是底层仓 ACL 的另一套副本：
源仓仍保有整仓维护边界，交付端严格按发布清单提供文件。

同一对象有部分 Aspect 未被选入时，Reader 不能从源仓补齐。空清单不等于整仓；关系端点
指向另一个对象也不扩大范围。服务端从可信发布记录解析范围，客户端自带清单或摘要不能
授权自己，临时配方也不能借用命名 Dataset 的授权。

## 发现与正文交付需要明确区分

现行选择是：公开 Catalog 的登记身份可以对已认证主体发现；私有 Catalog 仍检查其发现权。
发现库存不发出搜索或正文权限，也不自动把仓内 README 展成库存内容。

部署可以按仓声明「已认证主体默认可读」。声明覆盖的是 consume 侧动作闭集：正文与
Schema 读取、搜索、历史与来源、文件读取、投影读取；未声明的仓 fail closed，仍需 grant。
这份声明不是仓的类型，不是搜索过滤键，也不放行任何写或发权，与公开 Catalog 的发现
同一模式。没有部署的本地 Home 没有这类公开默认，本地初始化把同一声明写入耐久文件。
System Repository 是该声明的第一个使用者；授权器不得因为对象标识带保留前缀就短路求值。

遍历与语义召回沿用同一授权粒度。TRAVERSE 在请求开始固定范围；边只来自其存储仓已在
授权范围内的对象，frontier 继续扩展要求该对象所在仓属于本次范围，越界止步并显式标记；
Dataset 遍历不因跨仓引用扩大清单，按仓遍历按读权 fail closed。语义召回只在已准入范围
内形成召回窗口，召回策略不改变授权粒度，近似结果仍走同一交付链。

单仓知识搜索有独立准入。在允许发现而没有正文读权时，交付链可以按现行政策保留固定身份
与版本、屏蔽正文；它不改变候选身份或原查询依据。命名 Dataset 的搜索则先受发布文件范围
限制，不能先查出清单外对象，再只遮正文。

后置遮罩不能消除关键词、匹配数量或排序造成的信息泄露。敏感内容不能仅靠“最后不返回
正文”保护；外部动态源的授权尤其要在使用受保护值过滤和计算之前成立。
进一步按仓可见性裁剪发现范围、历史与来源动作如何统一，仍是待 review 的政策，不能在
文档整理中悄悄选定。原有 `AUTH-01`–`AUTH-03` 的准入、身份与交付边界继续保留。

## 版本固定不冻结权限

pin、Dataset 历史版本、缓存和分页坐标说明读什么，不说明谁一直有权读。
每次新的服务请求按当前授权判断；撤权后不能凭旧坐标续读。
这不意味着可以改变原查询的数据依据：重新授权与重新取最新数据是两件事。

复用缓存或投影只复用内容，不复用上一次调用者的授权结果；不能为每个主体复制索引来
代替政策求值。已经交付到客户端的字节无法靠服务端撤权远程收回，设计承诺止于后续交付。
这条边界还要前移到落盘之前：为 Agent 生成检出工作树时，授权裁剪必须在写盘前完成——
无权成员不能先落盘、再指望后续命令阻止它直接读文件；不同身份得到不同 checkout。

## 动态观察还有生产与消费两次授权

后台有权取值，不表示所有消费者都能看这份观察。接入关系需要明确：

- 来源要求逐调用方授权时，读取、动态搜索、分页和保留观察的重读都继续受当前源授权约束。
  共享缓存可以免去重复取值，不能免去授权；无法建立授权时明确拒绝。
- 接入方有权且明确发布共享观察时，平台才可在获准范围与期限内按消费授权交付。
  后台服务账号可见、Dataset 发布成功都不是这份共享许可。

未明确共享关系不能默认共享。源拒绝后也不能回退旧缓存、仓中的空占位或上一次用户的
观察。动态过滤与计数会泄露值，因此仅在交付末尾清空正文不足以满足源授权。

知识里的访问地址也不授予索取凭证的权利。发送调用方证明前，必须确认目标受信任、证明
适用于该目标且委托目的相符；地址改变或重定向不能绕过检查。后台对账使用按来源隔离的
服务身份，不能借最近一次请求或通知的用户身份。凭证不进入知识、观察、投影或诊断正文。

## 权限恢复必须保留已经作出的决定

首次部署建立初始管理身份属于显式初始化。启动恢复已有身份绑定、授权、撤销与治理配置；
权限账丢失不能被解释为一个可重新发管理员权限的空部署。
权限管理通过同一受控入口执行，知识仓中的一份规则说明不能自行成为生效授权。

拒绝原因要分得清身份不可信、动作无权、范围不允许与源侧拒绝，证据足够追查而不泄漏
秘密。访问证据与运行日志不能代替强制检查，也不能因为记录了拒绝就实际放行请求。

## 选定方案 / 被否决方案

选定按仓划维护边界、按已发布 Dataset 范围划交付边界：授权退化为
principal×action×repository，知识集按成员仓逐仓求值，复杂度随治理边界数而不是对象数增长；
业界同构（Purview 的 collection、Unity Catalog 的隔离单元、Atlas/Ranger 的元数据与强制
分离）支持这一层选择，Solid 式资源级 ACL 的复杂度不适合作为默认模型。拆仓另有三条经验
判据（同一次变更必须一起修改考虑合并；各自断言保持独立；真正敏感信息差另写受限知识）。

选定公开 Catalog 的登记身份对已认证主体发现、部署可按仓声明「已认证主体默认可读」且覆盖
consume 侧动作闭集、未声明仓 fail closed；System Repository 是该声明第一个使用者，授权器
不得因保留前缀短路求值。选定认证无会话与按 Server 隔离凭证；否决裸 Bearer 开发后门，也
否决把受控夹具身份模式当成生产默认。选定单仓搜索在只有发现权时保留固定身份与版本、
屏蔽正文；后置遮罩不能消除关键词、匹配数量或排序造成的信息泄露，敏感内容不能仅靠
「最后不返回正文」保护。

## 方向性用例

### U1：只分享 Dataset 的部分文件

消费者可以查询和读取选中内容，不能读取源仓其它文件，也不能写仓。未选入 Aspect、
关系端点和空清单都不成为扩大范围的旁路。

### U2：撤权后拿旧 pin 或 continuation 重试

后续请求拒绝交付，缓存命中也一样。若仍有权，数据继续按原依据解释，不自动换成最新值。

### U3：同名用户重新出现

不同可信身份不能因用户名相同获得原授权。正常重登恢复身份，不能恢复已撤销 grant。

### U4：后台看得见，但消费者被源拒绝

动态查询不能利用受保护观察筛选、计数后再仅遮正文；精确读取也不能回退共享缓存。
明确获准的共享发布则按其范围和期限执行，二者不能隐式混用。

### U5：发布者修改取值地址

消费者凭证不会自动发给新地址或重定向目标。无法证明目标信任与委托范围时拒绝访问，
后台仍使用自己的来源身份，不借发布者或通知发送者的身份。

### U6：实例重建与状态缺失

正常恢复保留全部授权和撤销。丢失身份或授权权威时报告恢复失败，不自动初始化管理员，
也不因为重放资源创建而重新发权。

既有文件范围检查不能充当它们已经实现的证明。历史/来源的授权一致性、发现政策与字段级
遮蔽/脱敏仍保留原待决项；不能把当前交付链扩写成已经选定的字段隐私语言。
本篇不新增对象 ACL、自动继承或隐式委托。组和角色属于外部身份系统，知识协议不再造
一组角色对象；发现与读取只对已认证主体开放，不提供匿名访客通道。平台只提供查权入口与
可选的外部申请地址，不托管申请或审批队列——发权只能由授权管理者通过受控入口执行。
