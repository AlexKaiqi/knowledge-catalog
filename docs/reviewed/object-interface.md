# 对象 Interface

## Goal

让具有共同处理逻辑的对象按同一能力合同提供实现信息，消费者通过系统统一使用能力。
Interface 的知识合同与处理实现能够独立扩展；业务对象身份、知识维护、版本与授权不随
处理器变化。首先将已有 ResourceDescriptor 的当前访问能力整理为 LiveAccess，
再用另一种对象能力检验扩展接缝，不把资源访问的专用分支当成通用机制。

## Non-Goals

- 不建立通用资源描述符或封闭的对象类型名单；材料组成由对象定义及领域 Schema 表达。
- 不强制所有对象具有 definition 或实现某种 Interface；基本知识读写继续独立成立。
- 不把任意 Aspect 的读取改为执行处理器；固定文件读取只返回固定字节。
- 不扩张 Hook：应用动作的出站扩展与对象能力处理各有入口和合同。
- 不承诺事件窗口、持续订阅、任意代码动态加载或平台未支持的媒体交付方式。

## 对象能力是完整扩展单元

Interface 根据处理逻辑共性定义能力语义、操作、对象实现要求和结果保证。
其定义作为独立知识合同发布；对应处理器完成公共处理逻辑。支持此实现形式的处理器
已经装配后，维护者通常提供声明、数据或入口即可兑现能力，不必为每个对象重复写处理代码。

Aspect 是维护粒度，Schema 是结构约束，Interface 是对象能力合同。对象可以实现多个
Interface，同一能力也可有多个明确命名的实现。Schema 合规并不证明操作语义正确；
处理器还需检查它支持的实现形式与该能力的约束。系统不通过扩展名、目录或业务类型猜测
对象实现了什么，也不因只有说明文档就认定处理器存在。

可供性关联具体对象的明确实现与操作，补充任务选择所需的用途、条件、效果和限制；其
关系由对象系统设计拥有。它不成为第二套分派系统，不授予权限，也不替代合同一致性。
声明可读、结构合法、依赖可解释、处理器支持、当前可用与本次获权分别成立。发布与发现
可以先解释这些声明，不以领域处理器已交付为前提，也不得将声明展示成使用成功。

推荐将实现声明组织为普通集合型 Aspect，各实现作为稳定 Member。目录只是位置。
对象定义直接描述含义、边界、组成及所需引用：内部材料复用对象与固定文件引用，外部
标识由领域及实现合同解释。图像可以关联原图，模块可以引用不同仓中的代码和合同，
数据集可以关联外部表与内部参考材料；没有统一的资源包装要求。

## 解析、装配与分派

公共机制固定本次对象、实现声明、Interface 与 Schema 的知识依据，按已装配的合同
和实现形式选择处理器，检查输入与调用边界，再交给对应扩展执行。选择有歧义时需要
明确实现，不能按文件顺序挑选。缺合同、缺范围内依赖、缺处理器和运行不可用分别报告，
不能扫描全仓或暗换版本来补齐。

普通 Schema 引用继续在实例所在仓的同一版本语境中解释。跨仓 Interface 引用保留明确
来源与固定采用依据；范围不允许解释该依赖时失败，不沿引用扩大读取。登记与调用携带
可信身份和上下文，写效果操作还需显式授权。声明可读不能授予实际执行权限。

独立扩展交付知识合同、实现 Schema、处理器、装配信息与一致性证据。新增能力通过公共
接缝接入，不向核心分派加入领域类型判断。合同版本与实现结构共同决定适配，不凭名字
相同猜测兼容。字段查询声明变化不改变处理器对实现结构的支持；完整知识版本和声明依据
仍保留，供查询解释与本次调用复核。实现运行语言、装配包格式和进程边界由部署选择，不成为知识协议的限制。

system repo 随平台版本出版且运行时只读。内置 LiveAccess 合同属于平台出版物；独立
扩展的合同发布到普通知识仓，业务实现声明发布到对象所在仓。独立扩展不要求重发或
运行时追加 system repo。发布知识、装配处理器和服务就绪分别留下结果。

## 结果依据与维护

固定文件结果保留文件版本，当前状态结果保留观察依据；不同能力按合同解释结果，
不把所有输出强行包装成状态观察。固定声明不冻结外部值，也不保证旧处理器或 runtime
永久可用。需要把结果长期维护为知识时，显式形成 Writer 变更。

衍生说明仍是普通 Aspect 或 Member，来源声明固定输入知识与算法，还需记录实际文件或
观察依据。维护判断按真实依赖展开：改变名称未必需要重算，更换原图或实际观察则需
复核；不能以对象每次版本变化触发全部衍生知识，也不能让更新输出自身再次触发同一推导。
人工修订、自动生成和索引重建保留各自维护责任。

声明式索引也采用版本化声明、解释验证、能力实现和独立就绪的组织方式，但仍保留
专门的逻辑编译、后台维护和查询执行合同。它不需要强行登记成对象 Interface。

## 硬性约束 / Invariants

- OI-01：对象身份与知识维护方式独立于处理器；文件位置和类型不推导能力。
- OI-02：分派固定对象、实现和合同依据；依赖解析不扩大调用范围，歧义不得靠加载顺序解决。
- OI-03：知识声明不授予运行权限；固定声明不冻结运行值，结果保留能力所需的实际依据。
- OI-04：扩展经注册与一致性证据接入，不新增核心领域分支，也不追加只读 system repo。
- OI-05：衍生知识按实际输入依赖维护，结果发布经过 Writer，不将运行观察或投影冒充正文。

## 选定方案 / 被否决方案

- 选定 Interface 合同作为知识、实现声明作为普通知识单元、处理器由运行装配提供；
  否决领域能力写进核心类型名单或只增加声明而没有可执行处理实现。
- 选定有界发现与精确版本解析、显式实现选择；否决全仓扫描兜底、文件类型推断和静默改用新版。
- 选定 LiveAccess 为首个内置对象 Interface，并保留历史 ResourceDescriptor 与 State 的兼容解释；
  否决把重命名当成事件订阅已实现，或立即使历史 pin 失去解释。
- 选定组成直接进入领域定义，引用内部定位原语；否决预先统一所有外部资源的形态与访问方式。

## 方向性用例

### U1：发布独立能力扩展

发布者在自己的知识仓发布合同与实现 Schema，部署方装配符合合同的处理器。
业务对象发布实现声明，消费者使用系统入口调用；system repo 无需重发。

### U2：视频同时提供视觉与音频内容

同一对象提供两个实现，分别引用原视频或明确音轨；消费者按能力选择。
需要两种相同能力的实现时必须明确选择，系统不能按文件顺序决定。

### U3：访问当前状态并发布说明

消费者按固定 LiveAccess 声明取得当前观察，随后显式发布推导说明及输入依据。
声明未变但来源变化时，维护者能识别实际输入变化；访问失败不被解释为业务空值。
