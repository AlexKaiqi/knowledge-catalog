KNOWLEDGE CATALOG

面向大规模数据的
通用知识底座

Knowledge Catalog 面向大规模数据的知识组织与访问：在 lakeFS 等现有存储之上，提供数据集切分、组合与独立授权，以自定义 Schema 声明业务结构和查询需求，由系统维护索引与访问缓存，向应用和 Agent 提供统一的检索与读取入口。

01

能力与架构全景

系统分为四个逻辑层。⓪ 通过适配器接入已有版本化存储；① 在其上组织和发布 Dataset；② 解释知识声明；③ 编排索引维护与检索。底层存储引擎承担文件、版本和容量，Knowledge Catalog 负责其上的数据组织、知识语义与访问流程。

逻辑分层不限定服务的部署数量。Knowledge 可直接读取单仓 Snapshot，也可通过 Dataset 读取组合后的文件范围。动态状态由外部运行时提供；VFS 将固定版本的数据集呈现为本地只读文件。

02

分层职责与能力边界

⓪ SNAPSHOT STORE

底层存储集成

Snapshot Store 是统一的存储适配接口。文件、快照、分支与提交由 lakeFS、Gitea、Dolt 等底层引擎提供；Knowledge Catalog 将这些能力接入数据集发布和知识读写流程。

普通文件的版本管理可由 Git 承担。大文件、大量文件的存储采用 lakeFS 与对象存储方案，其规模能力来自底层组件；系统整体的容量、吞吐与恢复能力仍需部署实测。

① DATASET / CATALOG

数据集组合与交付

从一个仓选取部分文件，或把多个仓的内容组合成 Dataset。Catalog 登记可用来源与 Dataset；源内容与历史仍保留在各仓。

Dataset 有自己的消费授权与发布版本，同一份源数据可按用途交付给不同使用者。发布固定选定范围与来源版本，源仓后续修改不会改写已发布版本。

② KNOWLEDGE

知识模型与读写

自定义 Schema 声明数据类型、字段与关系。同一个业务对象可以有不同方面，例如服务的定义、负责人和运行说明。

系统据此校验、解释和读取知识，保留对象标识与来源。文件改名不改变业务对象的标识，引用与关联不依赖文件路径。

③ RETRIEVAL

声明式索引与检索

在 Schema 中声明哪些字段支持全文搜索、过滤与排序，系统完成索引构建、更新与重建，并用同版本缓存和预热加速访问。

消费者通过统一入口查找对象、获取对应正文；接入方无需逐次操作检索引擎。可用查询能力取决于声明和部署，索引与缓存不替代源数据。

文件底座与知识层的分界

⓪、① 处理文件、范围和版本，不解析业务对象或 Schema。② 依据知识声明解释和校验内容，不自动理解未声明的普通文件。③ 依赖已声明的查询能力及相应检索服务，索引与缓存不替代源数据。

统一访问与持续发布

消费者使用稳定的 Dataset 入口。当前默认采用最新已发布版；正文与所需索引就绪后统一切换到最新可服务版，是需要继续完善的发布目标。查看版本机制与目标 →

03

开始之前：确认身份与使用范围

部署方准备服务、存储和授权策略。日常使用通过已配置服务入口的客户端完成；你需要知道要使用哪个 Catalog、Repository 或 Dataset。

已配置服务入口 / 按部署要求完成登录
kc whoami
kc admission show
kc catalog list
kc catalog use kr://acme/catalog
kc show

检查结果当前身份正确；已选中要使用的 Catalog；能看到登记的仓与 Dataset。示例 ID 请替换为实际值。

登录、发现与读取是不同条件。登录不自动授予数据读权。admission show 显示当前授权和部署提供的申请入口；缺少权限时按该入口联系授权方。Catalog 库存不等于知识搜索结果。

第一次配置客户端时，在哪里填写服务地址？

服务入口可由交付的客户端预设。原生客户端首次登录可用 kc login --server 'https://kc.example.com'，认证方式以该服务要求为准；登录后复用保存的会话。开发环境的 local 认证不是生产身份方案。后续参数以 kc help login 为准。

04

消费：用同一个 Dataset 找到并读取知识

日常消费不要求手工管理版本文件。选择已发布且获准使用的 Dataset，先搜索定位，再读取内容。下面的示例要求 Dataset 已采用知识声明与检索能力。

1

找到要用的 Dataset

从当前目录库存或维护者的交付说明获得 Dataset 名称、内容范围和示例对象。文件型 Dataset 不会自动获得知识搜索能力。

查看当前 Catalog 的库存
kc show
2

搜索需要的对象

例如在 oncall 中查找值班说明。系统在本次操作中固定 Dataset 的已发布版本。

oncall 已发布、已授权且具备全文检索字段
kc search --dataset oncall --query '值班'

检查结果CLI 列出命中对象的身份、Repository 和 commit。搜索结果用于定位，正文通过读取打开。

3

读取内容，按需要保留依据

使用搜索返回的对象 ID。Dataset 下同一身份可能来自不同仓，读取结果保留各自来源。

将对象 ID 替换为实际搜索命中
kc read --dataset oncall --object runbooks/oncall

检查结果确认正文、所属仓与返回的 commit。需要引用时将它们随任务结果保存。

默认最新以每次操作为单位。两条独立命令之间可能发布新版；需要严格复核上次搜索对应的原文时，应保留命中版本，使用获准的固定版本读取接口。单仓 CLI 可按返回的 --repo --commit 重读，但仍需仓级读权；Dataset 消费权不自动授予它。了解权限边界 →

只使用一个源仓，或已经知道对象身份

具备仓级权限时，可直接使用 kc read --repo kr://acme/operations --object runbooks/oncall，无需先定义 Dataset。查看类型用 kc schema list --repo kr://acme/operations；查询字段用 kc schema describe --repo kr://acme/operations --object schema/runbook，其中 Schema ID 应来自实际库存。

05

接入：从源仓组织出可交付的 Dataset

接入方负责内容、结构与持续维护；Dataset 维护者决定交付范围和发布节奏。先完成文件与 Dataset 底座，再按需要增加知识能力。

创建或连接仓→登记进 Catalog→准备并发布内容→发布 Dataset→授权消费
1

创建或连接源仓，再登记

选择部署提供的存储池，或连接允许接入的自有仓。创建或连接成功后，再将返回的 Repository ID 登记到当前 Catalog。

托管仓 / 需具备创建与登记权限
kc create --name operations
# 用上一条返回的 Repository ID 替换示例
kc attach --repo kr://acme/operations

检查结果创建与登记是两个步骤。kc show 能看到已登记仓；登记本身不授予正文读权。

连接自有仓

使用 kc create --url 'https://git.example.com/team/operations' --credential-file /private/repo-token。服务只接受已批准的来源与支持的连接方式；实际自有仓支持范围以部署为准。成功后按返回 ID 执行 kc attach --repo。源凭证不应写进 Dataset 或知识正文。

2

按采用范围准备内容

只交付文件时，保持文件形态即可。采用知识层时，为对象确定稳定身份、Schema 与来源，再经 Writer 发布。Schema 与实例一起随源仓版本保存。

知识发布 / drafts 须事先准备为符合 Schema 的知识草稿
kc diff --repo kr://acme/operations --dir .data/oncall-drafts
kc writer commit --command-id oncall-content-001 \
  --repo kr://acme/operations --dir .data/oncall-drafts

检查结果先核对差异，再提交；保存发布回执，按返回 commit 回读代表性对象。需要搜索时还要检查该版本索引是否就绪。

3

选取范围，发布 Dataset

Dataset 可以交付一个仓的部分内容，也可以组合多个仓。发布会固定来源 commit 与文件范围，上游后续提交不会改写这一版。下面先演示两个整仓来源；它们必须已登记且可用于发布。

发布 oncall 的第一版 / sources 需有可用的已发布版本
kc dataset define oncall --revision 1 \
  --source kr://acme/operations \
  --source kr://acme/services

需要只交付文件或子目录时，按配方选择范围和目录布局。切分针对文件与路径，不等同于任意内容条件、行级过滤或字段脱敏。共享的知识对象还应包含解释它所需的 Schema。

4

独立授权，并用消费身份验收

有授权管理能力的维护者可给指定用户授予 Dataset 消费权。消费者不必因此获得源仓维护权。

由具备授权管理权限的主体执行
kc grant add --catalog kr://acme/catalog --dataset oncall \
  --principal teammate --action file.read

检查结果目标用户可读取 Dataset 清单内的内容；清单外内容和仓级维护动作不因这项授权而开放。发布成功不等于自动完成授权。

交付给使用者什么？

Dataset 名称、用途与内容范围、授权方式、代表性对象或文件，以及本次版本的变更说明。采用知识层时再提供类型与可查询字段；无需把存储凭证、索引配置或内部缓存细节交给消费者。

06

声明数据与查询需求，系统维护索引

接入方描述“这是什么数据、需要怎样查”；系统负责把已发布内容变成可检索的索引，并维护更新与缓存加速。消费者使用同一套访问方式。

接入方声明系统承担消费者获得
类型、字段、身份与来源解释和校验知识，保留版本依据按业务对象读取，理解字段与来源
哪些字段可全文搜索、过滤、排序构建与更新索引，按声明变化重建关键词查找、类型化条件、排序与分页
需要访问的来源与动态声明按相应依据回读，维护可用的缓存与派生结果统一结果与诊断，不必直接操作后端引擎

仅声明“这是字符串”还不足以表达查询需求。Schema 还要声明哪些字段支持 text、filter 或 sort。接入方不需要逐次手动建索引，部署方仍需提供检索引擎、运行资源与维护服务。

统一访问：一次学会，多处复用

Unified Access 统一的是已声明数据上的检索与读取方式，以及权限和版本依据。应用不需要为每个来源分别编写搜索和回读逻辑；内容仍来自各自的权威来源。

示例 / 字段必须已经声明 filter 能力
kc search --dataset oncall --query '支付'
kc search --dataset oncall --eq team=payments
kc read --dataset oncall --object Service:orders

字段同名且有歧义时，使用实际 Schema、Aspect 与字段组成的完整字段名；详情见 kc help search。普通文件的全文扫描、任意 SQL、向量检索和自然语言问答不能由这个入口的存在推导为已支持。

索引会持续维护

知识发布后，后台追踪新版本并更新索引；Schema 的访问声明变化可能需要重建。接入方维护数据模型，不负责逐次操作搜索引擎。

查询必须说明依据

检索和正文回读使用相应版本依据。遇到能力不足或索引未就绪时，应根据返回状态处理，不能把不可用当成“没有匹配数据”。

“声明式”不等于无限能力。缓存用于访问加速，不能代替正确版本的正文。具体查询方式取决于 Schema 和部署能力；容量、延迟与索引追赶时间需要测量。查看当前能力与规划 →

07

维护者发布版本，消费者持续使用同一入口

源仓版本回答“内容改了什么”；Dataset 版本回答“这次向消费者交付哪组内容”。两者的发布节奏可以不同。

Dataset v1

oncall 固定手册 A1 与服务定义 B1。消费者通过这个 Dataset 查询和读取。

源仓更新

手册发布 A2。已发布的 Dataset v1 仍保持 A1 + B1，消费者不会被源仓提交直接切到半套新内容。

Dataset v2

维护者验收后发布第二版，交付 A2 + B1。消费者仍使用 oncall，后续默认操作采用最新已发布 Dataset。

固定消费

已经打开的固定视图、挂载或显式历史坐标保持原版本。需要复核的任务保留版本依据，不假定多次独立操作之间不会发生发布。

维护者 / 上游内容更新并验收后发布第二版
kc dataset define oncall --revision 2 \
  --source kr://acme/operations \
  --source kr://acme/services

规划目标：正文和索引就绪后统一切换

对知识型 Dataset，目标是在新版本的正文与所需索引都准备好之后，统一切换消费者可见的服务版本；消费者默认使用最新可服务版，一次查询、分页与正文回读不混版。文件型 Dataset 不需要为了发布而安装知识检索服务。

区分已有基础与完整承诺。当前已有 Dataset 固定版本、默认最新解析、后台索引维护及同依据回读基础。正文写入成功与索引就绪仍是两个检查点；“就绪后统一切换、失败仍可稳定服务”的完整闭环需要进一步细化和验收，不能把已发布直接当成已可检索。

修改、删除与恢复怎样处理？

知识修改先读取当前内容并核对差异，再经 Writer 发布新 commit，之后按交付需要重新发布 Dataset。每次新修订使用新的命令 ID；重试同一操作保留原 ID，并先查询 kc writer receipt --command-id。并发冲突应重新核对，不取消检查强行覆盖。

删除对象、退役 Dataset、取消仓登记与撤销权限分别处理。删除当前内容不会自动抹除历史，撤权也不是版本更新。恢复旧内容应按当前规则作为一次新发布提交。需要评审的发布使用部署支持的提案与验证流程，参数从 kc help governance 查看。

08

解决方案：瞬时状态与本地 Agent

瞬时状态接入将版本化的知识定义与持续变化的外部值关联起来；只读 VFS 将已发布 Dataset 暴露为本地文件视图，供 Agent 和现有文件工具使用。

瞬时状态：读取外部当前观察

服务健康、作业进度、表统计等状态会频繁变化。例如，同一个服务对象的负责人和运行说明随知识版本发布，健康状态则在访问时从源侧服务取得。Schema 关联对象与动态访问来源，应用按同一个对象标识访问这些信息，不必把每次状态变化都提交成新的文件版本。

源已接通 / Schema 已声明对应 Aspect 的 origin
kc access --dataset oncall --object Service:orders --aspect health

接入方发布 Schema 的访问声明，并提供可调用的源侧运行服务；系统已有 State 精确读取与独立动态投影基础。启用对应动态检索后，可以将已声明的状态字段用于统一查询。状态观察版本与知识声明版本分别保留。

当前值不是历史快照。固定 Dataset 不会自动冻结外部实时值。“当前”受观察时间和更新机制影响，不能承诺零延迟；能否重读过去状态取决于来源能力。过去一小时的事件或日志属于历史窗口需求，不能用当前状态代替。完整动态部署与新鲜度保障仍需按环境验收。

VFS：让本地 Agent 像访问普通文件一样读取 Dataset

把 Dataset 挂载到本机后，本地 Agent、编辑器和文件工具可以浏览目录、打开文件、查找内容，复用已有文件访问方式，无需为读取这些文件专门适配知识接口。

适用范围与限制
  • Dataset 必须是本机放得下的。受本机存储与资源容量约束，不适合特别大的数据集。按需读取也不扩大这一产品适用范围。
  • 目前只读。不能通过挂载目录修改、删除或写回知识。需要修改时，另行准备草稿并走发布流程。
  • 挂载固定一版内容。Dataset 更新后已有挂载不会自动漂移，采用新版需显式更新或重新挂载。
  • 需要受支持的宿主环境。当前挂载入口基于 Linux FUSE，并经服务读取；挂载不等于把全部内容下载好，也不保证离线可用。
你的情况选择
本机放得下，Agent 主要用文件工具只读 VFS，使用目录与文件工作方式。
数据特别大，或超出本机容量服务端统一检索与按需读取；或者先切分出本机可容纳的 Dataset 再挂载。
需要最新外部状态动态访问接口；VFS 展示固定文件与声明，不自动变成实时状态视图。
需要修改和发布内容准备草稿并经 Writer 发布；挂载目录不是编辑入口。
准备好本地条件后怎样挂载？

先确认 Dataset 配方包含明确的非根目录布局，挂载点不存在或为空，本机能容纳数据，并已具备服务访问权限与 Linux FUSE 环境。先查看计划，再执行挂载；示例项目路径须替换。

受支持的 Linux 主机 / 配方已有非根目录布局
kcfs plan --dataset oncall --root /work/my-project
kcfs mount --dataset oncall --root /work/my-project

确认计划中的目录、固定版本与只读状态。项目自身未被挂载覆盖的普通文件仍按原方式使用；挂载生命周期参数见 kcfs help。

09

交付范围、维护权限与引用依据各自明确

Dataset 将“能使用这一份交付内容”与“能访问或维护整个源仓”分开。版本坐标说明读到了什么，当前权限决定现在是否仍能读取。

边界用户能得到什么不能由此推导什么
Catalog 发现查看获准发现的目录库存自动读取所有成员内容或搜索整个 Catalog
Dataset 消费授权读取已发布清单内文件，并在其上使用知识消费能力清单外内容、整仓读取与写入权限
Repository 授权在获授动作范围内读取或维护该源仓自动获得其他资源或 Dataset 的授权
历史版本依据在保留和权限条件满足时复核内容永久保留权限，或冻结所有外部实时状态

Dataset 定义与发布不隐式发权；授权变更后，后续访问重新检查。外部系统的受保护操作仍由外部系统强制，能够读到相关知识不等于能够执行源系统操作。

回答“我依据的是什么”

引用知识时保留对象身份、Repository 和 commit。来源说明内容从哪里来，历史说明内容怎样变化；涉及动态状态时再保留观察时间与来源版本。应用和 Agent 应明确区分读取失败、无权限、结果不完整与确实没有匹配。

按固定版本复核单仓知识

具备仓级读取与相应追溯权限时，把返回的 commit 用于后续读取。Dataset-only 消费者需要使用其获准的消费接口，不能通过此例绕过源仓权限。

将示例 commit 替换为要复核的实际版本
kc read --repo kr://acme/operations --object runbooks/oncall \
  --commit '替换为实际返回的commit'
kc provenance --repo kr://acme/operations --object runbooks/oncall \
  --commit '替换为实际返回的commit'

常见问题

我只需要组织和分享文件，必须使用 Schema 吗？

不需要。Snapshot Store 与 Dataset 可以独立使用。需要按业务对象读取、结构化查询或知识检索时，再采用知识声明。普通文件不会因被登记或挂载就自动具备知识语义。

Dataset 是把多个仓复制到一个新仓吗？

Dataset 记录选定文件范围与固定来源版本，保留各源的身份与历史。组合不制造跨仓写事务；内容修改仍回到相应源仓，之后再发布新的 Dataset 版本。

消费者需要学习 commit 和 pin 吗？

日常使用 Dataset 名称即可，系统固定本次操作的版本。需要复核、审计或保持长任务上下文时，才需要保留具体依据。当前产品 CLI 不要求传 pin 文件；默认最新也不保证两次独立命令之间没有发布。

源仓已经更新，为什么 Dataset 仍是旧内容？

Dataset 发布时已固定文件范围和来源 commit。维护者需要再发一版 Dataset，后续默认消费才会采用它。已打开的固定视图与挂载还需要显式更新。

发布成功后，为什么还搜不到？

先按回执确认正文已发布，再检查 Schema 的查询声明、Dataset 范围与该版本索引状态。后台负责索引维护，但写入完成不等于索引已经就绪。索引不可用不能当成没有数据。

有 Dataset 权限，为什么不能直接读取源仓？

Dataset 授权只开放这份交付清单的消费范围。直接按 Repository 读取属于另一条授权路径，不因能消费 Dataset 自动开放；请使用 Dataset 入口或申请所需仓级权限。

可以把特别大的 Dataset 挂载到本机，让 Agent 扫描吗？

不可以把 VFS 当成这种使用方式。VFS 仅适用于本机放得下的 Dataset，目前只读。特别大的数据集使用服务端统一检索与按需访问，或先切分出本机可容纳的范围。虚拟挂载与按需回读不取消容量限制。

Agent 能直接修改挂载目录吗？

目前不能。VFS 是只读消费入口。Agent 可以在普通工作目录准备草稿，再通过具备权限的 Writer 或评审发布流程提交。

能查询过去一小时的日志或恢复上周的实时状态吗？

当前状态读取不等于历史事件查询。Stream 窗口尚未完成通用交付；动态状态能否按旧依据重读取决于源能力和保留策略，固定 Dataset 本身不保存全部历史观察。
