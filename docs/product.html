KNOWLEDGE CATALOG / USER HANDBOOK

让知识被找到，
被理解，可信地使用。

Knowledge Catalog 是供人和 Agent 共用的通用知识底座。接入方把知识发布为有身份、有版本、有来源的内容；消费方在授权范围内发现、搜索、读取，并把它带入自己的工作。

我要使用知识 / CONSUMER

找到需要的知识，用进任务

看这里有什么，找到所需内容，确认版本与来源。适合个人、应用和 Agent。

从消费方步骤开始↗ 我要提供知识 / PROVIDER

注册自己的知识源，持续维护

选择平台提供或自己的 Snapshot 仓库，注册后发布知识，持续修改并交付新版本。

从接入方步骤开始↗

初次接触：先读 01–03，再按角色继续。整份手册无需联网即可阅读；执行示例需要连接你所在部署的 Server。

01

它解决什么问题

手册、规范、领域定义和运行信息分散在不同地方。真正使用时，你需要知道：去哪找、内容由谁负责、读到哪一版，以及是否有权使用。

发现与理解

先知道有什么，再找内容

从目录了解知识源与知识集，从 Schema 了解知识类型和可查询字段，再按条件搜索或按身份直接读取。

可信消费

每次使用都有依据

已发布知识带着版本与来源。一个任务可固定一组版本，人和 Agent 可以引用同一份依据。

分工与复用

知识独立维护，多处使用

接入方负责领域内容和维护，授权方控制访问范围。消费方可以组合多个知识源，接到已有项目或自己的应用中。

贯穿这份手册的例子

一个团队发布“值班手册”，另一个团队维护“服务规范”。值班人员或 Agent 把两者选为本次任务的知识集，搜索处置步骤、读取原文、记录来源与版本。之后知识更新，原任务仍可以按保存的版本核对依据。

02

先认识这些概念

沿着“发布 → 发现 → 使用”理解系统，不需要先学习存储实现。

概念你可以怎样理解在例子里
知识对象Object / Entity有稳定身份的一项知识。文件移动后，仍应指向同一个对象。一份“值班手册”
Aspect对象的一个方面把同一对象的不同方面分别表达、寻址和维护。手册的正文、摘要或维护说明
Schema结构与访问约定说明内容有哪些字段、如何校验，以及哪些字段支持全文、过滤、排序。手册的标题、正文及其查询方式
Repository知识源与治理边界保存知识版本，界定谁能写、谁能读。一个源可以包含很多对象。团队的运行知识源
Catalog共享组合空间发现知识源、查看源说明和命名知识集的入口。组织共享的知识目录
知识集 / Workspace本次任务使用哪些源可以选用已命名的知识集，也可以为一次任务临时组合。“值班知识”：手册 + 服务规范
pinResolvedWorkspace一次解析后固定的各仓版本。保存后可在后续命令中继续使用。这次值班任务开始时选定的版本

来源与关系：来源（Provenance）回答“这条知识从哪里来”；关系（Relation）表达“它与哪些对象有关”。知识身份、来源和版本一起，构成引用内容时的依据。

03

开始之前：打开客户端，确认身份

产品的使用入口是已配置好的客户端：服务地址由客户端封装，你按所接服务的方式登录，然后选择要接入或消费的知识。部署方在平台初始化时准备能力和策略，日常使用应由你自行完成。

以下命令在已完成连接与登录的客户端环境中执行
kc whoami
kc catalog list

检查结果确认当前用户或服务主体正确，并能看到获准使用的 Catalog。登录成功不等于已经获得所有知识的读取或维护权限。

当前版本还未完成首次开通的全部自助入口。

原生 CLI 的地址配置、普通用户登录、仓库申请与连接、首次授权仍有缺口；已有连接和权限后的发布、修改与消费有公开入口。下文明确区分这两种状态，详见自助能力核验。

示例约定

示例使用 kc 命令行。kr://acme/catalog、kr://acme/operations 和 oncall 都是占位 ID，请替换为实际返回值。命令块中的 commit、digest 和草稿路径也需要替换；同一组步骤在同一终端执行。

使用原生 kc 调试时，怎样设置连接？

原生 CLI 当前仍从参数或环境变量读取服务地址。若你使用的客户端尚未预置连接，下面是现有技术入口；产品交付仍需把这一步封装进客户端。登录方式以服务的认证模式为准。

原生 CLI / 已有可用认证条件时
export KC_SERVER_URL='https://kc.example.com'
kc login --server "$KC_SERVER_URL"
kc whoami

当前 Gitea 登录使用已有用户 token；Taihu 登录的客户端交换仍依赖部署应用秘密，这不符合普通用户自助登录要求，应由产品实现补齐，不能把该秘密发给用户。local 认证仅用于已启动的开发 Server，可在登录时显式指定 --mode local --as user:reader；token 模式不额外自报身份。

04

消费方：自行选源，找到并使用知识

从“这里有什么”开始，走到“读到内容并知道依据”。你可以为当前任务自行选择知识源；已有命名知识集时，也可以直接采用它。

开始条件

  • 完成登录并确认身份，知道这次任务要找什么。
  • 具备目录发现、所选仓的 Schema 浏览与读取权限，搜索时还需相应查询权限。
  • 自行组合需要目标 Catalog 的 Workspace 解析与消费权限；仅获准使用某个命名知识集时，就在该范围内使用。了解权限边界 →
1

看看有哪些知识源

列出可见目录，再打开其中一个。通过源说明了解内容范围，记下这次任务需要的 Repository ID。

发现目录与知识源
kc catalog list
kc catalog show kr://acme/catalog

检查结果看到知识源 ID、已发布的标题与摘要，以及已有命名知识集。没有源说明时应明确显示缺失，不由系统猜测。

2

了解知识类型和可查询字段

查看选定 Repository 发布的 Schema，再用返回的 Schema 对象 ID 查看结构与访问声明。

将 Repository 和 Schema ID 替换为实际返回值
kc knowledge schema list --repo kr://acme/operations --limit 20
kc knowledge schema describe --repo kr://acme/operations \
  --object schema/runbook/v1

检查结果知道有哪些类型、字段能否用于全文搜索、过滤或排序。这里列的是 Schema；有续页标记时继续分页。

3

自选知识源，固定任务版本

把需要的知识源保存为任务 pin。多个来源可重复传入 --source，不需要先发布命名知识集。

临时组合 / 自行选择已接入且获准消费的来源
kc workspace pin --catalog kr://acme/catalog \
  --source kr://acme/operations --out pin.json

检查结果pin.json 保存组合定义、Catalog 与各仓版本。它只服务于本次任务，不向 Catalog 新增命名知识集；后续请求直接传入这份文件。

已有命名知识集时怎样使用？

用 kc workspace pin oncall --catalog kr://acme/catalog --out named-pin.json 固定版本。消费命令继续带 --workspace oncall --catalog kr://acme/catalog --pin named-pin.json。命名集是可复用的选择方案，不是临时任务的必备前置步骤。

4

搜索定位，再读取原文

未知对象先搜，再用命中身份读取。示例查询要求知识源已声明全文检索字段，平台提供相应版本的检索能力。

使用上一步的临时 pin
kc knowledge search --pin pin.json --query '值班' --limit 10

# 替换为搜索命中返回的对象身份
kc knowledge read --pin pin.json --object runbooks/oncall

检查结果检查正文、所属 Repository 与版本。正文屏蔽、能力不足或部分结果分别按常见问题处理。

5

查看来源，保留引用依据

查看来源与历史，把对象身份、Repository、版本和 pin 随任务结果保存。内容更新后，可继续旧任务或自行采用新版本。

追溯同一版本上的知识
kc knowledge provenance --pin pin.json --object runbooks/oncall
kc knowledge log --pin pin.json --object runbooks/oncall --limit 10
已有对象身份时可以直接读。

kc knowledge read --repo kr://acme/operations --object runbooks/oncall 不依赖搜索。保存返回的 commit，后续使用 --commit 就能重复读取同一版。

05

接入方：注册知识源、发布并维护

接入方负责知识内容与持续维护。预期从客户端自行申请平台提供的 Snapshot，或连接自己维护的 Snapshot；登记为知识源后，完成首次发布、修改、评审与下线。

登录→申请或连接仓库→注册与权限确认→发布→修改与维护
已有自助入口

使用平台提供的 Snapshot

获准后通过客户端创建知识仓。平台分配存储、保存连接并按显式策略开通该仓维护权限；创建成功后即可发布，无需再次登记。

预期自助入口 · 待补齐

连接自己的 Snapshot

在客户端提交仓库地址与访问授权，查看连接验证结果并登记。内容及版本历史继续保留在自己的仓库，后续 Writer 发布写回该仓。

平台仓可自行创建，自有仓连接仍有缺口。

平台已配置托管存储和明确的创建者策略时，获准的接入方可以创建新仓并直接发布。自有仓的客户端连接、逐仓凭证管理、登录封装与完整分享流程仍待补齐；现有 attach 只验证并登记服务已配置的连接。

目前支持的 Snapshot 是 Dolt 与 Gitea。Gitea 远程仓库要求 1.26+ 并有可访问的发布版本；当前还没有 Gitee（码云）适配器。普通文件仓可以登记，但不会自动获得 Schema 或搜索能力。

开始条件

  • 完成登录与身份确认，取得目标 Catalog；平台已启用托管仓供给。
  • 具备该 Catalog 的创建准入；平台的创建者策略明确包括本次发布、预览与回读所需能力。
  • 无需全局授权管理权限。自有仓连接、登录封装和分享缺项仍见能力状态。
1

创建平台知识仓

选择新 Repository ID，为这次申请保留一个命令 ID。接入方不提交存储地址、凭证或自选权限。

获准接入的平台仓 / 创建成功后直接发布
kc catalog repo create --catalog kr://acme/catalog \
  --repo kr://acme/operations --command-id operations-create-001

检查结果返回 APPLIED、Repository ID 和初始 HEAD。平台已完成连接和目录准入，并按明确策略开通该仓能力；无需再次 attach。相同申请重试返回原创建结果 REPLAYED，不会新建第二份仓或补回已撤销权限。

已有外部 Snapshot 时使用 attach

服务连接已就绪并获成员管理权限时，执行 kc catalog repo attach --catalog kr://acme/catalog --repo kr://acme/operations。该路径保持来源内容与版本不变，不创建外部仓，也不隐式发权。自有地址与逐仓凭证的客户端管理仍未交付。

2

先发布一条知识，验证最短闭环

在刚创建并按策略获准写入的 Repository 中发布一条值班说明。对象身份用于后续引用，来源指向这段知识的实际出处。

这一步会写入目标 Repository / 请先替换示例来源
kc writer put --repo kr://acme/operations \
  --command-id oncall-demo-001 \
  --object runbooks/oncall-demo --if-absent \
  --value '{"text":"交接前检查未关闭的告警，并记录处理进展。"}' \
  --origin-kind SOURCE \
  --source-ref 'file:///your-drafts/oncall.md'

检查结果确认回执为 APPLIED，保存 result.newCommit。--if-absent 防止覆盖已有内容；对象已存在时按修改与重新发布操作。

这条示例用于验证发布与精确读取。

它还没有声明 Schema 与检索字段。需要能被搜索时，继续完成第 4 步的结构与检索约定。

3

按发布版本回读，检查来源

将下面的占位值换成刚才回执中的真实 commit。使用同一个 Repository 和对象身份验收。

替换 commit 后执行
KC_PUBLISHED_COMMIT='替换为写入回执中的新 commit'
kc knowledge read --repo kr://acme/operations \
  --object runbooks/oncall-demo --commit "$KC_PUBLISHED_COMMIT"
kc knowledge provenance --repo kr://acme/operations \
  --object runbooks/oncall-demo --commit "$KC_PUBLISHED_COMMIT"

检查结果正文与预期一致，来源指向真实出处，返回版本等于刚才发布的版本。

4

为正式接入定义身份、结构与搜索方式

  • 身份：确定稳定的对象 ID 和源标识到知识身份的映射；不要让移动文件改变对象身份。
  • 结构：按需要定义 Entity、Aspect 和 Relation。Domain Schema 与实例在目标 Repository 中一起版本化；System Repository 提供 Meta Schema 和核心协议 Schema。
  • 可搜索性：实例绑定对应 Schema，Schema 明确哪些字段支持 text、filter、sort。平台已启用检索时，后台追踪发布并维护相应版本的投影；使用者按返回状态判断是否就绪。
  • 可理解性：维护知识源的标题与摘要，说明内容范围；维护来源与兼容性规则。

检查结果消费方能发现知识源、理解类型，并用声明的查询条件找到代表性内容。精确读取和搜索应分别验收。

5

批量内容：先预览，再发布

将准备好的知识草稿打包为变更。新 Schema 与绑定它的实例可以放在同一批次，便于预览时检查身份、绑定和访问声明。

drafts 为已准备好的知识草稿目录
kc pack --repo kr://acme/operations \
  --dir .data/oncall-drafts --out changeset.json

# 检查 files / diagnostics，修正问题后再提交
kc writer commit --command-id oncall-batch-001 \
  --changeset changeset.json

检查结果pack 只保存待提交变更并返回预览诊断；commit 才发布。发布后按第 3 步回读，再请目标消费身份测试搜索与读取。

交付给消费方什么

  • 知识源 ID、内容范围、Schema 和代表性对象身份。
  • 本次发布的 commit、变更说明与兼容性影响。
  • 可选的命名知识集；消费方也可自行临时选源。

发布后检查什么

  • 按回执版本读到正确正文与来源。
  • 目标消费身份确有读取权限；发布与授予权限是两项操作。
  • 需要搜索时，确认声明字段与相应版本的检索状态。

持续更新：手工修改按下一节重新发布；批量采集可由 Connector 负责源访问、领域转换和增量处理，经同一 Writer 提交。Connector 运行与凭证托管的产品入口也需完成交付，不能将现有发布命令等同于已经具备全托管采集服务。

06

日常维护：修改、重新发布与采用更新

首次发布只是开始。下面沿用 runbooks/oncall-demo，完整演示接入方修改知识、消费方保留旧版或采用新版。仓库连接和权限就绪后，这条路径不需要部署方参与。

1

消费方先保存当前任务版本

在知识修改前保存一份 pin，后续用它复核旧内容。已有任务 pin 时可直接保留原文件。

消费方 / 首次发布之后、修改之前
kc workspace pin --catalog kr://acme/catalog \
  --source kr://acme/operations --out pin-v1.json
kc knowledge read --pin pin-v1.json --object runbooks/oncall-demo
2

接入方读取旧版，再准备完整新内容

先解析对象，取得该版的 commit 与 digest，再按同一个 commit 读取正文。digest 用来确认发布前内容没有被别人修改。

接入方 / 将占位值替换为 resolve 的实际返回值
kc knowledge resolve --repo kr://acme/operations \
  --object runbooks/oncall-demo

KC_EDIT_COMMIT='替换为 resolve 返回的 commit'
KC_EDIT_DIGEST='替换为 resolve 返回的 digest'
kc knowledge read --repo kr://acme/operations \
  --object runbooks/oncall-demo --commit "$KC_EDIT_COMMIT"

检查结果确认原文、来源和要修改的内容。digest 来自 knowledge resolve，不能使用命令回执的摘要。

3

用新命令 ID 发布修改，并回读验收

对象身份保持不变；PUT 提交该地址的完整新值。版本和内容前置条件会阻止基于过期内容的覆盖。

接入方 / 修改已有知识
kc writer put --repo kr://acme/operations \
  --command-id oncall-demo-002 --object runbooks/oncall-demo \
  --base "$KC_EDIT_COMMIT" --expected "$KC_EDIT_COMMIT" \
  --if-digest "$KC_EDIT_DIGEST" \
  --value '{"text":"交接前检查未关闭的告警，记录处理进展，并确认下一班责任人。"}' \
  --origin-kind SOURCE --source-ref 'file:///your-drafts/oncall.md'

KC_UPDATED_COMMIT='替换为本次回执的 result.newCommit'
kc knowledge read --repo kr://acme/operations \
  --object runbooks/oncall-demo --commit "$KC_UPDATED_COMMIT"

检查结果回执为 APPLIED，新 commit 能读到更新后的完整正文。每次新修改都用新的命令 ID。

修改 Aspect 或 Member 时：

resolve、read、put 都要带上相同的 --aspect / --member，使用那个地址的 digest。不要把整个对象的摘要用于某个 Aspect 的更新。

4

消费方自行决定何时采用新版

原任务继续用旧 pin。需要新版时生成另一份 pin，保留旧文件，不必重新注册知识源。

消费方 / 接入方修改发布之后
# 旧 pin 仍读取修改前的内容
kc knowledge read --pin pin-v1.json --object runbooks/oncall-demo

# 显式采用生成 pin 时的最新发布版本
kc workspace pin --catalog kr://acme/catalog \
  --source kr://acme/operations --out pin-v2.json
kc knowledge read --pin pin-v2.json --object runbooks/oncall-demo

检查结果旧 pin 内容不变，新 pin 能读到新增的交接要求。读取时仍检查当前权限；pin 不会永久保留已撤销的访问权。搜索新版还取决于该版检索状态。

还会遇到的维护场景

发布超时，或遇到别人同时修改

结果不确定时，查询 kc writer receipt --command-id oncall-demo-002，或使用完全相同的输入和命令 ID 重试；已完成的请求重放为 REPLAYED。版本或内容冲突时，重新 resolve、回读并合并修改，再用新 ID 发布；不要删掉前置条件强行覆盖。

修改需要评审后才能发布

使用 Proposal → Preview → Validate → Merge 流程。已有评审知识集且相应角色具备权限时，可按下面步骤操作；提案作者、评审者与合并者可以是不同主体。示例的 oncall、目标 ref 与候选 ref 需按实际仓替换。先重新取得当前 commit、digest，再提交候选内容。

提案作者 / 使用最新 KC_EDIT_COMMIT 与 KC_EDIT_DIGEST
kc governance proposal create --proposal-id ONCALL-REVIEW-001 \
  --repo kr://acme/operations --target refs/heads/main \
  --candidate refs/heads/candidates/ONCALL-REVIEW-001 \
  --base "$KC_EDIT_COMMIT" --object runbooks/oncall-demo \
  --if-digest "$KC_EDIT_DIGEST" \
  --value '{"text":"待评审的完整值班说明"}'

kc governance preview create --proposal ONCALL-REVIEW-001 \
  --workspace oncall --catalog kr://acme/catalog
评审与合并 / 替换每步返回的 ID
KC_PREVIEW='替换为返回的 previewId'
kc governance preview validate --preview "$KC_PREVIEW" \
  --catalog kr://acme/catalog

KC_VALIDATION='替换为验证返回的 reportId'
# 确认验证 PASSED，内容评审及所需 Gate 证据均已完成，再合并
kc governance proposal merge --proposal ONCALL-REVIEW-001 \
  --preview "$KC_PREVIEW" --validation "$KC_VALIDATION" \
  --catalog kr://acme/catalog

Proposal 保存候选，消费方仍读已发布版本；Merge 成功返回新 commit 后，按该版本回读，再由消费方生成新 pin。内置 Validate 只提供结构验证，不能当作人工内容评审；配置了额外 Gate 时还须满足对应验证要求。目标或候选移动后应重新准备预览与验证。

知识下线：删除当前内容，保留历史依据

先按上面的方式取得当前 commit 与 digest，确认影响后通过 Writer REMOVE 发布删除。仅指定对象会删除该对象全部单元；只删除一个 Aspect 或 Member 时，要在 resolve 和 remove 中指定相同地址。

接入方 / 删除整个示例对象；先重新取得当前 commit 与 digest
kc knowledge resolve --repo kr://acme/operations \
  --object runbooks/oncall-demo
KC_REMOVE_COMMIT='替换为本次 resolve 返回的 commit'
KC_REMOVE_DIGEST='替换为本次 resolve 返回的 digest'

kc writer remove --repo kr://acme/operations \
  --command-id oncall-demo-003 --object runbooks/oncall-demo \
  --base "$KC_REMOVE_COMMIT" --expected "$KC_REMOVE_COMMIT" \
  --if-digest "$KC_REMOVE_DIGEST"

发布后用新 pin 检查对象已不可读。旧 commit / pin 仍可在当前权限允许时复核历史；删除当前内容不会抹除历史，也不能替代访问权撤销。整个知识源停用还要处理消费依赖、接入状态和权限，不等于删除一条知识。

误改后恢复，以及 Schema 升级

恢复时先按历史 commit 读取正确内容，再基于当前版准备变更，把旧内容作为一次新发布提交。对象已被删除时使用不存在前置条件重新创建；仍存在时使用当前 digest。不要直接回退仓库发布指针，历史修改应保留。

Schema 兼容修改先检查全部受影响实例；破坏性变化发布新版本 Schema，让新旧版本共存并显式迁移实例。新 Schema 与对应实例可在同一批次预览、提交；消费方在采用新 pin 前确认结构变化。

07

在项目与 Agent 中使用

把选中的知识带进已有工作，而不是为每个任务重新复制一份知识库。

选择知识源→解析并保存 pin→交给应用或 Agent→保留引用依据

结构化消费

应用或 Agent 通过服务接口执行发现、搜索、读取和溯源。命令行使用本手册的 kc 步骤；同一任务持续传递同一份 pin。

只读文件视图

部署和宿主支持时，可用 kcfs 将知识投影到项目中，供编辑器和文件工具阅读。知识目录只读，项目自己的工作目录可照常写入。

只使用一个知识源：直接固定该仓版本

先读取已知对象，再保存返回的 commit，后续请求明确指定同一版本。使用多个知识源时，按第 04 节自行选源或采用已有命名知识集，并复用 pin。

单仓任务 / 将 commit 替换为首次读取返回的值
kc knowledge read --repo kr://acme/operations --object runbooks/oncall

KC_TASK_COMMIT='替换为首次读取返回的 commit'
kc knowledge read --repo kr://acme/operations \
  --commit "$KC_TASK_COMMIT" --object runbooks/oncall

临时组合：保存本次任务的定义与版本

具备该 Catalog 的组合消费权限与来源读取权限时，可为任务选择已接入的知识源，无须先发布命名知识集。多个来源可以重复传入 --source。

临时 pin 随任务保存
kc workspace pin --catalog kr://acme/catalog \
  --source kr://acme/operations --out task-pin.json
kc knowledge read --pin task-pin.json --object runbooks/oncall

临时 pin 文件保留组合定义、Catalog 与固定版本；后续读取和搜索直接复用该文件，来源更新后仍使用原版本，权限按请求当时检查。

可以交给 Agent 的任务要求

“使用这份 pin 查找本次值班所需的手册和服务规范。回答时保留知识对象、所属知识源和版本；无权读取、搜索不可用或结果不完整时明确说明。需要更新知识时，准备变更供发布流程处理。”

任务中途跟随新版本：显式重新生成 pin，并用新 pin 开始后续读取。需要复核原任务时保留旧 pin；读取权限仍以请求当时为准。

08

怎样理解版本、权限与来源

这些规则决定你拿到的内容能怎样使用，也是接入验收中最值得确认的部分。

版本：固定的是知识版本，动态观察另有时间依据

任务开始

解析知识集，得到手册在 A 版本、服务规范在 B 版本的 pin。

后来发布

手册更新为 A2。继续带原 pin 的读取仍使用 A；显式重新解析后，才能选择新版本。

当前值

若内容来自外部 State Binding，pin 固定的是观察声明所在版本。动态值还要查看观察版本与时间，旧 pin 不会自动保存过去的实时值。

权限：能发现、能使用知识集、能读正文，分别授权

你看到的行为意味着什么
在 Catalog 看见一个知识源允许发现该源和它的公开库存说明；正文读取仍需该 Repository 的读授权。
使用一个命名知识集可以按授权解析、消费这个组合；成员关系和 pin 都不会自动授予知识搜索或正文读取权限。
搜索命中但没有正文发现与正文交付分开。可以保留命中身份，正文按仓读权屏蔽；无读权本身不算部分结果。
重放以前保存的 pin版本坐标保持固定，权限按当前请求重新判断。撤销读取权限后，旧 pin 不能绕过它。

来源：回答“根据什么”，而不只看谁提交了它

来源描述这条知识的出处和演变依据。消费方用 knowledge provenance 核对，接入方在发布时维护真实来源。知识历史用于看内容变化；平台访问证据用于追查谁在何时访问了哪个版本。

09

常见问题

先判断是内容、权限、版本还是检索能力的问题，再决定下一步。点击展开答案；打印时会包含所有答案。

能看到知识源，为什么读不到正文？

目录发现与 Repository 读权分开。先用 kc whoami 核对身份，再请授权方检查目标仓的读权限。知识集成员资格不会自动带来读权，重新生成 pin 也不能补足权限。

发布成功了，为什么还搜不到？

先按回执版本精确回读，确认内容已发布。再检查实例是否绑定 Schema、Schema 是否声明相应检索字段，以及该版本的检索投影是否可用。查询时也要确认选中了正确知识源和 pin。平台已启用检索时由后台自动维护，用户不需要逐次触发同步；持续不可用时按返回诊断处理。

搜索不可用、部分结果、零命中，有什么区别？

不可用表示当前请求缺少必要能力或可用投影，应处理配置或状态；部分结果表示覆盖不完整，不能当作全部范围已经查完；零命中表示在本次声明的查询范围与覆盖内没有匹配。检查返回的范围、版本和覆盖说明。不要把无权看到正文当作没有命中。

更新后，为什么任务里还是旧内容？

检查是否仍在传入原来的 pin 或 commit。这是固定版本的预期行为。保留旧坐标用于复核，再显式生成新 pin 读取新版本。

平台替换实例后，已有仓与发布如何继续？

继续使用原 Repository ID、创建命令 ID 和发布回执。平台恢复连接与耐久记录；重放原创建或 Writer 命令返回原结果，不需要重新 attach。历史 commit 仍可精确回读，后续修改继续带当前版本和内容前置条件。被撤销的权限不会因重启或重试恢复。

写入时发生冲突，或者不确定上次是否成功，怎么办？

网络重试使用相同命令 ID 和完全相同的输入，可通过 kc writer receipt --command-id oncall-demo-001 查询回执。若内容已改变，使用新命令 ID。遇到版本或内容前置条件冲突，先回读并确认其他修改，再调整变更；不要盲目覆盖。

需要把源系统里的所有数据都搬进来吗？

先确定要治理和复用的知识范围。适合保留版本的内容通过 Writer 发布；需要观察当前值时，可使用外部 Binding，分别记录声明版本与观察依据。源访问和领域转换由接入方的 Connector 负责。

我能直接在项目挂载目录里修改知识吗？

知识文件视图只读。修改在草稿中准备，经 Writer 或提案治理流程发布；项目自身的普通文件照常编辑。这样知识版本、来源和写入检查才能保持一致。

它会替我回答问题、推断 Schema 或生成业务规则吗？

Knowledge Catalog 提供知识发现、读取、组合与维护能力。回答问题和业务推理由你的应用或 Agent 完成；对象身份、Schema、字段含义和质量规则由接入方明确提供。

如何反馈一个无法解决的问题？

提供当前身份、客户端版本、失败命令、Repository 或知识集 ID、对象身份、pin/commit、请求 ID（如有）及完整错误信息；写入问题附命令 ID。不要把登录凭证放进反馈。权限问题由授权管理者处理，内容与 Schema 问题由接入方处理，持续的服务故障提交平台支持。故障处理不属于每次发布或消费的必经步骤。

能力范围与随手速查

本手册对应 2026-09-07 的 Go 参考实现公开入口。实际可用能力取决于你连接的部署配置、客户端版本和授权。

当前入口

从这些能力开始使用

单实例 Server/Client 已形成发布与回读闭环；提供目录与 Schema 发现、知识集与 pin、来源与历史。配置检索后可使用搜索与关系查询；具备相应宿主条件时可使用只读文件视图。State Binding 有精确读取与独立动态检索能力。

采用边界

按部署能力安排接入

共享服务试点需要部署方提供认证、TLS、备份与单实例写入保障。多实例生产服务、Stream 窗口查询、MCP Gateway、多语言 SDK 尚未完成交付验收；完整动态观察部署仍有验收缺口。

自助能力核验：哪些已可用，哪些还缺入口

目标是“一个已配置的客户端，接入方与消费方自行完成”。当前参考实现仍有以下差距；它们是产品待补能力，不应改写成用户每次联系部署方的操作步骤。

使用环节当前状态完成自助需要什么
客户端与登录已有单一服务入口。原生 CLI 仍需地址参数或环境变量；Gitea 使用已有 token，Taihu 交换仍要求部署应用秘密。交付客户端封装服务地址、登录与凭证刷新，普通用户无需持有部署应用秘密。
申请平台仓 / 连接自有仓平台仓已有 create 入口，成功后可直接发布；连接及创建结果随实例替换恢复。自有仓 attach 仍只接受预配置 ID。补齐自有仓动态连接和逐仓凭证管理；Gitea 托管供给仍使用部署侧服务凭证。
首次权限与对外共享平台仓按明确创建者策略建立可撤销维护权限；登录与普通 attach 不发权。完整新用户准入与消费分享仍有缺口。按显式策略开通基础能力，允许维护者在获授范围内管理共享，不要求普通用户拥有全局管理权。
发布、修改、评审与下线仓连接与权限就绪后有公开入口。Writer 回执、内容与版本前置条件支持维护闭环。按本手册操作；批量采集托管与运行状态等产品体验仍需另行完善。
消费、复核与采用更新获准消费后可自行选源，保存临时 pin、读取并追溯；重新 pin 采用更新。不必预建命名知识集。跨全部 Catalog 的发现搜索入口仍未完成，可先列源再选择范围。
