KNOWLEDGE CATALOG / USER HANDBOOK

让知识被找到，
被理解，可信地使用。

Knowledge Catalog 是供人和 Agent 共用的通用知识底座。接入方把知识发布为有身份、有版本、有来源的内容；消费方在授权范围内发现、搜索、读取，并把它带入自己的工作。

我要使用知识 / CONSUMER

找到需要的知识，用进任务

看这里有什么，找到所需内容，确认版本与来源。适合个人、应用和 Agent。

从消费方步骤开始↗ 我要提供知识 / PROVIDER

注册自己的知识源，持续维护

选择平台提供或自己的 Snapshot 仓库，注册后发布知识，持续修改并交付新版本。

从接入方步骤开始↗

初次接触：先读 01–03，再按角色继续。整份手册无需联网即可阅读；执行示例需要连接你所在部署的 Server。

01

它解决什么问题

手册、规范、领域定义和运行信息分散在不同地方。真正使用时，你需要知道：去哪找、内容由谁负责、读到哪一版，以及是否有权使用。

发现与理解

先知道有什么，再找内容

从目录了解知识源与知识集，从 Schema 了解知识类型和可查询字段，再按条件搜索或按身份直接读取。

可信消费

每次使用都有依据

已发布知识带着版本与来源。一个任务可固定一组版本，人和 Agent 可以引用同一份依据。

分工与复用

知识独立维护，多处使用

接入方负责领域内容和维护，授权方控制访问范围。消费方可以组合多个知识源，接到已有项目或自己的应用中。

贯穿这份手册的例子

一个团队发布“值班手册”，另一个团队维护“服务规范”。值班人员或 Agent 把两者选为本次任务的知识集，搜索处置步骤、读取原文、记录来源与版本。之后知识更新，原任务仍可以按保存的版本核对依据。

02

先认识这些概念

沿着“发布 → 发现 → 使用”理解系统，不需要先学习存储实现。

概念你可以怎样理解在例子里
知识对象Object / Entity有稳定身份的一项知识。文件移动后，仍应指向同一个对象。一份“值班手册”
Aspect对象的一个方面把同一对象的不同方面分别表达、寻址和维护。手册的正文、摘要或维护说明
Schema结构与访问约定说明内容有哪些字段、如何校验，以及哪些字段支持全文、过滤、排序。手册的标题、正文及其查询方式
Repository知识源与治理边界保存知识版本，界定谁能写、谁能读。一个源可以包含很多对象。团队的运行知识源
Catalog共享组合空间发现知识源、查看源说明和命名知识集的入口。组织共享的知识目录
知识集 / Workspace本次任务使用哪些源可以选用已命名的知识集，也可以为一次任务临时组合。“值班知识”：手册 + 服务规范
pinResolvedKnowledgeSet一次解析后固定的各仓版本。保存后可在后续命令中继续使用。这次值班任务开始时选定的版本

来源与关系：来源（Provenance）回答“这条知识从哪里来”；关系（Relation）表达“它与哪些对象有关”。知识身份、来源和版本一起，构成引用内容时的依据。

03

开始之前：打开客户端，确认身份

产品的使用入口是已配置好的客户端：服务地址由客户端封装，你按所接服务的方式登录，然后选择要接入或消费的知识。部署方在平台初始化时准备能力和策略，日常使用应由你自行完成。

以下命令在已完成连接与登录的客户端环境中执行
kc whoami
kc admission show
# 首次使用且显示可申请时，显式申请部署允许的基础能力
kc admission request
kc catalog list

检查结果确认当前用户或服务主体正确，并能看到获准使用的 Catalog。登录成功不等于已经获得所有知识的读取或维护权限。

登录、首次准入与仓权限分别确认。

客户端保存已登录的服务入口，并按服务隔离会话。部署启用首次准入时，你可以显式申请允许的基础能力，再创建平台仓、连接已批准的自有 Gitea 仓或消费获分享的来源。登录本身不发权，重试申请也不会补回已撤销权限；详见自助能力核验。

示例约定

示例使用 kc 命令行。kr://acme/catalog、kr://acme/operations 和 oncall 都是占位 ID，请替换为实际返回值。命令块中的 commit、digest 和草稿路径也需要替换；同一组步骤在同一终端执行。

使用原生 kc 调试时，怎样设置连接？

首次登录时指定服务地址，成功后客户端保存入口；后续命令可以直接使用。显式 --server 或 KC_SERVER_URL 可选择其他服务，相应会话分别保存。登录方式以服务返回的认证模式为准。

Taihu Server / 首次浏览器登录
kc login --server 'https://kc.example.com'
# Taihu：在浏览器完成授权后，按返回提示等待登录完成
kc login --wait --server 'https://kc.example.com'
kc whoami

Taihu 浏览器授权和凭证刷新由 Server 中介完成，普通用户无需持有部署应用秘密。Gitea 使用个人 token，登录时指定 --mode token，并通过 KC_AUTH_TOKEN 或 --token 提供凭证；token 模式不额外指定 --as。local 认证仅用于已启动的开发 Server，可显式指定 --mode local --as kaiqidong。whoami 返回当前规范用户名，新的托管仓据此分配同名账号或隔离空间。

04

消费方：自行选源，找到并使用知识

从“这里有什么”开始，走到“读到内容并知道依据”。你可以为当前任务自行选择知识源；已有命名知识集时，也可以直接采用它。

开始条件

  • 完成登录并确认身份，知道这次任务要找什么。
  • 目录发现与 Catalog 发现搜索需要 catalog.read；Schema 浏览和正文读取仍分别按仓授权。
  • 自行组合可使用每个所选来源获分享的解析、消费与读取权限，也可使用相应 Catalog 范围授权；无需先取得 Catalog 管理权。命名知识集仍按其消费与查询权限使用。了解权限边界 →
1

看看有哪些知识源

列出可见目录，再打开其中一个。通过源说明了解内容范围，记下这次任务需要的 Repository ID。

发现目录与知识源
kc catalog list
kc catalog show kr://acme/catalog

检查结果看到知识源 ID、已发布的标题与摘要，以及已有命名知识集。没有源说明时应明确显示缺失，不由系统猜测。

尚未选源，能先在 Catalog 中搜索吗？

已配置发现知识集时，使用 kc search --catalog kr://acme/catalog --query '值班'。客户端先解析该 Catalog 的 discoveryWorkspaceId，固定本次版本，再执行搜索。只搜索管理员明确选定的来源，不自动包含全部登记仓，也不跨 Catalog 联搜。准入只需当前 catalog.read；无需额外的消费或逐仓查询授权，命中正文仍按仓读权屏蔽。持续任务需要固定版本时，选源并保存 pin。

2

了解知识类型和可查询字段

查看选定 Repository 发布的 Schema，再用返回的 Schema 对象 ID 查看结构与访问声明。

将 Repository 和 Schema ID 替换为实际返回值
kc schema list --repo kr://acme/operations --limit 20
kc schema describe --repo kr://acme/operations \
  --object schema/runbook/v1

检查结果知道有哪些类型、字段能否用于全文搜索、过滤或排序。这里列的是 Schema；有续页标记时继续分页。

3

自选知识源，固定任务版本

把需要的知识源保存为任务 pin。多个来源可重复传入 --source，不需要先发布命名知识集。

临时组合 / 自行选择已接入且获准消费的来源
kc pin --catalog kr://acme/catalog \
  --source kr://acme/operations --out pin.json

检查结果pin.json 保存组合定义、Catalog 与各仓版本。它只服务于本次任务，不向 Catalog 新增命名知识集；后续请求直接传入这份文件。

已有命名知识集时怎样使用？

用 kc pin oncall --catalog kr://acme/catalog --out named-pin.json 固定版本。消费命令继续带 --dataset oncall --catalog kr://acme/catalog --pin named-pin.json。命名集是可复用的选择方案，不是临时任务的必备前置步骤。

4

搜索定位，再读取原文

未知对象先搜，再用命中身份读取。示例查询要求知识源已声明全文检索字段，平台提供相应版本的检索能力。

使用上一步的临时 pin
kc search --pin pin.json --query '值班' --limit 10

# 替换为搜索命中返回的对象身份
kc read --pin pin.json --object runbooks/oncall

检查结果检查正文、所属 Repository 与版本。字段过滤、动态状态、分页和结果解释见动态索引与检索；正文屏蔽或其它错误见常见问题。

5

查看来源，保留引用依据

查看来源与历史，把对象身份、Repository、版本和 pin 随任务结果保存。内容更新后，可继续旧任务或自行采用新版本。

追溯同一版本上的知识
kc provenance --pin pin.json --object runbooks/oncall
kc log --pin pin.json --object runbooks/oncall --limit 10
已有对象身份时可以直接读。

kc read --repo kr://acme/operations --object runbooks/oncall 读取仓内已发布内容，不依赖搜索。保存返回的 commit，后续使用 --commit 重读同一版；读取外部 State 值时使用带 pin 的消费 READ。

05

接入方：注册知识源、发布并维护

接入方负责知识内容与持续维护。从客户端自行申请平台提供的 Snapshot，或连接自己维护的 Gitea Snapshot；登记为知识源后，完成首次发布、修改、评审与下线。

登录→申请或连接仓库→注册与权限确认→发布→修改与维护
已有自助入口

使用平台提供的 Snapshot

获准后通过客户端创建知识仓。平台分配存储、保存连接并按显式策略开通该仓维护权限；创建成功后即可发布，无需再次登记。

已有自助入口 · Gitea

连接自己的 Snapshot

在客户端提交仓库地址与访问授权，查看连接验证结果并登记。内容及版本历史继续保留在自己的仓库，后续 Writer 发布写回该仓。

选择平台托管，或连接已有 Gitea 仓。

平台仓由 Server 分配账号或隔离空间、保存连接并登记；自有 Gitea 仓由 Server 只读验证固定地址与身份，再保存逐仓授权。两条入口均按显式部署策略应用初始仓权限。凭证轮换、管理地址查询和受限分享有独立入口；attach 保留为已有静态或托管绑定的目录接入操作。

平台托管支持 Dolt 与 Gitea；自有仓动态连接当前支持 Gitea。Gitea 远程仓库要求 1.26+ 并有可访问的发布版本；尚未提供自有远程 Dolt 或 Gitee（码云）适配器。普通文件仓可以登记，但不会自动获得 Schema 或搜索能力。

开始条件

  • 完成登录与身份确认，通过已启用的首次准入申请或现有授权取得所需能力。
  • 创建平台仓需创建准入与已配置的托管池；连接自有仓需连接准入、批准的 Gitea 服务地址及你授权的逐仓凭证。
  • 初始策略明确包括发布、预览、回执、管理地址查询与回读所需能力；分享另按策略和当前授权检查，无需全局管理权限。
1

创建平台知识仓

填写仓名称。Server 使用当前用户名生成仓身份和恢复坐标，并自动分配存储。只有多个托管池时才需追加 --store 选择允许的池；不用手填 Repository ID、创建命令 ID、地址或凭证。

获准接入的平台仓 / 创建成功后直接发布
kc catalog repo create --name '值班知识'
kc catalog repo list --mine

检查结果创建结果包含 repositoryId、owner、初始 HEAD 与 managementURL；我的仓列表也可再次查询管理地址。Dolt 使用平台管理页；Gitea 可同时返回原生管理地址与登录准备状态。平台已完成连接和目录准入，无需再次 attach。同一用户重试相同名称与存储池恢复原结果，不补回已撤销权限。后续示例中的 Repository ID 均替换为本次返回值。

连接自己的 Gitea Snapshot，并管理凭证

选择逻辑 Repository ID，用 kc catalog repo connect --catalog kr://acme/catalog --repo kr://acme/operations --url https://git.example.com/kaiqidong/operations --credential-file /private/gitea-token 提交已有仓。服务地址必须在部署批准范围内；Server 只读验证已有发布与仓身份，不创建或改写外部仓。连接成功后可直接发布。

使用 kc catalog repo connection show --repo kr://acme/operations 查询管理地址，connection check 只读复查，connection rotate --repo kr://acme/operations --credential-file /private/new-gitea-token 轮换凭证（后两条也以 kc catalog repo 开头）。轮换只替换凭证，不更换地址或仓身份；失败保留旧连接。凭证过期后重启仍可进入管理接口恢复。已有静态或托管绑定加入 Catalog 时，仍可使用 catalog repo attach。

把已获准的来源分享给其他用户

具备本仓分享管理权时，使用 kc catalog repo share add --repo kr://acme/operations --principal teammate --action knowledge.read,dataset.resolve,file.read。只可分享部署白名单允许且你当前拥有的整仓消费动作。share list --repo <id> 查看；share remove --repo <id> --id <share-id> 撤销。分享不给对方全局管理权；撤销立即影响后续读取。

2

先发布一条知识，验证最短闭环

在刚创建并按策略获准写入的 Repository 中发布一条值班说明。对象身份用于后续引用，来源指向这段知识的实际出处。

这一步会写入目标 Repository / 请先替换示例来源
kc writer put --repo kr://acme/operations \
  --command-id oncall-demo-001 \
  --object runbooks/oncall-demo --if-absent \
  --value '{"text":"交接前检查未关闭的告警，并记录处理进展。"}' \
  --origin-kind SOURCE \
  --source-ref 'file:///your-drafts/oncall.md'

检查结果确认回执为 APPLIED，保存 result.newCommit。--if-absent 防止覆盖已有内容；对象已存在时按修改与重新发布操作。

这条示例用于验证发布与精确读取。

它还没有声明 Schema 与检索字段。需要能被搜索时，继续完成第 4 步，并按索引与检索章节验收。

3

按发布版本回读，检查来源

将下面的占位值换成刚才回执中的真实 commit。使用同一个 Repository 和对象身份验收。

替换 commit 后执行
KC_PUBLISHED_COMMIT='替换为写入回执中的新 commit'
kc read --repo kr://acme/operations \
  --object runbooks/oncall-demo --commit "$KC_PUBLISHED_COMMIT"
kc provenance --repo kr://acme/operations \
  --object runbooks/oncall-demo --commit "$KC_PUBLISHED_COMMIT"

检查结果正文与预期一致，来源指向真实出处，返回版本等于刚才发布的版本。外部 State 的观察值另按动态接入步骤验收。

4

为正式接入定义身份、结构与搜索方式

  • 身份：确定稳定的对象 ID 和源标识到知识身份的映射；不要让移动文件改变对象身份。
  • 结构：按需要定义 Entity、Aspect 和 Relation。Domain Schema 与实例在目标 Repository 中一起版本化；System Repository 提供 Meta Schema 和核心协议 Schema。
  • 可搜索性：实例绑定对应 Schema，Schema 明确哪些字段支持 text、filter、sort。平台已启用检索时，后台追踪发布并维护相应版本的投影；使用者按返回状态判断是否就绪。
  • 可理解性：维护知识源的标题与摘要，说明内容范围；维护来源与兼容性规则。

检查结果消费方能发现知识源、理解类型，并用声明的查询条件找到代表性内容。精确读取和搜索应分别验收。

5

批量内容：提交草稿目录

将准备好的知识草稿作为期望正文提交。新 Schema 与绑定它的实例可以放在同一目录。

drafts 为已准备好的知识草稿目录
kc diff --repo kr://acme/operations --dir .data/oncall-drafts
kc writer commit --command-id oncall-batch-001 \
  --repo kr://acme/operations \
  --dir .data/oncall-drafts

检查结果kc diff 对照当前版本列出 add / update，不写仓。writer commit --dir 用同一对照后发布。发布后按第 3 步回读，再请目标消费身份测试搜索与读取。

交付给消费方什么

  • 知识源 ID、内容范围、Schema 和代表性对象身份。
  • 本次发布的 commit、变更说明与兼容性影响。
  • 可选的命名知识集；消费方也可自行临时选源。

发布后检查什么

  • 按回执版本读到正确正文与来源。
  • 目标消费身份确有读取权限；发布与授予权限是两项操作。
  • 需要搜索时，确认声明字段与相应版本的检索状态。

持续更新：手工修改按修改与更新步骤重新发布；批量采集可由 Connector 负责源访问、领域转换和增量处理，经同一 Writer 提交。墙外 kc-integration 已提供构建、激活、调度、暂停与恢复入口，复用 KC 登录；运行方管理进程并注入源凭证。完整操作见仓库中的 integrationruntime/README.md。

06

动态索引与检索：查知识，也查当前状态

你既可以查“服务的负责人和处置手册”，也可以查“支付团队当前失败的服务”。前者来自已发布知识，后者需要外部状态。索引帮助定位对象；返回的正文和版本依据让你确认这次命中究竟代表什么。

一个对象，两类内容

服务 Service:orders 的团队、说明和操作规范随知识发布版本保存；它的 health 状态由外部监控系统提供。团队没变、知识 commit 没变，状态也可能从 healthy 变成 failed。动态索引让你按这个变化后的状态找到服务。

你想查什么内容与索引怎样更新怎样理解版本
已发布知识说明、规范、团队、配置定义Writer 发布新 commit，平台后台更新对应的 Snapshot 索引。pin 固定知识版本；搜索与正文按同一 commit 解释。
动态 State当前健康状态、进度、运行结果通过 Binding 观察外部值，更新独立动态索引；这次状态变化不产生知识 commit。同时看声明 commit、动态索引版本和每条命中的观察依据。pin 不单独冻结实时值。
历史事件与时间窗口过去一小时的告警、日志序列属于 Stream 的窗口与记录查询，不等于查询一个当前状态。当前通用 SEARCH / READ 尚未交付 Stream 窗口能力，不能用当前值代替历史记录。

接入方：让字段可检索，并持续反映变化

1

声明要查什么、值从哪里来

在目标仓发布 Schema，让实例绑定它。Schema 的 text 表示可做关键词匹配，filter 表示可按类型过滤，sort 表示可排序。这些声明对 Snapshot 值与动态 State 值都适用。

动态字段所属的 Aspect 还要发布 State Binding，说明怎样观察外部值；业务 Schema 描述观察得到的业务字段。服务端运行环境负责实际调用外部系统，返回完整值及观察依据。只发布一个 Binding 不会自动部署采集程序。

检查结果消费方能够浏览 Schema，知道可查询字段；通过带 pin 的精确 READ 能读到动态值及 observations。仅通过 --repo 的维护读取仍是仓内声明。

最小示例：发布一个可检索的动态健康状态

前提是目标仓可写，平台已接通运行环境，且其 health / health.lookup 调用已经实现。下面发布 Schema 与 State Binding；逻辑名称需与实际运行环境一致。新对象身份必须先经 Writer 发布，单有状态读取接口不会自动发现源系统全部对象。

接入方 / 发布动态状态的结构与访问声明
kc writer put --repo kr://acme/operations \
  --command-id health-schema-001 \
  --object schema/service.health --if-absent \
  --value '{"entity":"Service","aspect":"health","fields":{"status":{"type":"string","access":["text","filter"]}}}'

kc writer put --repo kr://acme/operations \
  --command-id health-binding-001 \
  --object Service:orders --aspect health \
  --schema-ref schema/service.health --if-absent --value null \
  --value-source '{"kind":"binding","binding":{"mode":"state","runtime":"health","protocol":"resource-access/v1","operations":{"lookup":{"call":"health.lookup"}}}}'

null 是仓内占位，实际健康状态由运行环境返回。这里没有把每次状态变化提交进仓库。发布后生成包含该版本的新 pin，用本节的 knowledge read --pin 验收，再以 --eq 'schema/service.health::health::status=failed' 验证动态检索。已存在的 Schema 或 Binding 应按修改与发布流程更新。

2

让平台维护索引

知识发布触发

正文、对象、Schema 或 Binding 经 Writer 更新后，后台根据发布版本推进索引。普通内容可增量更新；Schema 的检索声明变化需要重建。写入成功与新版本可检索是两个检查点。

外部状态触发

观察程序报告“这个状态发生了变化”，平台按固定 Binding 拉取新值与观察依据，再发布动态索引版本。通知不夹带正文，接入方无需直接操作检索引擎。

平台已装配检索服务和 State 运行能力时，首次建立动态索引由后台处理。日常消费不触发建索引，发布者也不需要每次手动执行同步。

给接入程序作者：怎样报告外部状态变化？

由具备 projection.manage 权限的观察程序自动发送变化通知。下面是现有入口，示例身份与 Aspect 请替换为实际声明；该权限不由知识写权限自动包含。

观察程序 / 状态已在外部系统发生变化后
kc operations projection notice --repo kr://acme/operations \
  --object Service:orders --aspect health \
  --source-revision health-002

source-revision 只是刷新提示，真正的版本依据来自运行环境返回的观察结果；通知被接受不代表新值已可搜索。消费者无需发送此通知。

已入队但刷新失败的通知会重试；尚未送达的外部变化不能靠知识 commit 对账发现。接入程序需要补发、定期对账或其它恢复机制。当前后台周期检查不等于对所有外部状态持续全量轮询。

3

分别验收读取、搜索与状态更新

先确认精确 READ 正确，再用声明过的字段查询。随后在外部系统改变状态并触发通知：应看到动态搜索的命中或正文变化、观察依据更新，而知识声明 commit 保持不变。

开始条件需要已启用的检索服务、可用的外部 State 运行环境、Binding 和相应访问授权。运行环境与逐源托管的自助入口仍有交付缺口；不能把“已发布 Schema”当成“动态检索已就绪”。

消费方：使用同一搜索入口

先按消费步骤自行选源并生成 pin.json。以下字段与服务对象是示例，执行前用 knowledge schema list / describe 确认实际 Schema、Aspect、字段类型和访问声明。

关键词检索 / 所选来源已声明 text 字段
kc search --pin pin.json \
  --query '值班' --match-mode AllTerms --limit 10

--match 'title=值班'		字段需声明 text。匹配模式可选 AllTerms、AnyTerms、Phrase，默认 AllTerms。

--in 'status=failed,degraded'		字段需声明 filter，值按 Schema 类型解释。多个过滤条件组成 AND。

同名字段有歧义时，使用 Schema::Aspect::字段路径 明确定位。下面假设 properties.team 来自 Snapshot，health.status 来自 State Binding，两者都声明 filter。

静态条件 + 动态条件 / 找支付团队当前失败的服务
kc search --pin pin.json \
  --eq 'schema/service.properties::properties::team=payments' \
  --eq 'schema/service.health::health::status=failed' \
  --limit 10

检查结果涉及 State 字段时系统选择动态检索能力，不需要额外的动态开关。动态索引中的静态字段仍按 pin 的声明版本解释；“当前”指这次索引记录的观察，不保证与此刻外部系统零延迟一致。

已知对象时直接观察当前状态 / 不依赖搜索索引
kc read --pin pin.json \
  --object Service:orders --aspect health

动态查询后再 READ，可能得到更新的值。动态搜索命中已经按这次动态索引版本回读正文；另发 READ 会通过固定 Binding 发起新的观察。需要保留“搜索当时看到什么”时，保存搜索命中的正文与观察依据，不能用后续 READ 的值替换原结果。

判断结果是否新鲜、完整、可复核

要确认什么看哪里怎样理解
查了哪个知识版本searchView.snapshots各 Repository 的声明 commit，与本次 pin 一致。
用了哪版动态索引searchView.projectionRevisions标识本次动态投影版本；不是知识 commit，也不是全源系统的同一时刻快照。
命中的正文与观察时间hits[].knowledge
hits[].version.observations[].basis		将正文与观察依据一起保存。basis 含 observedAt、consistency、bindingGeneration；源支持时还含 sourceRevision 或 watermark。
结果是否完整completeness 与 claimscomplete / partial 描述本次查询范围与执行完整性，不表示结果包含所有可能的知识，也不等于实时无延迟。
是否还有下一页continuation非空时可继续同一查询。命中条数与 limit 不是全量结果总数。
观察时间、可重复读取和任务 pin 的关系

observedAt 是观察发生的时间，不能代替源版本。repeatable 表示运行源支持按相同依据重读；bounded 只提供有界的新鲜度或版本约束；latest-only 只能给出调用时的最新观察。具体保留期限与运行能力仍需满足，旧 pin 本身不保证历史动态值可重放。

State 更新不会改变知识文件视图：项目挂载、checkout 和 --repo 维护读取仍展示固定 Snapshot 与声明。通过带 pin 的消费 READ 获取动态值，Stream 历史窗口则需要独立能力。

怎样翻页，动态状态变化后还能继续吗？

沿用完全相同的 pin、查询条件与排序，仅追加返回的 continuation。不要解析 token，也不要一边换查询一边沿用它。

继续上面的动态查询 / 仅当响应包含 continuation
KC_NEXT='替换为上一页返回的 continuation'
kc search --pin pin.json \
  --eq 'schema/service.properties::properties::team=payments' \
  --eq 'schema/service.health::health::status=failed' \
  --limit 10 --continuation "$KC_NEXT"

分页固定查询与动态投影版本。当前实现中，动态版本推进后旧 continuation 可能被拒绝；此时重新发起查询，并将结果作为新的一次检索，不能把新旧页拼成同一份完整结果。

零命中、部分结果、索引未就绪怎么处理？
  • 零命中：先检查知识源、pin、字段和值，并确认 completeness 与 claims；只有完整执行的零命中才能表示该次范围内未找到匹配。
  • partial：存在已声明的不完整覆盖或执行限制，保留 claims，不能据此断言其它对象不存在。
  • CAPABILITY_UNSATISFIED：字段未声明、查询能力或动态投影缺失；先查 Schema 和所选来源能力，不通过扫全仓代替。
  • PRECONDITION_FAILED：索引、观察依据或 continuation 已不匹配；重新查询。系统不能把更新后的值冒充原命中的值。
  • 运行环境暂时失败：按返回诊断重试或反馈故障。观察失败不等于业务字段缺失，不能当作 MISSING 或零命中。

搜索仍独立检查发现与正文权限：可能看到命中身份但正文被屏蔽。不要让无权读取、索引未就绪和真正零命中混成一个“没有数据”。

当前能力边界：已具备 Snapshot 检索、State 精确读取、独立动态投影和同版本正文回读。完整动态运行部署仍有验收缺口；Stream 窗口尚未交付。Catalog 发现搜索已提供入口，范围由显式配置的 discovery Workspace 决定。关键词检索不等同于任意自然语言问答或向量搜索，具体可用范围以 Schema、请求能力与返回诊断为准。

07

日常维护：修改、重新发布与采用更新

首次发布只是开始。下面沿用 runbooks/oncall-demo，完整演示接入方修改知识、消费方保留旧版或采用新版。仓库连接和权限就绪后，这条路径不需要部署方参与。

1

消费方先保存当前任务版本

在知识修改前保存一份 pin，后续用它复核旧内容。已有任务 pin 时可直接保留原文件。

消费方 / 首次发布之后、修改之前
kc pin --catalog kr://acme/catalog \
  --source kr://acme/operations --out pin-v1.json
kc read --pin pin-v1.json --object runbooks/oncall-demo
2

接入方读取旧版，再准备完整新内容

先解析对象，取得该版的 commit 与 digest，再按同一个 commit 读取正文。digest 用来确认发布前内容没有被别人修改。

接入方 / 将占位值替换为 resolve 的实际返回值
kc resolve --repo kr://acme/operations \
  --object runbooks/oncall-demo

KC_EDIT_COMMIT='替换为 resolve 返回的 commit'
KC_EDIT_DIGEST='替换为 resolve 返回的 digest'
kc read --repo kr://acme/operations \
  --object runbooks/oncall-demo --commit "$KC_EDIT_COMMIT"

检查结果确认原文、来源和要修改的内容。digest 来自 knowledge resolve，不能使用命令回执的摘要。

3

用新命令 ID 发布修改，并回读验收

对象身份保持不变；PUT 提交该地址的完整新值。版本和内容前置条件会阻止基于过期内容的覆盖。

接入方 / 修改已有知识
kc writer put --repo kr://acme/operations \
  --command-id oncall-demo-002 --object runbooks/oncall-demo \
  --base "$KC_EDIT_COMMIT" --expected "$KC_EDIT_COMMIT" \
  --if-digest "$KC_EDIT_DIGEST" \
  --value '{"text":"交接前检查未关闭的告警，记录处理进展，并确认下一班责任人。"}' \
  --origin-kind SOURCE --source-ref 'file:///your-drafts/oncall.md'

KC_UPDATED_COMMIT='替换为本次回执的 result.newCommit'
kc read --repo kr://acme/operations \
  --object runbooks/oncall-demo --commit "$KC_UPDATED_COMMIT"

检查结果回执为 APPLIED，新 commit 能读到更新后的完整正文。每次新修改都用新的命令 ID。

修改 Aspect 或 Member 时：

resolve、read、put 都要带上相同的 --aspect / --member，使用那个地址的 digest。不要把整个对象的摘要用于某个 Aspect 的更新。

4

消费方自行决定何时采用新版

原任务继续用旧 pin。需要新版时生成另一份 pin，保留旧文件，不必重新注册知识源。

消费方 / 接入方修改发布之后
# 旧 pin 仍读取修改前的内容
kc read --pin pin-v1.json --object runbooks/oncall-demo

# 显式采用生成 pin 时的最新发布版本
kc pin --catalog kr://acme/catalog \
  --source kr://acme/operations --out pin-v2.json
kc read --pin pin-v2.json --object runbooks/oncall-demo

检查结果旧 pin 内容不变，新 pin 能读到新增的交接要求。读取时仍检查当前权限；pin 不会永久保留已撤销的访问权。搜索新版还取决于该版检索状态。

还会遇到的维护场景

发布超时，或遇到别人同时修改

结果不确定时，查询 kc writer receipt --command-id oncall-demo-002，或使用完全相同的输入和命令 ID 重试；已完成的请求重放为 REPLAYED。版本或内容冲突时，重新 resolve、回读并合并修改，再用新 ID 发布；不要删掉前置条件强行覆盖。

修改需要评审后才能发布

使用 Proposal → Preview → Validate → Merge 流程。已有评审知识集且相应角色具备权限时，可按下面步骤操作；提案作者、评审者与合并者可以是不同主体。示例的 oncall、目标 ref 与候选 ref 需按实际仓替换。先重新取得当前 commit、digest，再提交候选内容。

提案作者 / 使用最新 KC_EDIT_COMMIT 与 KC_EDIT_DIGEST
kc governance proposal create --proposal-id ONCALL-REVIEW-001 \
  --repo kr://acme/operations --target refs/heads/main \
  --candidate refs/heads/candidates/ONCALL-REVIEW-001 \
  --base "$KC_EDIT_COMMIT" --object runbooks/oncall-demo \
  --if-digest "$KC_EDIT_DIGEST" \
  --value '{"text":"待评审的完整值班说明"}'

kc governance preview create --proposal ONCALL-REVIEW-001 \
  --dataset oncall --catalog kr://acme/catalog
评审与合并 / 替换每步返回的 ID
KC_PREVIEW='替换为返回的 previewId'
kc governance preview validate --preview "$KC_PREVIEW" \
  --catalog kr://acme/catalog

KC_VALIDATION='替换为验证返回的 reportId'
# 确认验证 PASSED，内容评审及所需 Gate 证据均已完成，再合并
kc governance proposal merge --proposal ONCALL-REVIEW-001 \
  --preview "$KC_PREVIEW" --validation "$KC_VALIDATION" \
  --catalog kr://acme/catalog

Proposal 保存候选，消费方仍读已发布版本；Merge 成功返回新 commit 后，按该版本回读，再由消费方生成新 pin。内置 Validate 只提供结构验证，不能当作人工内容评审；配置了额外 Gate 时还须满足对应验证要求。目标或候选移动后应重新准备预览与验证。

知识下线：删除当前内容，保留历史依据

先按上面的方式取得当前 commit 与 digest，确认影响后通过 Writer REMOVE 发布删除。仅指定对象会删除该对象全部单元；只删除一个 Aspect 或 Member 时，要在 resolve 和 remove 中指定相同地址。

接入方 / 删除整个示例对象；先重新取得当前 commit 与 digest
kc resolve --repo kr://acme/operations \
  --object runbooks/oncall-demo
KC_REMOVE_COMMIT='替换为本次 resolve 返回的 commit'
KC_REMOVE_DIGEST='替换为本次 resolve 返回的 digest'

kc writer remove --repo kr://acme/operations \
  --command-id oncall-demo-003 --object runbooks/oncall-demo \
  --base "$KC_REMOVE_COMMIT" --expected "$KC_REMOVE_COMMIT" \
  --if-digest "$KC_REMOVE_DIGEST"

发布后用新 pin 检查对象已不可读。旧 commit / pin 仍可在当前权限允许时复核历史；删除当前内容不会抹除历史，也不能替代访问权撤销。整个知识源停用还要处理消费依赖、接入状态和权限，不等于删除一条知识。

误改后恢复，以及 Schema 升级

恢复时先按历史 commit 读取正确内容，再基于当前版准备变更，把旧内容作为一次新发布提交。对象已被删除时使用不存在前置条件重新创建；仍存在时使用当前 digest。不要直接回退仓库发布指针，历史修改应保留。

Schema 兼容修改先检查全部受影响实例；破坏性变化发布新版本 Schema，让新旧版本共存并显式迁移实例。新 Schema 与对应实例可在同一批次预览、提交；消费方在采用新 pin 前确认结构变化。

08

在项目与 Agent 中使用

把选中的知识带进已有工作，而不是为每个任务重新复制一份知识库。

选择知识源→解析并保存 pin→交给应用或 Agent→保留引用依据

结构化消费

应用或 Agent 通过服务接口执行发现、搜索、读取和溯源。命令行使用本手册的 kc 步骤；同一任务持续传递同一份 pin。

只读文件视图

部署和宿主支持时，可用 kcfs 将知识投影到项目中，供编辑器和文件工具阅读。知识目录只读，项目自己的工作目录可照常写入。

只使用一个知识源：直接固定该仓版本

先读取已知对象，再保存返回的 commit，后续请求明确指定同一版本。使用多个知识源时，按第 04 节自行选源或采用已有命名知识集，并复用 pin。

单仓任务 / 将 commit 替换为首次读取返回的值
kc read --repo kr://acme/operations --object runbooks/oncall

KC_TASK_COMMIT='替换为首次读取返回的 commit'
kc read --repo kr://acme/operations \
  --commit "$KC_TASK_COMMIT" --object runbooks/oncall

临时组合：保存本次任务的定义与版本

具备每个所选来源的解析、消费与读取权限（或相应 Catalog 范围授权）时，可为任务选择已接入的知识源，无须先发布命名知识集，也无需 Catalog 管理权。多个来源可以重复传入 --source。

临时 pin 随任务保存
kc pin --catalog kr://acme/catalog \
  --source kr://acme/operations --out task-pin.json
kc read --pin task-pin.json --object runbooks/oncall

临时 pin 保留组合定义、Catalog 与固定版本；Snapshot 内容和 Binding 声明保持固定。外部 State 值另有动态观察依据，权限按请求当时检查。

可以交给 Agent 的任务要求

“使用这份 pin 查找本次值班所需的手册和服务规范。回答时保留知识对象、所属知识源和版本；涉及外部状态时，同时保存观察时间、来源版本与搜索命中依据。无权读取、搜索不可用或结果不完整时明确说明。需要更新知识时，准备变更供发布流程处理。”

任务中途跟随新版本：显式重新生成 pin，并用新 pin 开始后续读取。需要复核原任务时保留旧 pin；读取权限仍以请求当时为准。

09

怎样理解版本、权限与来源

这些规则决定你拿到的内容能怎样使用，也是接入验收中最值得确认的部分。

版本：固定的是知识版本，动态观察另有时间依据

任务开始

解析知识集，得到手册在 A 版本、服务规范在 B 版本的 pin。

后来发布

手册更新为 A2。继续带原 pin 的读取仍使用 A；显式重新解析后，才能选择新版本。

当前值

若内容来自外部 State Binding，pin 固定的是观察声明所在版本。动态值还要查看观察版本与时间，旧 pin 不会自动保存过去的实时值。具体步骤见动态索引与检索。

权限：能发现、能使用知识集、能读正文，分别授权

你看到的行为意味着什么
在 Catalog 看见一个知识源允许发现该源和它的公开库存说明；正文读取仍需该 Repository 的读授权。
使用一个命名知识集可以按授权解析、消费这个组合；成员关系和 pin 都不会自动授予知识搜索或正文读取权限。
搜索命中但没有正文发现与正文交付分开。可以保留命中身份，正文按仓读权屏蔽；无读权本身不算部分结果。
重放以前保存的 pin版本坐标保持固定，权限按当前请求重新判断。撤销读取权限后，旧 pin 不能绕过它。

来源：回答“根据什么”，而不只看谁提交了它

来源描述这条知识的出处和演变依据。消费方用 knowledge provenance 核对，接入方在发布时维护真实来源。知识历史用于看内容变化；平台访问证据用于追查谁在何时访问了哪个版本。

10

常见问题

先判断是内容、权限、版本还是检索能力的问题，再决定下一步。点击展开答案；打印时会包含所有答案。

能看到知识源，为什么读不到正文？

目录发现与 Repository 读权分开。先用 kc whoami 核对身份，再请授权方检查目标仓的读权限。知识集成员资格不会自动带来读权，重新生成 pin 也不能补足权限。

发布成功了，为什么还搜不到？

先按回执版本精确回读，确认内容已发布。再检查实例是否绑定 Schema、Schema 是否声明相应检索字段，以及该版本的检索投影是否可用。查询时也要确认选中了正确知识源和 pin。平台已启用检索时由后台自动维护，用户不需要逐次触发同步；持续不可用时按返回诊断处理。

搜索不可用、部分结果、零命中，有什么区别？

不可用表示当前请求缺少必要能力或可用投影，应处理配置或状态；部分结果表示覆盖不完整，不能当作全部范围已经查完；零命中表示在本次声明的查询范围与覆盖内没有匹配。检查返回的范围、版本和覆盖说明。不要把无权看到正文当作没有命中。

更新后，为什么任务里还是旧内容？

检查是否仍在传入原来的 pin 或 commit。这是固定版本的预期行为。保留旧坐标用于复核，再显式生成新 pin 读取新版本。

平台替换实例后，已有仓与发布如何继续？

继续使用原 Repository ID、仓名称与存储池选择，以及 Writer 发布回执。平台恢复连接与耐久记录；重试同名建仓或重放原 Writer 命令返回原结果，不需要重新 attach。历史 commit 仍可精确回读，后续修改继续带当前版本和内容前置条件。被撤销的权限不会因重启或重试恢复。

写入时发生冲突，或者不确定上次是否成功，怎么办？

网络重试使用相同命令 ID 和完全相同的输入，可通过 kc writer receipt --command-id oncall-demo-001 查询回执。若内容已改变，使用新命令 ID。遇到版本或内容前置条件冲突，先回读并确认其他修改，再调整变更；不要盲目覆盖。

需要把源系统里的所有数据都搬进来吗？

先确定要治理和复用的知识范围。适合保留版本的内容通过 Writer 发布；需要观察当前值时，可使用外部 Binding，分别记录声明版本与观察依据。源访问和领域转换由接入方的 Connector 负责。

我能直接在项目挂载目录里修改知识吗？

知识文件视图只读。修改在草稿中准备，经 Writer 或提案治理流程发布；项目自身的普通文件照常编辑。这样知识版本、来源和写入检查才能保持一致。

它会替我回答问题、推断 Schema 或生成业务规则吗？

Knowledge Catalog 提供知识发现、读取、组合与维护能力。回答问题和业务推理由你的应用或 Agent 完成；对象身份、Schema、字段含义和质量规则由接入方明确提供。

如何反馈一个无法解决的问题？

提供当前身份、客户端版本、失败命令、Repository 或知识集 ID、对象身份、pin/commit、请求 ID（如有）及完整错误信息；写入问题附命令 ID。不要把登录凭证放进反馈。权限问题由授权管理者处理，内容与 Schema 问题由接入方处理，持续的服务故障提交平台支持。故障处理不属于每次发布或消费的必经步骤。

能力范围与随手速查

本手册对应 2026-09-08 的 Go 参考实现公开入口。实际可用能力取决于你连接的部署配置、客户端版本和授权。

当前入口

从这些能力开始使用

单实例 Server/Client 已形成发布与回读闭环；提供目录与 Schema 发现、知识集与 pin、来源与历史。配置检索后可使用搜索与关系查询；具备相应宿主条件时可使用只读文件视图。State Binding 有精确读取与独立动态检索能力。

采用边界

按部署能力安排接入

共享服务试点需要部署方提供认证、TLS、备份与单实例写入保障。多实例生产服务、Stream 窗口查询、MCP Gateway、多语言 SDK 尚未完成交付验收；完整动态观察部署仍有验收缺口。

自助能力核验：哪些已可用，哪些还缺入口

目标是“一个已配置的客户端，接入方与消费方自行完成”。以下入口已按显式部署策略提供；尚未支持的适配器或部署能力保留明确边界，日常使用无需重复配置服务端连接或向用户交付部署秘密。
