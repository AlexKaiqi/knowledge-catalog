# DEBT-PRODUCT-FLOW-01 · 对齐产品书架构与首次使用旅程

## 债

- 位置：[产品书](../../doc/product.html) 的系统架构、例子详解、怎么接入与权限说明；[愿景](../../doc/vision.md) 的插件地基说明。
- 信号：2026-10-16 文档审阅发现，产品书把 Dataset 画在对象层之上，而正式架构将其放在文件底座；接入步骤允许跳过对象登记却继续使用对象目录发布命令，并依赖未交付的 Schema 与配方；已完善的公开首次发布指南尚未接入产品书。
- 判定：能力划分总体合理，问题是同一产品的结构图、角色、输入和成功条件没有连成可重复的阅读与使用路径。不是要求按当前实现收窄设计，也不是本轮运行验收结论。
- 处置：本条承接叙事结构、架构对齐及使用入口衔接；实现与能力证据仍归 `DEBT-PRODUCT-CLAIMS-01`、`DEBT-OBJECT-WRITE-GUIDE-01`、`PUBLICATION-SYNC-01` 等既有任务。重复的示例漂移沿既有产品示例自动合同修复，不复制验证器。
- 触发条件：下一次修改产品书，或将其作为接入方可直接照做的指南发布前。

## 目标

首次读者能依次理解谁维护内容、交付什么、怎么消费、如何更新与复核。产品书与正式架构使用同一能力边界，操作概览能通向完整公开指南，不要求读者补造输入或访问源码。

## 审阅发现与处置

| 位置（审阅时行号） | 证据与后果 | 处置 |
|---|---|---|
| 产品书 311–328：自下而上五层，Dataset 在对象之上，接入方连接仓 | 正式架构的五层是存储、对象、插件、服务、入口；Dataset 设计明确其停在文件层、不依赖对象。当前图与“只交付文件”承诺不一致，也容易误读为接入方绕过服务 | 统一正式分层，Snapshot 与 Dataset 放在底座，KC 的供给和消费请求均经服务；若画产品能力关系，明确不是依赖分层 |
| 产品书 255、328、440：完整对象、按对象交付、受限方面 | 对象设计要求仅组装当前范围中选入的方面，Dataset 不自动补齐引用或方面；Dataset 消费权整体覆盖选中文件，不能用来源仓的直读限制代替交付裁剪 | 在组合与权限段说明“先明确选入，再按身份组装”；区分仓范围读取的无权来源和 Dataset 范围外未选入内容 |
| 产品书 394–417：跳过对象登记后仍执行 writer commit --dir | 对象目录帮助要求合法对象文件；文件仓帮助另有原生来源工具路径。跳过第 2 步不等于第 3 步能上传原始视频、CSV 等文件 | 分出原始文件与对象两条供给入口，在固定版本及 Dataset 交付处汇合；链接公开输入说明，不扩张 Writer 的职责 |
| 产品书 395–423：首次对象发布依赖隐含材料 | Schema 未给获取路径，store-oncall.yaml 未提供；直接复用已公开例子的仓名、Dataset 名和版号；回读未固定目标仓和提交 | 复用系统首次发布指南中的公开原文件下载、练习目标、回执与固定版本回读。给出可取得的配方，或采用已公开的最小组合方式；不另造第三套样例 |
| 产品书 420–429：发布、授权后直接宣告用户可用 | 未以消费身份验证选中文件和对象，也没证明未选入内容保持不可达；供给、组合、消费的角色在同一组步骤中隐式切换 | 最短闭环补“消费者按同一修订读取”；每段写明所需角色与成功结果，按需指向授权说明 |
| 产品书 172、354、382：销售下降和活动效果 | 正文列出的输入是表与字段、作业、口径和关系，却直接跳到业务原因或计算结果；口径能指导查询，不能单独证明实际销量变化 | 明确例子回答的是口径解释还是实际分析。实际分析应展示经授权取得事实数据、计算和证据的环节；否则将结果限定为查明口径与形成待验证解释 |
| 愿景 23：外部取值按仓启用 | 插件设计明确不绑定仓或 Dataset，取值来源在读到单元时生效，关闭靠撤声明或卸载插件；产品书使用的是新模型 | 同步愿景概述，不为迁就旧概述改变新设计 |
| 产品书第一部分混入安装流程，第二部分再重复三组例子 | 面向接入方的读者需要在消费试用、架构、案例和供给步骤间反复切换；“零知识”的前提与扩展工具安装容易混在一起 | 首屏交代适用对象和前提；一个主例子贯穿价值、结构和供给/消费闭环，另两个作为扩展例子；高级插件与工具登记放在闭环之后 |

## 已有问题的去向

以下沿用 `DEBT-PRODUCT-CLAIMS-01`，本条不重复立项，也不认领其它在途修改：

- 区分来源仓提交、Dataset 新修订、消费者采用新版；自动跟随正文与“近期”状态不能互相矛盾。
- LiveAccess 无需全量迁入源库，不等于读取结果不离开来源系统；当次值、证据和可共享索引需如实说明。
- 对象登记不等于搜索已配置并就绪；工具登记与下载不等于任意 Agent 已完成安装、认证和业务调用。
- KC 权限承诺限定于经 KC 服务的访问；外部工具调用由外部系统执行授权，不能承诺约束 Agent 的全部行为。
- 稳定对象身份不等于脱离范围、权限、保留期后仍永远可读。
- 示例公开可读以当前部署库存为前提，不能由仓内夹具推导为任意服务已发布；静态健康快照、演示工具与真实系统状态继续明确区分。
- HTML 内可执行示例接入既有命令与旅程检查；能力状态与验收证据沿原任务维护。

## 建议阅读顺序

产品定位与适用角色 → 一个任务的结果与依据 → 仓、对象、Dataset 和统一服务的关系 → 消费已有交付 → 发布自己的对象并交付 → 更新、反馈和历史复核 → 按需搜索、外部取值与工具登记 → 边界和能力状态入口。

这是编辑建议，不新增协议约束。先解决架构和旅程断点，再调整目录与文案，保留清河茶铺的现有材料。

## 验收

- 架构图与正文同时支持纯文件交付及对象消费；Dataset 不被描述为依赖对象层，插件声明作用范围与现行设计一致。
- 新接入者能通过公开入口取得示例需要的全部输入；已存在的公开例子和个人练习目标分开，不默认拥有来源仓维护权。
- 首次发布旅程核对内容、身份、回执版本和消费范围；涉及示例的合同从实际公开材料执行，不从私有夹具补缺项。
- 更新说明区分仓版本、Dataset 修订与任务固定版本；实际业务结论提供所用事实，产品能力与 Agent 行为的边界清楚。
- 重读改动篇章，`make check-docs`、`make quality` 及受影响的公开指南与示例合同通过。真实部署或陌生 Agent 验收单独记录，不由文档检查代替。
