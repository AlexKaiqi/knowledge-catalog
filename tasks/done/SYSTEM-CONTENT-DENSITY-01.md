# SYSTEM-CONTENT-DENSITY-01 · 能力说明与短指南的内容密度守卫

## 目标

系统仓的正文密度有可执行的判定，不再靠人工感觉。低于判定的说明在发布时被拦下或明确登记豁免，而不是长期以"定义一句话 + 指向 help"的形态占着对象身份。

当前状态：`capabilities/` 下 30 篇正文全部落在 476-1644 字节区间，`inventory/usage.md` 476 字节、`extensions/usage.md` 548 字节、`identity/definition.md` 552 字节；`guides/` 下另有五篇 812-908 字节。这是同类信号在同一位置重复出现三十余次，按工程质量闭环应当升级为自动检查，而不是逐篇修。

现有守卫只覆盖结构：说明分类必须有已复核依据、导航闭包、发布清单一致性、Schema 对应。没有一条约束正文是否真的解释了任务。

## 依据

- [工程质量闭环](../../doc/engineering/quality.md)：同类信号出现两次以上升级为守卫或契约，不靠人记；质量问题三个出口。
- 系统仓说明分类守卫 `systemrepo/system_explanations_test.go` 与 `systemrepo/publish_test.go`：现有结构类守卫的位置与写法来源。
- [affordance](../../doc/design/affordance.md)：系统仓持有任务语义，help 持有参数合同，两者分工不该退化成前者只做指路。

## 验收

- 判定可执行且有意愿基础：先按说明类别（概念、能力用法、能力定义、指南）给出各自的正文判定，判定依据写明为什么是这个门槛，不用一个数字卡所有类别。
- 守卫上线后，现有低于判定的条目要么补齐，要么进入显式豁免清单并写明理由；不允许用调整门槛让存量自动变绿。
- 至少一条反例回归：构造一份只写"是什么 + 去查 help"的说明，守卫必须失败。
- `go test ./systemrepo/...`、`make quality`、`make check-docs` 全绿且无 skip。

## 前置

- `SYSTEM-GUIDE-EXECUTABLE-01` 先完成，本任务的门槛以补齐后的指南实际形态为参照，避免先卡门槛再为过关而写水。

## 不做

不把体量当唯一指标做机械字数检查；不要求所有说明达到同一长度；不因此新增 Schema 字段或改变说明的 Schema 形状。

## 关闭

2026-10-23 关闭，不实现。理由：本任务唯一的判定口径是正文字节数（自己记录的存量区间 476–1644 字节），
而它同时写着"不把体量当唯一指标"却没给出第二个指标。上限 1644 说明现有正文并非全部偏短，按字节卡只会
要求偏短的条目凑字数；没有第二个指标时，任何门槛都无法判定"这条说明是否真的解释了任务"，验收不可判定。
系统仓现有守卫（`systemrepo/system_explanations_test.go`、`publish_test.go`）已覆盖结构、依据、导航闭包与
Schema 对应；正文质量属于写作职责，不升级为自动检查。

若将来要重开，须先给出与体量无关的判定依据（例如"必须回答该任务的三类问题"这类可检出的结构），
而不是字节数。原文件在 git 历史里可查。
