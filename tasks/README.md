# 任务

一个任务一个文件，所在目录就是状态：

| 目录 | 含义 |
|---|---|
| `todo/` | 待做：目标和验收已经写清，还没开始 |
| `doing/` | 正在进行：已开始，进展写在文件里 |
| `done/` | 已结束：验收全绿后完成，或者未完成就关闭；关闭的条目末尾有 `## 关闭`，写明原因与去向 |
| `explore/` | 待回答的问题：结论未知，不预设交付物；不是第四种状态，见下 |

改状态就是移动文件（`git mv tasks/todo/X.md tasks/doing/`），文件里不另写状态字段。`make check-docs`
检查这个布局：只有这三个状态目录加 `explore/`；文件名是任务 ID；标题以同一个 ID 开头；同一个 ID 不会
同时出现在两个目录；文件里的链接都有效。

## 探索（`explore/`）

`explore/` 放的是**待回答的问题**，不是待做的工作。"这个入口的权限判定是否一致"有明确答案，但没有
已知的交付物和验收标准——先写验收等于先假定结论。因此它不进 `todo/`：`todo/` 的每一条都能判定变绿，
而探索的合法结论包括"没有问题，不改代码"。

- 不用 `audit` 这类命名：审计预设有问题存在，而探索的结论可能恰恰是没问题。目录名描述的是产出形态，
  不是对结论的预判。
- 探索文件不移动状态，在原位结束：末尾加 `## 结论`，写确认了什么、排除了什么、证据在哪。
- 确认的问题不就地修，另开任务承接。新任务用自己的 ID，不复用探索的 ID（同一个 ID 不允许同时是探索
  和任务）。探索文件保留结论作为该任务的由来。
- 排除了的疑点也写进 `## 结论`，避免同一疑点被反复重开。
- 探索不写 `## 验收`，改写成 `## 要回答的问题` 和 `## 判定标准`：前者是要消除的不确定性，后者是
  什么证据能让问题关闭，不假定结论方向。

## 写法

新任务的 ID 用大写词加两位序号，如 `PLUGIN-INTERPRETER-01`；债以 `DEBT-` 开头。`done/` 里有些历史
条目没有序号，保持原样。

```markdown
# <ID> · 一句话标题

## 目标
做完后系统是什么样，写结果，不写步骤。

## 依据
触碰的设计篇，链接到 doc/。

## 验收
哪些用例或规格变绿、哪些门禁通过。不写“命令成功”。

## 前置
依赖哪些任务，或要等什么条件。没有就写“无”。

## 不做
明确排除的范围。
```

- 开始：移到 `doing/` 即开始。前置已完成、彼此不改同一批文件的任务可以并行推进；有前置或改动重叠的按 `## 前置` 依次做。任务文件不记录由谁、在哪个分支执行，进展和交付只写事实与证据。
- 完成：契约（含 `make check-docs`、`make quality`）全绿、无 skip，才能移到 `done/`；在文件末尾加
  `## 交付`，写实现范围、已验证范围和提交。实现完成不等于验收通过，两者分开写。
- 关闭：不再做的任务也移到 `done/`，末尾加 `## 关闭`，写原因和剩余部分去了哪个任务。
- 债：质量“三出口”里登记为债的问题就是一条 `DEBT-` 任务，`## 目标` 之前加 `## 债`，写位置、信号、
  判定、处置、触发条件。
- 债的归并：登记时一个信号一条债；执行时按文件和环境归并。债的触发条件指向某个任务，或与某个任务改同一批
  文件、占同一测试环境时，该任务开工即把债并入（债登记时该任务已在 `doing/` 的，登记后立即并入）：主任务
  加 `## 并入`，写原债的位置、信号与剩余验收；原债移到 `done/`，末尾 `## 关闭` 写明并入哪个任务。不为单个
  信号另开一条与主任务改同一批文件的并行线。
- 大任务拆成多个文件，用 `## 前置` 连起来，不在一个文件里嵌套子任务清单。
- 任务之间按 ID 引用（写成 `` `PLUGIN-INTERPRETER-01` ``），不写成链接：文件会随状态移动，链接一移就断。
  链到 `doc/` 等不移动的位置照常写链接。
- `done/` 是历史，内容不再改写；词汇守卫对它豁免，对 `todo/`、`doing/` 不豁免。
- 本机 `.validation/` 证据用代码路径记录，不写 Markdown 链接；忽略的运行产物不随检出交付。

## Object、索引与 ARCH 推进安排（2026-10-20）

本轮主线先做 `OBJECT-VERSIONING-01` 与 `INDEX-PHYSICAL-01`，再按稳定下来的接口推进 ARCH 主要迁移。
此安排只更新规划，不改变任务状态；已有在途缺陷修复和各任务原验收范围继续按其合同推进。

| 顺序 | 工作与前置 | 放行结果 |
|---|---|---|
| 1 | Object 与 Index 共同审查接口；核对 `INDEX-SEARCH-SPACE-01` 的重叠批次 | 固定读取依据、范围和解释依赖明确；读取依据、观察证据与查询资源的保留责任分清 |
| 2 | `OBJECT-VERSIONING-01` 先交付固定读取依据基础 | 实现可被索引消费，固定回读、跨重启解析、范围及当前授权回归通过；具体交付条件由该任务维护 |
| 3 | `INDEX-PHYSICAL-01` 消费上述交付，推进资源保护、恢复与成员产物复用；Object 继续比较、无变化写入和历史 | 不重叠部分可分别推进，重叠文件按固定候选顺序接入；索引接入与接口稳定交付条件由索引任务维护 |
| 4 | 达到上述交付点后，推进 `ARCH-DATASET-PIN-01`、`ARCH-HOME-REPOSITORIES-01`、`ARCH-INVOCATION-01`、`ARCH-INVOKE-01` | 每批待迁职责的实际接口与回归已稳定，再做归位；不靠迁移替行为任务补实现 |
| 5 | `ARCH-TEST-OWNERSHIP-01` 收尾，再由 `ARCH-LAYOUT-01` 联合验收 | 测试归属、实际依赖和覆盖映射一致；各实现任务自己的测试仍须同批完成 |

`ARCH-CLIENT-SESSION-01` 可提前做；`ARCH-HOME-CONFIG-01` 可在共同审查后穿插，须确认不与索引的
新增持久状态、恢复及生命周期配置重叠，否则等该批配置交付后再迁。两项均不作为 Object 或 Index 开工前置。
错误码可先审计，实际删除须等对应行为合同与生产路径稳定，也不阻塞主线。

只有一条执行线时，按“共同审查 → Object 固定读取依据基础 → 索引物理重构与 Object 剩余交付 →
ARCH 主要迁移”推进；会话可提前做不表示应占用主线优先级。
交付点用于放行下游，须记录接口 owner、源码候选和通过的回归，不等于整项任务验收通过；
不要求两个行为任务整项互等，也不要求全部 Dataset 生命周期工作结束后才能开始所有 ARCH 工作。
