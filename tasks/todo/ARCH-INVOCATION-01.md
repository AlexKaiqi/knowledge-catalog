# ARCH-INVOCATION-01 · 调用链按职责归位

## 目标

一条调用路径只有一套职责划分：`invocation/` 保留统一执行器、请求载体、当前授权与固定范围协调，以及必要的
跨模块交付和留证；单模块规则由已有能力服务实现；调用参数、执行阶段、HTTP 编解码和观测各归其实际消费者。
只有仍被多个入口需要且不引入上层依赖的纯词汇可以保留为窄公共包；`invoke/` 是否保留由实际调用决定，
不以消除相似名称作为完成标准。

## 依据

- [服务](../../doc/design/service.md)、[权限](../../doc/design/permissions.md)、[Affordance](../../doc/design/affordance.md)、[架构](../../doc/architecture.md)。
- [架构不变量](../../doc/engineering/architecture-invariants.md)、[工程质量闭环](../../doc/engineering/quality.md)。
- 实施时核对 `invoke/README.md`、`invocation/README.md`、`internal/httpjson/README.md` 及公开输出合同。
- 迁移某个模块前，只补读其 owner 设计、包 README、公开接口与 Conformance。

## 范围

`invocation/` 一侧：逐项审查 `session_helpers.go` 的残留、`verbs_*.go`、请求形状、Dataset 范围、交付和证据适配。
已由会话与仓管理任务迁出的职责不再重做；对象、发现和外部取值的具体规则分别归已有所属服务。
基础授权规则仍在 `snapshot/access`，请求级授权协调可留应用层；证据存储仍在 `observability`，
与本次调用关联的留证顺序由执行器负责。不强制按文件行数再造子包。

`invoke/` 一侧：以实际生产消费者梳理七类现有文件及导出符号。执行阶段归执行器；通用 HTTP 编解码与现有
`internal/httpjson` 统一；调用观测按应用适配和底层遥测分开；参数读取与规范输出按共享需求确定归属。
HTTP 基础设施不能为接收现有结果类型而反向依赖 Invocation，底层遥测也不取得授权或证据决策权。
既有公开 Go 入口按总任务兼容约定处理，不保留私有壳或另造宽泛工具包。

## 验收

- 每个迁出职责的目标服务使用已有或确有业务消费者的窄端口，不接收整个 Home/Invocation 取得隐藏依赖。
- 生产 CLI 经模块 SDK 到 Server，同一业务任务由同一执行器处理；
  CLI 与 HTTP 的结果、固定版本、授权、错误和证据语义保持一致。
- 空主体在资源访问前拒绝；一次请求只固定一次范围和版本；撤权后的新请求与续页重新检查当前权限。
  消费路径不扫描全库、不启动投影维护，依赖不可用不回退最新或空结果。
- 对象读写、发现和 LiveAccess 的模块算法只有一个 owner；
  不用私有转发、类型别名堆叠或复制规则维持两套路径。
- 应用执行不解析 argv、不注册 HTTP 路由、不打开部署、不构造具体 provider；
  必要的借用资源通过既有生命周期边界传入，相关正反架构守卫保留。
- 每项 `invoke/` 原职责有唯一去向和生产消费者，剩余公共包的允许依赖有明确清单；
  无仅为改名新增的平行实现或全量原样转发。
- HTTP 解码、输入大小与压缩限制、无损 JSON 数字、错误信封和状态映射保留原合同；
  CLI 输出与服务端编码的已有边界回归通过。
- 执行阶段和 Hook 作用范围不因位置变化改变；日志、trace 与证据观察仍关联同一请求，
  不重复计数，不将凭据或敏感正文写入遥测。
- 通用 HTTP/JSON 基础设施、参数词汇和底层遥测各自依赖方向受守卫保护；
  CLI 与 Server 仍使用同一应用执行器，而不是相互调用运输适配。
- 模块 SDK 与 CLI 不因共享辅助导入 Home 或执行器实现。
- 迁移测试同批完成，真实跨模块执行、授权、交付与证据失败回归继续覆盖；
  按 `tasks/README.md` 的「目录重组的共同约定」取门禁范围；同步包说明、依赖表和相关测试登记。

## 前置

- `ARCH-HOME-REPOSITORIES-01`：会话、配置和仓管理的前置拆分已完成，执行器消费明确的资源和管理服务。
- `ARCH-DATASET-PIN-01`（已归档）：固定范围转换已有唯一 owner。
- 上述两项传递前置包含 Object 的“固定读取依据交付”和 Index 的“索引接入与接口稳定交付”。
  另外，`COMPARE-01`、`NO-CHANGE-01`、`ZERO-DIFF-01`、`HISTORY-01` 中本轮要迁的比较、无变化写入、目录意图、历史和回放操作，
  必须先由原任务交付该批实际接口、实现与回归；基础读取依据通过不自动放行这些操作的搬迁。
- `INDEX-SEARCH-SPACE-01`、Dataset 生命周期及发现入口的重叠批次也须先固定；逐项记录消费者、
  源码候选与迁移映射，不要求未触及的可选优化或整项任务全部结束。
  未完成的行为不在本任务补实现，既有未解决债仍保留原任务归属。
- 路由清单继续复用 `ROUTE-MANIFEST-01` 的现有交付（已归档）。

## 不做

不新增协议或业务能力，不机械把 `invocation` 改名为通用 app 包，不删除合法跨模块协调，
不改变独立 Snapshot Service 的职责。

不强制移除 `invoke`，不重写命令框架或路由清单，不改输出、状态码或错误码集合，
不把 KC 会话、授权或领域 DTO 塞入 HTTP 基础设施。

## 沿革

2026-10-23 把 `ARCH-INVOKE-01` 并回本条。并入理由：两者改同一条调用路径的同一批文件——`invoke/` 的
执行阶段就是 `invocation/` 执行器的职责边界，`invocation/` 的 `verbs_*.go` 正是 `invoke` 参数的消费者。
原 `ARCH-INVOKE-01` 的“前置”第一条就是“`ARCH-INVOCATION-01` 完成：先稳定实际执行职责和消费者，
避免对尚待归位的调用链整体改名”。分两条时，同一条链要改两遍，第二遍必须等第一遍的边界定稿；
合并后一次定界，执行、参数、编解码与遥测各归其位。

原 `ARCH-INVOKE-01` 的三条约束原样保留：`invoke` 不必然被删除，包的去留由实际依赖决定，
不以改名作为完成标准。

同时修正一处规划矛盾：[路线](../../doc/roadmap.md) 目录重组表把 `invoke/` 处理写成
“可选：给 `invoke/` 改个更清楚的名字”，但 `ARCH-TEST-OWNERSHIP-01` 曾把它列为前置，
而测试归属又是 `ARCH-LAYOUT-01` 的七项前置之一——一条“可选项”实际卡住了总验收。
现改为：`invoke/` 归位是本任务的组成部分，不再是独立可选项；其去留仍由实际依赖决定。
