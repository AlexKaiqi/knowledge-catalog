# 治理：反馈、提案、Gate 与 Hook

多团队维护的对象需要一条从“发现问题”回到“发布修订”的路径，也需要在关键动作上接入团队已有的
流程。治理负责这条路径，但不是第二个写入口。

## 目标

- 使用中发现的问题带着依据回到维护者。
- 需要评审的修改经提案、预览、检查后合并，合并时能复核到底批准了什么。
- 团队已有的 CI、通知、审批通过 Hook 和 Gate 接入，平台不托管它们的业务规则。

## 三个独立的问题

| 边界 | 回答什么 | 依据 |
|---|---|---|
| 授权 | 谁现在可以做这个动作 | 身份、资源与当前政策 |
| Gate | 这次合并是否具备所需证据 | 固定的预览和已保存的检查结果 |
| Hook | 动作前后是否调用外部逻辑 | 部署配置与动作的生命周期 |

通过授权仍可能缺证据；外部脚本同意也不授予权限。失败要分开说明，用户才知道该补权、补证据还是修外部调用。

## 反馈到修订

1. Agent 在使用订单服务的值班说明时，发现第 2 步过时，提交反馈，关联这次访问。
2. 交易团队按对象身份和当时的版本核对，区分是内容错误、范围缺失、能力不足还是观察过时。
3. 团队形成正常的 Writer 提交或提案；修订发布后，后续任务按采用规则使用新版。
4. 已固定的旧任务仍按原版本复核。

反馈本身不改变对象，不批准修订，不给模型推断发写权。

## 提案与 Gate

- 评审面对的是固定来源、候选变更和内容共同确定的预览，不是会移动的分支名。
- 候选或目标变了，旧证据不能批准新组合；合并仍要检查目标没有漂移并条件提交。
- Gate 要求哪些检查由治理配置决定，调用者不能靠少传某项证据绕过。
- 外部系统运行自己的检查，再经受控入口记录结果；记录证据的权限受控。平台不运行业务套件。
- Gate 只管提案合并，不挂在普通写入和读取上，以免外部 CI 卡住每次写入。
- 合并产生新的源提交，不自动发布新的 Dataset。

## Hook

- 挂在应用动作上，命令行和 HTTP 共用触发时机。授权先成立，再进入动作生命周期。
- 前置 Hook 只能否决，不能修改变更、补造来源或代替 Schema 校验；超时和拒绝都阻止动作。前置 Hook 不应做不可逆的外部操作。
- 后置 Hook 在成功回执可靠保存后触发，适合通知。投递失败进入重试，不回滚提交。
- 同一个已接受的命令重放不再触发新一轮 Hook；网络投递仍可能重试，接收方要防重。
- 出站内容只带主体、动作、资源、版本、回执等指针，正文由接收方在授权下回读。
- 搜索、读取不挂 Hook；外部取值走 LiveAccess；源变化通知和索引维护各有自己的机制，不共享配置。

## 例子

交易团队为值班说明配置 Gate：合并前必须有“格式检查”的通过记录。团队提出提案后，后置 Hook 通知
CI；CI 对精确的预览运行检查并记录结果；合并时 Gate 核对记录。前置合并 Hook 放行也不能替代这条记录。

## 代码位置

| 目录 | 负责 |
|---|---|
| `controlplane/` | 提案、预览、校验、合并编排 |
| `gate/` | 合并前的证据清单（计划与 `controlplane/` 合并为 `governance/`） |
| `hook/` | 出站 Hook |
| `observability/` | 反馈与访问证据 |

## 进度

| 进度 | 内容 |
|---|---|
| 已有 | 反馈记录、提案到合并、Gate、前置与后置 Hook、投递重试 |
| 近期 | 定提案流程的去留，再把 `controlplane/` 与 `gate/` 合并为 `governance/` |
| 未到 | 在真实任务中证明反馈到修订再到采用的效果和成本 |
