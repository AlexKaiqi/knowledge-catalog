# 治理：反馈、工作分支、条件合并与 Hook

多团队维护的对象需要一条从“发现问题”回到“发布修订”的路径，也需要在关键动作上接入团队已有的
流程。治理负责这条路径，但不是第二个写入口：所有对象变更仍经 Writer，评审与审批由业务负责。

## 目标

- 使用中发现的问题带着依据回到维护者。
- 需要评审的修改先写到工作分支，评审后以条件合并发布；合并时能复核到底发布了哪个 commit。
- 团队已有的 CI、通知、审批通过 Hook 接入，平台不托管它们的业务规则，也不保存评审或检查结论。

## 三个独立的问题

| 边界 | 回答什么 | 依据 |
|---|---|---|
| 授权 | 谁现在可以做这个动作 | 身份、资源（含目标引用）与当前政策 |
| 条件合并 | 这次合并发布的是不是审阅过的组合 | 审阅时固定的分支 commit 与目标 commit、目标的 Schema |
| Hook | 动作前后是否调用外部逻辑 | 部署配置与动作的生命周期 |

通过授权仍可能因基点移动被拒；外部脚本同意也不授予权限。失败要分开说明，用户才知道该补权、重新评审还是修外部调用。

## 反馈到修订

1. Agent 在使用订单服务的值班说明时，发现第 2 步过时，提交反馈，关联这次访问。
2. 交易团队按对象身份和当时的版本核对，区分是内容错误、范围缺失、能力不足还是观察过时。
3. 团队直接经 Writer 提交，或先写工作分支、评审后合并；修订发布后，后续任务按采用规则使用新版。
4. 已固定的旧任务仍按原版本复核。

反馈本身不改变对象，不批准修订，不给模型推断发写权。

## 工作分支

- Writer 可以把提交写到指定分支。分支写入复用同一套 Schema、来源、并发与幂等校验，一次仍只修改一个仓。
- 开分支需要新分支范围的 `writer.branch`；向分支提交需要该分支范围的 `writer.commit`。授权按引用区分，写分支的权限不蕴含发布到 main。
- 分支写入不推进 main，不通知索引、Dataset 或维护；分支不随 main 自动前进。
- 系统仓不接受分支与合并。

## 条件合并

- 评审面对的是分支上的一个确定 commit，而不是会移动的分支名。合并可以固定审阅时的分支 commit 与目标 commit。
- 分支在审阅后又被写入，以 `CANDIDATE_MOVED` 拒绝；目标已推进、不再能快进，以 `NON_FAST_FORWARD` 拒绝。两者都需要在新基点上重新评审。
- 合并只做快进，不做三方合并或自动变基。合并前把分支改动当作一份变更集，按目标的 Schema 重新校验每个改动对象，并要求改动全部是经 Writer 写入、可定位的对象单元。
- 合并需要目标引用范围的 `writer.merge`，带命令身份；同一身份重放返回原回执，换内容拒绝。
- 只有推进 `refs/heads/main` 时才通知索引、Dataset 与维护；合并产生的新源版本不自动发布新的 Dataset 版本。

## 审批归业务

KC 不保存提案、预览、评审意见或外部套件结果。需要在 KC 内强制审批时，业务在 `writer.merge` 上配置前置 Hook：
它查询自己的评审系统，拒绝即否决本次合并。CI 可以由分支提交的后置 Hook 触发，读分支 commit 自行运行。

## Hook

- 挂在应用动作上，命令行和 HTTP 共用触发时机。授权先成立，再进入动作生命周期。
- 前置 Hook 只能否决，不能修改变更、补造来源或代替 Schema 校验；超时和拒绝都阻止动作。前置 Hook 不应做不可逆的外部操作。
- 后置 Hook 在成功回执可靠保存后触发，适合通知。投递失败进入重试，不回滚提交或合并。
- 同一个已接受的命令重放不再触发新一轮 Hook；网络投递仍可能重试，接收方要防重。
- 出站内容只带主体、动作、资源、版本、回执等指针，正文由接收方在授权下回读。
- 搜索、读取不挂 Hook；外部取值走 LiveAccess；源变化通知和索引维护各有自己的机制，不共享配置。

## 例子

交易团队修订值班说明：开 `review/oncall` 分支并提交修改；分支提交的后置 Hook 通知 CI，CI 读取该分支 commit
运行格式检查，结果留在团队自己的评审系统。评审通过后，维护者带着审阅的分支 commit 与 main commit 请求合并；
`writer.merge` 前置 Hook 向评审系统确认这个 commit 已批准，KC 再做快进与 Schema 校验并发布。

## 代码位置

| 目录 | 负责 |
|---|---|
| `object/writer/` | 分支写入、条件合并与合并前校验 |
| `hook/` | 出站 Hook |
| `observability/` | 反馈与访问证据 |

## 进度

| 进度 | 内容 |
|---|---|
| 已有 | 反馈记录、工作分支写入、条件快进合并与合并前校验、前置与后置 Hook、投递重试 |
| 未到 | 在真实任务中证明反馈到修订再到采用的效果和成本 |
