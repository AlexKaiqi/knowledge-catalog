# 权限

多团队协作要求权限按团队和用途分开：维护一个仓、消费一份交付、看到库存里有什么，是三件不同的事。
权限每次请求都重新检查。

## 目标

- 所有请求都经 Server 认证，包括本机命令行。客户端自报的名字、Git 作者、本地目录都不是身份。
- 身份是一个稳定的用户名。同名的新用户不能接管旧授权。
- 授权按“谁、对哪个资源、做什么动作”判断，资源只有三种：服务库存、仓、Dataset。
- 版本固定不冻结权限。撤权后，拿着旧版本坐标也不能继续读。
- 外部系统的权限由外部系统执行。读得到“谁能查这张表”的知识，不等于能查这张表。

## 三种资源

| 资源 | 授权回答什么 | 不隐含什么 |
|---|---|---|
| 服务库存 | 能否看到有哪些仓和 Dataset，能否登记和组合 | 看得到不等于能读内容 |
| 仓 | 能否维护或消费这个仓的内容与历史 | 外部存储的管理员身份不自动变成 KC 权限 |
| Dataset | 能否消费这份交付、管理它的发布 | 不开放来源整仓、清单外文件或写权限 |

## 为什么边界落在仓，不做对象级权限

仓是完整的版本图。对象或文件级的读权限会迫使每次历史读取、索引、备份和迁移都做正确裁剪，
而且历史一旦被克隆就无法隐藏一部分。边界落在仓之后，授权就是“身份 × 动作 × 仓”，复杂度随团队
数量增长，而不是随对象数量增长。

需要更细的隔离时，用仓来划分：

- 读者集合、历史可见性、写权限或发布节奏真正不同时，分仓。
- 两个仓经常必须在同一次变更里一起改，说明边界划错了，考虑合并。
- 同一对象有敏感信息差时，把敏感方面放在受限仓，不引入方面级读权限。对象身份不带仓，同一个
  `object_id` 的方面可以分布在不同仓，见[对象](object.md)；无权读的仓里的方面在读取时标为无权。

## 规则

- 发现与读取分开。已认证用户可以看到库存；部署可以声明某个仓“已认证用户默认可读”，覆盖读取、
  搜索、历史、来源这类消费动作，不放行任何写或发权。系统自描述仓是第一个使用者。
- 范围先于搜索。在 Dataset 内搜索只在发布的文件范围内执行；跨仓按类型发现只在调用者可读的仓内
  执行。都不能先查出范围外对象再遮住正文。
- 关系不扩权。引用另一个仓的对象不授予它的读权限，也不把它加入 Dataset；遍历越界时停下并标明。
- 发布不发权。创建仓、登记、发布 Dataset、授权是不同的事。可以配置创建者自动获得窄权限，但要可审计、可撤销，重放不能恢复已撤销的权限。
- 发布者不能通过组合把自己没有的能力授予别人。
- 缓存和索引只复用内容，不复用上一个调用者的授权结果。
- 外部状态有两次授权：后台有权取值，不表示所有消费者都能看。来源要求逐个调用者授权时，读取、搜索、翻页都受当前来源授权约束；没有明确的共享许可就不共享。
- 凭证只发给可信目标，访问地址变化或重定向不能扩大凭证范围；凭证不进入知识、观察、索引或日志。
- 为 Agent 生成本地文件时，裁剪必须在写盘之前完成。
- 拒绝原因要分清：身份不可信、动作无权、范围不允许、来源拒绝。

## 恢复

首次部署建立初始管理身份是显式初始化。启动只恢复已有的身份绑定、授权和撤销；权限记录丢失不能
被当成空部署而重新发管理员权限。

## 代码位置

身份绑定在 `identity/`；仓与 Dataset 的授权规则在 `snapshot/access/`，强制检查在 `snapshot/service/`
与 `server/`；认证接入（local、Taihu、Gitea 登录）在 `server/` 与 `home/` 的装配中。

## 进度

| 进度 | 内容 |
|---|---|
| 已有 | 统一用户名、local/Taihu/Gitea 登录、保存登录、仓与 Dataset 分开授权、来源发布许可、撤权后旧依据失效、默认可读声明 |
| 近期 | 服务端拒绝空身份：本地直连不带身份时目前会被放行 |
| 未到 | 用户名能否改名或回收；首次准入是资格、邀请还是审批；维护者可转授的上限；按仓可见性进一步裁剪库存 |
