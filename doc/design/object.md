# 对象

对象层把仓里的文件解释成业务对象：有稳定身份，可以分方面维护，用 Schema 约束结构，所有发布都
经过 Writer。字节和版本仍归 [Snapshot](snapshot.md)。

## 目标

- 用户用的是对象，找的是 Dataset。对象身份只回答“这是哪个东西”，不回答“它存在哪个仓”。
- 文件改名、移动，仓拆分、合并、迁移，已有引用都不变。
- 一个对象可以拆成多个方面分别维护，这些方面可以来自不同团队的仓，读取时按请求范围组装。
- 领域模型由接入方用 Schema 定义，平台源码里没有业务类型名单。
- 发布只有 Writer 一个入口：检查 Schema、身份、来源和基于哪一版修改，通过后才形成新版本。
- 读取在固定版本上进行，只解释请求允许的范围，每个方面都说得清来自哪个仓、哪一版。

## 身份：URN 不感知 repo

这是对象模型的核心决定。

对象 URN 只由 `object_id` 构成，不带仓。`object_id` 必须带命名空间，形如 `<namespace>/<name>`：

| 对象 | object_id | 说明 |
|---|---|---|
| 订单服务 | `trade/order-service` | 命名空间 `trade` 是交易域 |
| 订单 ODS 表 | `dw.ods/orders` | 命名空间 `dw.ods` 是数仓 ODS 层 |
| 订单业务实体 | `trade/order` | 和上面那张表是两个对象，用关系连接 |

命名空间是语义上的归属，不是仓。很多时候它和仓名、团队名重复，这个重复是有意接受的：

- 一个仓可以放多个命名空间，一个命名空间也可以从一个仓搬到另一个仓，引用都不断。
- 只看 ID 就能读懂对象属于哪个域，不需要查一张登记表。
- 类型不写进 ID，由 Schema 决定。类型调整不改变身份。

可以类比 Java：类的全名是 `com.trade.order.OrderService`，里面没有 jar 名。jar 是打包和发布的
单位，相当于仓；包名是命名空间。包名常和 jar 名重复，但换 jar、拆 jar 不影响引用。

repo 没有消失，只是挪了位置：

- 每个方面在一个仓里发布，写入、条件提交、回退和权限都按仓进行。
- 每次读取的依据里记录每个方面来自哪个仓、哪个 commit。生产需要的可追溯性靠依据，不靠 URN。

## 冲突

系统负责 ID 不冲突，靠两件事：

1. 命名空间让无意的撞名很少发生。
2. 真撞上时，在相遇的地方明确报出来，不悄悄合并，也不悄悄选一个。

同一个 `object_id` 出现在多个仓里是允许的，系统视为同一个对象的不同方面。唯一要拒绝的是：
在同一个范围里，同一个对象的同一个方面来自两个仓。

| 发生在哪里 | 怎样处理 |
|---|---|
| 同一个仓内 | Writer 提交时拒绝 |
|Dataset 发布 | 拒绝发布，指出冲突的对象、方面和两个来源仓 |
| 跨仓发现与读取 | 结果里标为冲突，列出两个来源，不返回任何一份作为“正确值” |

两个团队用同一个 ID 说的是两样东西（比如都叫 `orders`，一个是表，一个是业务概念），系统发现
不了，只能靠命名空间约定和治理来避免。

命名空间认领暂不做。冲突真的多起来，再加一个可选的认领机制。

## 一个对象，还是相关的两个对象

这件事由建模者决定，系统既不鼓励也不约束。两种写法都成立：

- 同一个对象的多个方面。订单服务 `trade/order-service` 的 `definition` 和 `runbook` 归交易团队，
  `monitoring` 方面由 SRE 团队在自己的仓里发布，三个方面用同一个 ID。
- 相关的两个对象。物理表 `dw.ods/orders` 归数仓团队，业务实体 `trade/order` 归交易团队，
  两者用关系“订单 落在 表”连接。

判断时可以参考三点：两者是否一一对应，生命周期是否一致，负责人关心的是否同一件事。三点都是，
多半是同一个对象；有一点不是，多半是两个对象。表可以重建、分层、分表，业务概念不随之改变，
所以表和业务实体通常是两个对象。

给别人对象的某一部分补充说明（比如给某一列写业务含义），可以写成同一个对象的一个方面，也可以
写成独立对象，用关系指向 `dw.ods/orders#/columns/amount`。

## 模型

| 单元 | 说明 |
|---|---|
| Entity | 有稳定身份的业务对象。可以整体保存，也可以拆成方面；同一仓里同一对象不同时保存整体正文和方面正文 |
| Aspect | 对象的一个方面，有自己的 Schema，可单独修改。一个对象的不同方面可以在不同仓 |
| Member | 方面里一组带键的成员，可单独寻址和更新；普通字段留在方面内即可 |
| Relation | 对象之间有业务含义的关联，有自己的身份和版本。端点按 ID 引用，不关心对方在哪个仓；写关系只修改关系所在的仓 |

每个单元是一个文件，文件开头的头部写身份和 `schema_ref`，后面是正文。身份写在内容里，而不是
另存一张地址映射，因为身份和内容随同一次提交一起变化。

## 对象引用

读写都只用一种地址：对象 URN 加上定位到哪一部分（整个对象、某个方面、某个成员、某个字段）。
URN 在请求所在的范围里解析：某个 Dataset，或部署中调用者可读的仓。精确的历史读取用回执和依据
里的版本向量，不靠在 URN 里塞仓和 commit。

写入时由请求指定写哪个仓。同一个 URN 加定位符，在不同仓里指向的是同一对象的不同方面。

## Schema

- Schema 本身也是对象，随仓发布。系统仓发布基础 Schema，接入方发布领域 Schema。
- Schema 同时描述值的结构和字段的访问声明（可搜索、可过滤、可排序、来自外部系统）。这是索引和
  外部取值声明唯一的写法，插件按它生效，见[插件](plugins.md)。
- Schema 按 ID 引用，可以引用别的仓发布的 Schema，并固定版本。业务团队不需要在自己的仓里复制
  一份数仓团队的 Schema。
- 兼容的修改要继续能解释已有实例，不能只验证新写入的那一个。删除被引用的 Schema 会被拒绝。
- 不兼容的修改怎样迁移，还没有定。

## Writer

- 一次提交只改一个仓。不采集外部数据，不在发布中运行模型，不做跨仓事务。
- 提交带着基础版本，基础已变就拒绝，由提交方重新读取、核对后再提交。
- 网络中断不等于失败。重试用同一个命令身份，得到原来的结果，不重复写入。
- 修正错误用新提交或显式回退提交，保留历史。恢复历史内容也是一次新的发布。
- 仓的终点是归档，不提供领域级的删除。对象只要还有一个方面存在就存在。
- 需要评审的修改先写到工作分支，校验后由 Writer 条件合并（见[治理](governance.md)）；工作分支不是第二个写入口。
- 直接改仓、不经过 Writer 的提交，也应在成为正式发布前通过同样的检查（未到）。

## 读取

- Reader 在固定版本上读取并组装，不负责找候选，找候选是[发现](discovery.md)的事。
- 组装一个对象时，在请求范围内收集同一 ID 的各个方面，每个方面带着自己的仓和版本。没有跨仓的
  全局时刻，对象的版本就是各方面版本的组合。
- 调用者无权读的仓里的方面，标为无权，不假装不存在。
- Dataset 只选了部分文件时，缺的方面就是这个范围里没有，不从源仓补齐。
- 消费面没有“列出全部对象”。全量遍历只属于重建、迁移、导出、一致性检查这类维护入口。
- Schema 等依赖缺失时，报告解释受限，不反过来认定文件组合无效。
- 字段声明来自外部系统时，由 [LiveAccess](liveaccess.md) 取值，同时保留内容版本和观察依据。

## 来源与历史

历史回答“当时保存了什么”，来源回答“这份内容依据什么产生”，两者不能互相代替。由脚本或模型推导
的内容，要固定输入版本和算法信息，否则无法复现。组装多个方面或多个对象时也要保留各自来源。

## 系统仓

系统自描述仓 `kr://kc/system` 发布 KC 自己的模型、命令入口、运行机制、能力说明、使用指南和基础
Schema，对象都在命名空间 `kc` 下。它和 `kc help` 分层说明同一件事：系统仓讲用途和选择，叶子命令
的 help 持有精确调用方式，两者由自动检查约束一致，见 [Affordance](affordance.md)。

- 已认证用户默认可读；运行时 Writer 不能写系统仓，只有平台版本发布能更新它。
- 部署时把出版物发布到明确绑定的实际仓，启动只核对，不在启动时补发布，也不用内置仓代替。
- 校验 Schema 的 Meta Schema 内置在服务里，不用仓里的内容校验它自己。

## 待确认

- 多环境：staging 和生产里的同一个对象，按部署或 ref 区分，不按仓区分。同一部署内用两个仓装
  两套环境会变成方面冲突。
- Fork：换一个新 ID，还是成为原对象的一个分支版本。

## 用例

每条用例是一项目标，场景树按 `object#U<编号>` 关联验证入口和缺口，见
[测试](../engineering/testing.md)。用例写完不代表实现通过。

### U1：首次发布领域对象

接入方读取系统 Schema，发布自己的 Schema 与实例，再按回执版本读回身份、内容和来源。
可以一次发布互相匹配的 Schema 与实例；Schema 不合法时整批不生效，不留下半份内容。

### U2：修改一个方面

维护者只修改某对象的说明方面。其余方面保持原值，身份不变；使用者仍能选择读完整对象或
这个方面。文件改名不会被解释成删除旧对象再创建无关对象。

### U3：Schema 演进影响已有实例

接入方修改一个被多份实例引用的 Schema。系统说明是否兼容，并对受影响实例保持一致校验。
不能只因 Schema 自身格式正确就接受破坏已有实例的发布；没有选定的迁移方式不能伪装可用。

### U4：评审之后目标仓又被修改

维护者评审了工作分支上的某个 commit 后，分支又被写入，或另一个人推进了目标仓。合并不能发布
未经评审的组合：分支移动或目标不再是快进基点时拒绝，需要在新的基点上重新评审；已发布版本不因失败被改写。

### U5：提交成功但响应丢失

接入方用原命令重试，得到同一个已接受结果；同一命令身份不能换一份内容。
无法确认是否已提交时，明确说明待恢复，不重复发布，也不制造假失败。

### U6：建立跨仓关系

作者在自己有写权的仓发布关系，端点指向另一个仓里的对象。发布不写端点所在的仓、不扩大读权；
读取关系时保留来源，目标对象是否存在、是否可读由当前范围判断。

### U7：从只包含部分文件的 Dataset 读取对象

Dataset 已经交付文件，调用方再按对象读取。Reader 只组装范围内的方面，缺少 Schema 或其他依赖时
明确报告；不能为了得到完整对象而补读范围外的文件，也不能因为交付路径变了就改变对象身份。

### U8：Agent 首次理解与使用系统

Agent 读取系统仓导读，按目标找到模型、入口或机制说明，再按能力查看同一版本的 `kc help`。
它能区分能力含义、部署是否就绪和当前权限；没有索引时仍可精确读取导读和已知对象。
出版物缺失或与二进制版本不一致时明确拒绝，不能带着另一版本的说明继续运行。

### U9：只知道 kc help 就能认识对象模型

没有登录、Server 配置或系统仓坐标，只读根帮助就能理解核心概念、它们的联系、基础能力和一个例子；
不发业务请求，不创建文件。再沿真实的叶子帮助完成一次读、改、删。

### U10：同一引用用于读写

读取、写入、删除共用对象 URN 加定位符。URN 不含仓：路径迁移、仓拆分合并都不改身份；同一 ID
出现在多个仓时是同一对象的不同方面，同一范围内同一方面来自两个仓时明确报冲突。版本和范围冲突
明确拒绝；分列寻址一律拒绝；不能把定位符误当存储路径。

### U11：读取准确范围并固定依据

完整对象、方面、成员、深字段与数组位置返回准确值；空定位符、空键、转义、合法的 null 与缺失
分别处理。读取过程中 HEAD 前进，正文、实际采用的 Schema 与来源仍保持本次的固定依据。
只读取所选范围必需的单元，不能先读无关内容再裁剪。

### U12：读取后依据完整更新维护内容

读取直接给出固定版本和所属维护单元的摘要，调用方不必再解析就能完整更新。
深字段值没变、但所属成员的其他字段变了时，摘要必须改变，旧依据的更新必须拒绝。

### U13：独立创建、替换和删除维护内容

分别验证整体值、完整方面和成员的创建、完整替换与删除。省略的旧字段不会被合并保留，
未选中的单元与其他对象保持不变；根删除覆盖所有维护单元，旧版本仍可读。

### U14：最终表示冲突整批拒绝

没有 Schema 时也拒绝整体值与方面、完整方面与成员的混用。批内顺序不能绕过检查；
显式移除旧表示再创建新表示可以成立。拒绝后版本、原内容和已接受回执都不变。

### U15：Schema 可浏览、采用且不能绕过

在固定范围内浏览和描述 Schema，名单、结构和约束准确。普通内容可以不采用 Schema；
采用后，更新继承约束。同批 Schema 与实例一起校验，演进时检查已有引用者，仍被引用时不能删除。

### U16：Dataset 消费不扩大授权与材料

消费沿已接受发布版的来源 commit，源 HEAD 推进不会偷换版本。部分对象和缺失的说明材料不能
补读源仓或冒充完整；额外的来源版本冲突时拒绝。撤权后旧引用也拒绝，Dataset 读权不产生源仓写权。

### U17：并发、失败与重试不损坏写入

单仓批次原子生效，任一前置条件失败都不留下部分结果；仓的条件提交与单元摘要各自验证。
同命令同内容得到原结果，换内容拒绝；不确定的结果不自动重做。写到工作分支只推进该分支，
后续 Hook 投递失败不撤销已接受的提交或合并。

### U18：历史、差异与来源可独立复核

对象历史按身份归集，删除修订和分页准确；两个固定版本的内容对照不偷换成目录 diff。来源只反映
本对象已保存的依据，不递归访问 sourceRefs，不把 Git 作者或结构合规当作外部事实的证明。

### U19：基础读写不需要插件

没有装发现、外部取值或治理插件时，对象和 Schema 仍可读写；外部来源离线也不触发外呼，
不阻断基础采用。插件专属的说明与执行留在插件所属模块。

### U20：实际结构与基础合同一致

Reader 只提供只读能力，写入只经 Writer；类型、组装和说明各只有一份。真实的 import、公开入口
和调用方符合所有权与依赖方向，不能用目录存在或同名转发壳代替实现归属。
