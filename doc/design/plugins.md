# 插件

插件是 KC 里最像 AOP 的部分：搜索、外部取值这类能力横切大量对象，不应该写进每个对象，
也不应该由每个团队自己搭。区别在于，被织入的对象不是由程序调用，而是由 Agent 发现和访问。

## 和 AOP 的对应

| AOP 概念 | KC 里是什么 | 例子 |
|---|---|---|
| 切面（Aspect） | 插件本身 | 声明式索引、LiveAccess |
| 切点（Pointcut） | Schema 里的声明：哪个类型、哪个字段 | 服务 Schema 的 `name` 字段声明可搜索；`health` 字段声明来自监控系统 |
| 连接点（Join point） | 插件能参与的固定过程点 | 发布之后、查询时、读取时、读说明时 |
| 通知（Advice） | 插件在连接点做的事 | 发布后更新索引；读取时取回外部值 |
| 织入（Weaving） | 服务装了插件，对象用了带声明的 Schema，就自动生效 | 类似 Spring Boot 的自动配置 |

注意一个名词冲突：KC 的 Aspect 指对象的一个“方面”（如订单服务的值班说明），和 AOP 的切面
不是一回事。本套文档里 AOP 的 Aspect 一律叫“切面”或直接叫“插件”，Aspect 只指对象的方面。

连接点是固定的几个，不提供任意的 before/after 改写点。每个连接点都要有明确的调用者、输入和
结果怎样采用：

| 连接点 | 谁调用 | 插件拿到什么 | 结果怎样采用 |
|---|---|---|---|
| 发布之后 | 后台维护，在 Writer 提交成功后 | 来源仓、新旧版本、变化范围 | 插件更新自己的派生状态；失败不撤销提交 |
| 查询 | 发现服务 | 固定范围和版本、查询条件、预算 | 返回候选，由对象层按同一版本回读 |
| 读取 | 对象读取 | 固定声明、调用者身份、来源 | 每个值单独采用，失败只影响该值 |
| 说明 | `kc plugin <名称> help` 与访问概览 | 插件名称 | 返回用途、适用条件和用法，不执行业务 |

## 插件定义在什么上

插件声明在类型上，不在仓上，也不在 Dataset 上。

这是[对象](object.md)“URN 不感知 repo”的直接推论。对象不属于某一个仓，一个对象的不同方面可以
来自不同团队的仓，同一类型的对象分散在很多仓。切点如果落在仓上，就相当于在 Spring 里按 jar 名
定切点：一个类型的对象一半被织入、一半没有，同一个对象的不同方面行为不一致，最后只能让 Dataset
去汇总各仓的配置，Dataset 因此承担了不该承担的职责。

切点落在类型上以后，三件事各归其主：

| 问题 | 谁决定 | 写在哪里 |
|---|---|---|
| 这类对象的哪些字段可搜索、哪些来自外部系统 | 方面 Schema 的所有者 | Schema 的 `access` 与 Binding 声明，就像 `@Indexed` 写在类上 |
| 插件运行所需的资源和凭证 | 发布这个方面的仓的所有者 | 仓的配置。比如 `dw.ods/orders` 的 `rowCount` 用的 metastore 凭证绑在数仓团队的仓上 |
| 这次在哪些对象里找 | 调用者，在获准范围内 | 请求的范围：某个 Dataset，或调用者可读的全部仓 |

以订单表为例：数仓团队的表结构 Schema 声明列名可搜索、`rowCount` 来自 metastore。服务装了声明式
索引和 LiveAccess，所有用这个 Schema 的表就自动可搜、可取实时行数，不管它们在哪个仓。业务团队
为 `dw.ods/orders` 发布的 `glossary` 方面，按自己的 Schema 声明生效，两边各管各的，不冲突。

## 规则

- 默认生效，可以关闭。仓的所有者可以对自己仓里的方面关闭某个插件，承担索引成本和失败影响的
  还是数据所有者。关闭的仓在结果里单独列出，不当作没有匹配。
- 按类型发现。可以直接问“所有服务类型里，名称或用途匹配‘订单’的”，不需要先知道它们在哪些仓。
  结果里每个命中带着来源仓和版本；未就绪或已关闭的范围单独列出。
- 同一对象的多个方面各自被索引，查询时按对象 ID 合并。方面冲突按[对象](object.md#冲突)的规则
  报出。
- 插件不是内容权威，不发权，不改写已发布内容；声明了但实现缺失时明确失败，不回退到隐藏的全局
  实现；未装插件不影响基础读写；一次请求内版本固定；每个仓的权限照常检查。
- 首批假设插件之间没有冲突，不设计优先级和覆盖。

## 代价

- 按类型跨仓发现需要先有“调用者可读的全部仓”这个范围，权限求值要能高效给出它。
- 默认生效让索引成本随对象总量增长，需要按插件设定容量预期。
- Schema 跨仓引用后，一个 Schema 的修改会影响多个仓的索引，Schema 版本演进要和插件维护一起考虑。

## 待确认

1. 按类型发现的范围是否默认为“调用者可读的全部仓”，还是必须显式给出范围。
2. 关闭插件的粒度：整个仓，还是仓内的某个类型。

## 说明入口

每个插件提供自己的 Affordance，统一从 `kc plugin <名称> help` 读取：用途、适用的声明、例子和
已有的命令入口。访问一个 Dataset 或仓时，系统顺带给出这个范围实际用到的插件和帮助入口，调用者
不用先列插件。说明不证明插件已就绪，也不证明调用者有权使用。

## 插件内部的处理器合同

对外只有“插件”一个概念，没有独立的 Interface。插件内部如果需要“一组对象按同一合同交给同一处理器”
的机制，例如 LiveAccess 按取值协议找处理器、校验输入和结果，这套合同、登记与分派属于插件的实现，
放在插件自己的目录里，不作为顶层能力，也不出现在帮助和概念里。

“对象有一组可被调用的方法”属于 wield，当前不做；以后做 wield 时重新设计，不沿用现在的处理器合同。

## 代码位置

| 目录 | 负责 |
|---|---|
| `discovery/adoption/` | 插件作用域和说明事实，不依赖具体插件 |
| `discovery/plugin/` | 声明式索引类插件的登记与来源选择 |
| `declarativeindex/plugin/` | 声明式索引插件入口 |
| `liveaccess/plugin/` | LiveAccess 插件入口 |
| `interfaces/` | 现为顶层；近期收进 LiveAccess 作为其内部的处理器合同 |
| `home/` | 按配置加载插件入口，连接系统依赖，统一启停 |

## 进度

| 进度 | 内容 |
|---|---|
| 已有 | 插件登记、按仓选择、多实例、说明读取与访问概览的接线 |
| 近期 | 插件按 Schema 声明生效、仓可关闭；Dataset 不参与插件配置；两个插件完成改接 |
| 近期 | `interfaces/` 降为 LiveAccess 内部机制，对外不再有 Interface 概念 |
| 近期 | 按类型跨仓发现，结果按对象 ID 合并并列出未就绪与关闭的范围 |
| 未到 | 插件之间的优先级与覆盖 |
