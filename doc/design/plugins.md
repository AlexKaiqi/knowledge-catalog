# 插件

插件是 KC 里最像 AOP 的部分：搜索、外部取值这类能力横切大量对象，不应该写进每个对象，
也不应该由每个团队自己搭。区别在于，被织入的对象不是由程序调用，而是由 Agent 发现和访问。

## 和 AOP 的对应

| AOP 概念 | KC 里是什么 | 例子 |
|---|---|---|
| 切面（Aspect） | 插件本身 | 声明式索引、LiveAccess |
| 切点（Pointcut） | 经 Writer 发布的声明：索引声明指向某个类型的字段，选进 Dataset 生效；取值来源写在某个方面或成员上 | 运维组为 `oncall` 选进的索引声明让服务 Schema 的 `name` 可搜索；订单服务的 `health` 成员声明来自监控系统 |
| 连接点（Join point） | 插件能参与的固定过程点 | 发布之后、查询时、读取时、读说明时 |
| 通知（Advice） | 插件在连接点做的事 | 发布后更新索引；读取时取回外部值 |
| 织入（Weaving） | 部署装了插件，请求范围里有它认识的声明，就自动解释；没装时声明只是普通的方面与成员 | 类似 Spring Boot 的自动配置 |

注意一个名词冲突：KC 的 Aspect 指对象的一个“方面”（如订单服务的值班说明），和 AOP 的切面
不是一回事。本套文档里 AOP 的 Aspect 一律叫“切面”或直接叫“插件”，Aspect 只指对象的方面。

连接点是固定的几个，不提供任意的 before/after 改写点。每个连接点都要有明确的调用者、输入和
结果怎样采用：

| 连接点 | 谁调用 | 插件拿到什么 | 结果怎样采用 |
|---|---|---|---|
| 发布之后 | 后台维护，在 Writer 提交成功后 | 来源仓、新旧版本、变化范围 | 插件更新自己的派生状态；失败不撤销提交 |
| 查询 | 发现服务 | 固定范围和版本、查询条件、预算 | 返回候选，由对象层按同一版本回读 |
| 读取 | 对象读取 | 固定声明、调用者身份、来源 | 每个值单独采用，失败只影响该值 |
| 说明 | `kc plugin <名称> help` 与访问概览 | 插件名称 | 返回用途、适用条件和用法，不执行业务 |

## 声明写在哪里

声明是对象，由业务维护，经 Writer 发布。Schema 只描述结构，不含插件声明；插件内部配置
只管资源，不含字段语义。系统负责公开能配什么、按声明执行；声明由谁、借助什么工具写出来，不归系统管。

| 问题 | 谁决定 | 写在哪里 |
|---|---|---|
| 怎么检索 | Dataset 的维护者，在实例的能力清单之内；使用记录作为数据供他参考 | 维护者仓里的索引声明，选进 Dataset 才生效：一个 `index` 方面，每个成员写一个检索字段的输入与构建方式，见[发现](discovery.md#索引声明) |
| 哪些值来自外部系统 | 方面或成员的维护者 | 单元上的取值来源，引用一份取值描述，见 [LiveAccess](liveaccess.md#声明) |
| 外部系统怎么访问 | 外部系统的团队 | 取值描述对象：`origin`、取值协议和操作 |
| 插件装哪些、清单对应哪个实例、资源和凭证 | 部署方 | 部署配置：装了哪些插件、能力清单名到实例的对应、资源与凭证可信范围 |
| 这次在哪些对象里找 | 调用者，在获准范围内 | 搜索的范围是一个 Dataset；已知身份的读取在 Dataset 或调用者可读的仓里解析 |

为什么不写进 Schema：Schema 的所有者不知道每个使用方怎么查；同一类型在不同仓里的取值来源可能
不同；把用途写进类型，会逼着业务为不同用法复制 Schema。当前阶段怎么检索依赖业务先验，由使用这份
交付的人写更合适。

为什么索引声明跟 Dataset 走、而不留在来源仓：交付给使用者的是 Dataset，检索空间也应是它。拼接来自
不同团队方面的检索字段，只在组合好的范围里有意义；一个 Dataset 一套打分，不用合并各仓的分数；谁使用、
谁声明、谁承担成本也落在同一个人身上。

为什么不放在插件内部配置：插件配置不经过 Writer，没有版本，固定的 Dataset 无法随来源一起固定；
对外不可见，调用者分不清“搜不到”和“没索引”；索引丢了，“该索引什么”也一起丢了。

声明虽然是文件，切点仍然是类型或单元：索引声明指向的是 Schema 字段，覆盖 Dataset 里采用这个 Schema
的全部对象，不是逐个文件配置。索引声明作为普通文件选进 Dataset，随发布一起固定；Dataset 不另设
插件配置。

以订单表为例：`dw.ods/orders` 的 `stats` 方面声明取值来源，引用 metastore 团队发布的取值描述。
分析组发布 `sales-analysis` Dataset，选入数仓团队的表、业务团队的 `glossary` 方面和自己仓里的一份
索引声明，把列名和术语释义拼成一个语义检索字段。另一个 Dataset 选入同样的表，可以用完全不同的
声明，两边各管各的，不冲突。

## 规则

- 插件是解释器，不绑定 Dataset 或仓。部署装了插件，它按形状认领声明：采用 `kc/index-declaration`
  Schema 的方面归声明式索引，单元上的 `valueSource` 归 LiveAccess。认领看 Schema，不看方面名，业务自己
  叫 `index` 的方面仍是普通内容。声明在哪里生效由范围决定：索引声明选进哪个 Dataset 就在哪个
  Dataset 生效，取值来源在读到该单元时生效。没有声明的不被索引，也不外呼。
- 没装插件时，声明照常读写、照常按 Schema 校验，只是不被解释：搜索明确报没有检索能力，不当作零命中；
  外部单元逐个报没有取值能力，其他值不受影响。不回退到隐藏的全局实现。
- 声明写明所依据的能力清单名，部署把清单名对应到唯一实例，所以声明本身就确定由谁解释，不再另外
  绑定。LiveAccess 以取值描述的 `runtime` 与 `protocol` 作为清单名。清单名没有对应实例时，相关成员或
  单元明确报没有能力；同一清单名对应多个实例，或部署配置里还写着按仓选择插件，部署拒绝启动。
- 能配什么由实例公开。每个实例给出带版本的能力清单，声明只能在清单之内写；清单外的写法明确报
  不支持，不静默忽略。
- 搜索在 Dataset 里。跨仓、跨类型的发现靠把来源组合进 Dataset，不提供“调用者可读的全部仓”这种
  临时范围。结果里每个命中带着来源仓和版本；未声明、不支持或未就绪的部分单独说明。
- 同一对象的多个方面各自被索引，查询时按对象 ID 合并。方面冲突按[对象](object.md#冲突)的规则
  报出。
- 插件不是内容权威，不发权，不改写已发布内容，不写任何分支；使用记录只作为数据公开；未装插件不
  影响基础读写；一次请求内版本固定；权限照常检查。
- 首批假设插件之间没有冲突，不设计优先级和覆盖。

## 代价

- 调用者要先知道用哪个 Dataset。库存按消费权限列出可用的 Dataset 和用途，承接这一步；需要全局
  搜索时，显式维护一个大的 Dataset。
- 多个 Dataset 引用同一来源时，索引会重复建。实现可以按“来源提交 + 构建配置摘要”复用分段，只是优化。
- 索引成本随声明数量和对象总量增长，需要按实例设定容量预期；使用记录供维护者发现不值得保留的声明。
- 索引声明通常指向别的仓发布的 Schema。Schema 删掉字段时，相关成员在下一次维护中标为失效，需要
  Dataset 的维护者跟进。

## 范围与关闭

1. 搜索的范围是一个 Dataset；不提供不带 Dataset 的搜索。
2. 关闭靠撤下声明或在部署里卸载插件，不另设按 Dataset、仓或类型的开关；细粒度靠声明本身。

## 说明入口

每个插件提供自己的 Affordance，统一从 `kc plugin <名称> help` 读取：用途、声明写法、例子和
已有的命令入口。插件实例的能力不同时，按实例公开带版本的能力清单，并提供试运行校验。访问一个
Dataset 或仓时，系统顺带给出这个范围里的声明由哪些插件实例解释、清单版本和帮助入口，调用者不用先列
插件。说明不证明插件已就绪，也不证明调用者有权使用。

## 插件内部的处理器合同

对外只有“插件”一个概念，没有独立的 Interface。插件内部如果需要“一组对象按同一合同交给同一处理器”
的机制，例如 LiveAccess 按取值协议找处理器、校验输入和结果，这套合同、登记与分派属于插件的实现，
放在插件自己的目录里，不作为顶层能力，也不出现在帮助和概念里。

“对象有一组可被调用的方法”属于 wield，当前不做；以后做 wield 时重新设计，不沿用现在的处理器合同。

## 代码位置

| 目录 | 负责 |
|---|---|
| `discovery/adoption/` | 插件作用域和说明事实，不依赖具体插件 |
| `discovery/plugin/` | 声明式索引类插件的登记与来源选择 |
| `declarativeindex/plugin/` | 声明式索引插件入口 |
| `liveaccess/plugin/` | LiveAccess 插件入口 |
| `liveaccess/handler/`、`liveaccess/dispatch/` | LiveAccess 内部的处理器合同与调用任务，不对外暴露 |
| `home/` | 按配置加载插件入口，连接系统依赖，统一启停 |

## 进度

| 进度 | 内容 |
|---|---|
| 已有 | 插件登记、多实例、说明读取与访问概览的接线；当前按仓选择实例，待移除 |
| 已有 | 处理器合同收进 `liveaccess/handler/` 与 `liveaccess/dispatch/`，对外不再有 Interface 概念，部署不能注入额外处理器 |
| 近期 | 声明移出 Schema：索引声明成为 `index` 方面并选进 Dataset 生效，取值来源只写在方面或成员上并引用取值描述 |
| 近期 | 插件只作解释器：去掉按仓选择实例，按声明形状认领、按清单名对应实例；实例公开能力清单与试运行校验；去掉按仓与跨仓按类型搜索 |
| 未到 | 插件之间的优先级与覆盖 |
