# Snapshot：仓与版本

Snapshot 是多团队协作的底座：每个团队有自己的仓，每次修改形成不可变版本，并发修改互不覆盖。
它只管文件和版本，不认识对象、Schema 或搜索。

## 目标

- 每个团队独立维护自己的仓，仓是维护权限和发布节奏的边界。
- 每次提交形成不可变版本，历史可以按版本复核。
- 并发提交互不覆盖：提交时必须说明基于哪一版，基础版本已变就拒绝，由提交方重新读取后再提交。
- 一套服务只有一个登记空间，登记了哪些仓、发布了哪些 Dataset 都保存在独立的 Snapshot 里，重启后恢复。
- 生产存储是 lakeFS，大文件和大量文件由 lakeFS 和对象存储承载。

## 合同

| 能力 | 说明 |
|---|---|
| 读 | 按路径读取文件字节、列目录、读某个版本的树 |
| 版本 | 不可变的 commit、可移动的 ref，默认 ref 是 `snapshot.DefaultRef` |
| 条件提交 | 带期望的旧版本提交，不一致就拒绝 |
| 合并与归档 | 支持合并分支；仓的终点是归档，保留历史与身份 |
| 原生元数据 | 仓可以带可选的自定义键值元数据，由存储本身保存，不需要对象层解释 |

存储合同是 `snapshot.Store`。它不认识 `object_id`、Aspect、Schema、Binding 或检索；
这些解释都在对象层。

## 为什么 Snapshot 保持简单

- 身份写在内容里，随同一次提交原子演化。路径索引可以随时重建，不需要第四份需要单独加锁的状态。
- 存储层不解释对象，才能让纯文件交付在没有对象层的环境里独立成立。
- 不做跨仓事务。多个仓的修改各自提交，需要同时满足的约束靠 Dataset 固定一组版本，而不是伪造一次全局提交。

## 登记、供给与连接

供给新仓、连接已有仓、登记到服务的登记空间、授权是四件不同的事，恢复时不能用一个成功推导其它也成功。

- 托管仓：用户按名申请，系统分配存储空间、创建仓、保存绑定、登记，并按策略授予创建者权限。
- 自有仓：用户连接自己的 lakeFS，系统校验身份和可用性后再登记，凭证可以轮换。
- 登记失败不留下半个登记；跨介质失败按已完成的阶段恢复，不覆盖已有仓、不重复发权。
- 来源暂时离线和登记记录丢失要区分，不能在恢复时自动收养同名来源或重新建仓。

## 恢复

| 状态 | 要求 |
|---|---|
| 仓的历史、登记与 Dataset 发布记录 | 恢复原权威，不能从缓存猜出一份新历史 |
| 登记文件全部缺失 | 视为损坏，不能因为当前为空就重新初始化 |
| 结果未知的提交 | 按实际权威恢复，不笼统认定失败 |

## 入口

存储模块自带完整入口，不反向依赖整个应用：`snapshot/service` 是文件 HTTP，`snapshot/client`
是 SDK，`snapshot/cli` 是命令行，`snapshot/console` 是 lakeFS 控制台与 Dataset 管理页面。
lakeFS 实现在 `snapshot/internal/`，只能经公开构造和能力合同接入。

已知仓、固定版本和文件路径时可以直接读取单文件，不以发布 Dataset 为前提。Agent 从对象正文
读到普通文件地址后，按业务说明选择资源自己的坐标，再调用同一文件入口；存储层不识别图片或
自动执行正文中的地址。对象说明与资源可以属于不同仓、不同版本，读取仍检查资源的当前权限。
