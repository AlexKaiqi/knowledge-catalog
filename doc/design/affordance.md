# Affordance

Agent 要先读懂对象和系统能做什么，才能 discover 和 access。Affordance 是“能做什么、需要什么条件、
会有什么效果”的说明。KC 自己按同一套规范实现，命令行就是系统的 Affordance。

## 目标

- Agent 只从 `kc help` 出发，就能认识对象模型，并完成一条真实任务。
- 对象和系统用同一种方式说明自己。
- 多个对象共有的能力由插件提供，维护者只需在仓里发布声明并提供数据，Schema 只描述结构，见[插件](plugins.md)。
- 说明、可解释、处理器支持、当前可用、本次获权分别成立，说明不能冒充其它几项。

## 对象的 Affordance

可供性作为普通对象关联到对象的明确实现和操作，提供任务、适用条件、效果和限制等选择信息。

- 不能超出对象的 Schema、仓里的插件声明和已装插件实际提供的能力。
- 不是执行守卫，不授予权限，不是第二套分派系统。
- 发布照常经过 Writer。

对象正文给出普通文件地址时，系统说明应能引导 Agent 找到通用文件读取入口，取得资源自己的
仓、固定版本和路径后下载。说明对象与资源可以采用不同版本；对象读取不自动下载或授予文件权限。
文件保存与读取边界见 [Snapshot](snapshot.md)。

## 系统的 Affordance：命令行

| 层级 | 说明什么 |
|---|---|
| `kc help` | 日常能做什么、最短路径，以及对象模型（object_id、Aspect、Member、地址、Relation）和基础访问例子 |
| 功能组帮助 | 这组有哪些动作，例如 `kc help consume`、`write`、`compose` |
| 叶子命令帮助 | 当前动作的参数和取值方法，是精确调用合同的唯一来源 |
| `kc plugin <名称> help` | 插件的用途、适用声明、例子与命令入口 |
| `kr://kc/system` | 用途、选择、机制和使用指南，作为对象发布；调用入口与 help 同源，由自动检查约束漂移 |

一次值班任务的最短路径：交易团队发布对象并打包成 Dataset，值班同事发现、读取并取当前状态。
示例里的命令由测试按命令注册表检查，写错路径或参数会失败。

```bash
kc login
kc writer commit --command-id oncall-001 --repo kr://acme/trade --dir ./drafts
kc dataset define oncall --revision 1 --source kr://acme/trade
kc grant add --dataset oncall --principal teammate --action file.read
kc show
kc help consume
kc search --dataset oncall --query 订单
kc access --dataset oncall --object trade/order-service --aspect health
kc provenance --dataset oncall --object trade/order-service
```

## 命令行的设计规则

- 按用户任务组织命令，不按协议分层或代码目录。主要路径：连接服务、发现并读取、向一个仓发布、接入来源并分享。
- 一条命令只表达它承诺的副作用。供给仓、登记、发布、发布 Dataset、发权分别可观察、可恢复，“接入”不能暗含授权。
- 上下文和本次目标分开。服务地址和身份是已保存的上下文；本次的仓、Dataset、对象、写入命令身份必须明确。
- 写入命令身份由用户提供，响应丢失后用同一身份查明结果，不偷偷换新身份重试。
- 预览、校验、发布、Dataset 采用、索引就绪是不同状态，输出要让人分得清。
- 失败要说清是哪一种：用法错误、身份无效、无权、不存在、未就绪、版本冲突、暂时不可用。没有权限时说明缺什么、去哪申请，不自动发权。
- 没有命中是正常答案，和“对象存在但读不出来”是不同的结果。
- 命令行和 HTTP 调用同一个应用执行器，结果语义、权限和副作用一致。
- Agent 不需要专用工具，直接调用同一套命令；文件经下载或只读挂载成为普通路径。

## 用例

场景树按 `affordance#U<编号>` 关联验证入口和缺口，见 [测试](../engineering/testing.md)。

### U1：首次进入系统并读到一个对象

用户从帮助了解入口，连接获准的服务，发现来源和 Schema，再在明确范围里搜索、读取。
不需要知道存储地址或索引代际，也不会把"能发现"误当成"有正文读权"。

### U2：接入一个已有仓并分享 Dataset

用户能分清连接、登记、选择文件、发布和授权各自完成了什么。中途停下时已有结果清楚，
继续操作不会重复建仓，也不会隐式扩权。

### U3：提交目录后网络中断

用户用原命令身份重试，得到同一个已接受结果或明确的恢复状态；不需要换身份才能继续，
也不会把后置 Hook 失败说成没有提交。

### U4：命中对象但没有正文读权

命令说明"能发现"和"能读取"的差别，后续读取按真实授权返回。在 Dataset 范围里，
范围外的对象根本不能借这条路被发现。

### U5：搜索未就绪或输入写错

两种失败给出不同反馈。前者不返回零命中、不现场建索引；后者显示当前叶子命令的原因和用法，
用户不用翻设计书就能改对一次输入。

### U6：脚本与人工使用同一动作

脚本得到稳定的结果与失败语义，人工得到能看懂的帮助与恢复指引。换成 HTTP 后，授权、
固定版本和副作用保持一致，只有展示形式可以不同。

### U7：声明式索引通过插件执行已有查询

选进 Dataset 的索引声明说明怎么检索，部署装了插件就自动解释；写后维护和查询用同一份声明。
使用者从实例公开的能力清单得知能配什么，用试运行校验检查声明，再沿已有入口发布、查询和读取，在
describe 和执行反馈里看懂声明、固定范围和就绪状态。系统不替使用者提出意图或生成声明，业务可以
接入自己的 Agent 完成这一步。不要求先跑新的安装命令，也不把物理引擎当成新的业务能力；授权、
同依据回读和未就绪时的失败语义不变。

### U8：从基础帮助了解适用的插件

用户离线阅读 `kc help`，理解固定读取与维护这些基础能力，找到插件说明入口。连接 Server 后，
在访问概览里看到当前范围内生效的插件、用途和帮助入口，再用 `kc plugin <名称> help` 读插件说明，
沿 search、read、access、invoke 的帮助完成使用。直接按仓消费和按 Dataset 消费得到同样的引导。
缺说明、仓关闭了插件、插件没装或没就绪要如实区分。说明过程不执行来源操作，不替换本次授权。
帮助不把"仓里有声明"说成"插件已生效"或"索引已就绪"。
