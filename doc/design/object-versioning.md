# 对象版本与读写（待重构）

对象读写需要分别回答三个问题：这次内容与上次是否相同，怎样按原依据回读，以及历史上发生过哪些
变化。仓内无关提交不应被误判为对象状态变化；看到了相同内容，也不能据此推断写入条件成立或历史没有变化。

术语见[核心概念](../concepts.md)，身份与 Unit 模型沿用[对象](object.md)，提交边界沿用
[Snapshot](snapshot.md)。本篇确定这些保证及取舍；接口与实现进度列在文末。

## 比较的状态与范围

本地状态比较以完整 Unit 为粒度，覆盖地址、保存的值和本地声明。聚合摘要可表达为：

```text
H(按 Unit 地址稳定排序的 [(地址, 值摘要, 本地声明摘要), …])
```

本地声明包括 Schema 引用和取值来源声明。Unit 构成参与比较，因为拆分变化会改变寻址与维护边界。
路径、来源仓、commit 和 provenance 不参与该摘要；因此摘要相同不代表所有持久信息相同。
Schema 或描述符的解析版本、外部观察分别保留依据：本地声明不变时，解释依赖和外部值仍可变化。

字段投影不缩小所属 Unit 的比较范围：同一 Snapshot Unit 中未返回字段的持久变化仍改变状态摘要。
部分读取只聚合所选 Unit，不为计算摘要额外读取未选单元。状态摘要用于识别值、声明和构成变化；
既有维护摘要继续服务原条件写，Snapshot 单元比较值，Binding 单元比较本地声明，不能静默更换相等关系。

本地状态摘要不充当索引成员的构建身份：摘要相同仍须核对解释依赖、观察与构建规则；摘要不同也可能
只是未参与构建的 Unit 或字段变化。成员计算产物的复用按[构建身份](index-physical.md#构建身份)判断。

比较必须同时保留三类依据：

| 依据 | 决定什么 |
|---|---|
| 对象身份、候选来源身份及逻辑选择规则 | 应比较的范围；范围标识不含 commit、Dataset 修订号或实际返回的 Unit 集合 |
| 固定来源与所需依赖坐标 | 本次采用哪一版；来源绑定也必须可核对，不能只靠同名仓识别来源 |
| 范围内的未决项 | 是否足以声称该范围完整；无权、读取失败、组成冲突和覆盖未知分别报告 |

范围标识不能由返回的 Unit 集合生成，否则新增单元就会被误当作范围改变，无法比较构成变化。
同样，固定依据须保留未贡献内容的候选来源，才能复核缺失和冲突；只保存实际贡献者不够。
摘要带算法版本，只有相同对象、相同范围、相同算法且双方本地状态完整时才能直接比较。

例如订单服务的定义在 A 仓、监控说明在 B 仓，D1 只选 A，D2 选 A+B。两份 Dataset 均可完整授权，
但覆盖不同；没有被拒绝的来源不能证明全局完整。两者分别报告范围内状态，跨范围另比较共同部分。
不能用可见部分的摘要代表更大范围，也不能据此保护范围外写入。

本地状态完整不要求解释依赖或外部观察成功，三者各自报告结果。已证明范围内不存在对象是一种完整的
空 Unit 状态；无权或未知不能作为空集合。状态摘要也不辨认修订：内容经历 A → B → A，摘要可以恢复，
历史仍有两次变化。

## 条件写

条件写的原子保证限于目标仓的基准与 CAS。读取依据用作条件时，必须匹配目标仓、维护范围和相等关系。
新增声明或 Unit 构成敏感的条件，也须在同一受保护基准上检查，不能直接把聚合状态摘要当作现有维护条件。

跨仓对象即使完整可读，也没有全对象原子条件：分别写 A、B 仓的请求可以各自通过 CAS。
Dataset 固定经过验证的来源组合，不改变这一写入边界。若未来允许无关对象提交后继续写入，必须重新取
基准并重做受影响的 Schema、引用及提交校验，不能只重比对象摘要；本轮不放宽仓级 CAS。

## 无变化写入

### 判据与结果

合法命令的全部仓内业务效果都与基准相同时，可以不创建提交。判据包括路径、provenance 和声明；
仅正文或本地状态摘要相同不够。Binding 虽无 Snapshot 值，仍有持久声明，须纳入比较。
文件型存储可比较计划产生的树变化，原生存储须提供等价判据。

无变化出口保留正常写入的全部授权、归档、Schema、操作前置和基准约束，包括基准与期望目标一致、
目标引用的可写性及存在性检查。显式空操作集仍拒绝。目录对照为零差异时，服务端须能核验原始发布意图
和固定基准，不能仅接收过滤后的空集合，更不能由客户端直接宣布成功。

[条件合并](governance.md#条件合并)的业务效果还包括发布已评审提交。即使两棵树相同，只要目标引用
推进到另一个提交，就属于仓变更，不能按无变化省略合并。

无变化结果持久记录判定、基准和回执；原提交保持不变，不发仓推进通知。命令成功的审计与 Hook 仍按
[治理](governance.md#hook)处理，不能将没有仓推进理解为没有命令结果。同一命令重试核对完整请求，
返回原结果；不同无变化命令即使共享基准提交，其回执仍须可区分。旧回执没有变更判定时保留未知，
不能默认为无变化。

Writer 无变化、Dataset 同一发布的幂等重放，以及新修订的成员输入未变是不同判定。前者不推进仓，
后两者仍按 [Dataset 发布规则](dataset.md#版本)处理；不能用成员输入相同省略应有的新修订。
外部观察刷新与能力变化按各自维护路径核对，不因没有仓推进通知而停止。

### 接受与恢复

无变化命令采用全部校验完成后的最后一次权威目标 ref 条件检查作为线性化点，最终回执可靠保存后才
返回成功。一次成功命令的 ref 检查与回执保存之间，其他命令可以推进仓；原结果仍对应检查时的基准。
不要求为保存回执锁住目标 ref。该检查须具有与条件提交一致的目标引用一致性保证，不能采用允许
陈旧的 head 缓存；存储未提供此保证时不能启用无变化出口。

尚未保存最终结果的命令不能承诺恢复先前的内存判定。恢复依据必须足以区分以下情况：

- 已有持久最终回执：按原请求核对后重放，不按当前内容重新判定。
- 能持久证明未调用提交且已限定为无变化处理：允许重新鉴权、校验原请求与原固定基准，并重新检查
  目标 ref。通过才形成新的无变化判定；基准已失效则按真实冲突结束，不能自动改用新基准。
- 可能已经调用提交，或无法证明未调用：沿既有未知提交的权威核对与恢复流程，不能自动重发。

例如命令在 c1 完成 ref 检查，最终回执未落盘便崩溃，随后另一个命令推进到 c2。恢复不能凭 c2 的正文
恰好相同补出 c1 的成功；有“未调用提交”的持久证明时重新检查原基准会冲突，否则仍按未知结果处理。
同一命令的判定、恢复和完成须串行受保护，失效的执行者不能覆盖新执行者的最终结果。

这些是恢复所需保证。持久记录的具体组织、写入顺序、终结方式与故障注入证明在实施前完成；现有通用
待恢复记录本身不证明提交尚未调用，也不因本设计更新就获得安全自动重试能力。

## 固定读取与缓存

### 精确回读

固定读取依据由对象层统一提供，保留候选来源（含未贡献者）及所需依赖的版本向量；正文、Schema 和后续
续页沿用同一组坐标。没有跨仓的全局时刻；固定向量保证的是采用组合可复核。依赖解析失败与本地状态
不完整分别报告。搜索回读沿本次 Dataset 修订的合法范围与固定依赖执行，不能从计算产物的实际贡献者
倒推读取范围或来源依据。

精确回读复用服务端可校验的固定依据，绑定原对象、选择规则、范围、候选来源及依赖坐标。它与另一套
范围或版本输入互斥，不能把部分读取的依据换成整对象读取，也不能重新发现一套候选来冒充原范围。
依据须跨重启可解析，不依赖进程内缓存；编码版本、验证材料和必要记录的保留规则须明确。

每次回读重新鉴权。依据不携带访问许可；Dataset 或其版本退役、来源绑定改变、固定坐标不可用时
明确失败，不回退最新。Dataset 回读仍按交付授权与文件范围，不额外要求来源整仓读权。

单仓 commit 只固定本仓保存内容。只有所需解释依赖也已由该提交确定时，它才足以固定完整解释。
例如订单服务在 A@a1，取值描述在 B@b1；B 推进后再请求 A@a1，普通新读取可能采用新的描述符。
要复用原解释就必须同时固定 B@b1。外部值另带观察依据；固定声明和依赖仍不保证重现原外部观察，
当次观察的复核由 [LiveAccess](liveaccess.md) 的证据能力负责。

固定本地回读和原观察证据各按自身合同保留，不依赖查询生成代存活。可回读不延长检索保留，索引回收
也不得破坏仍有效的读取依据或证据；访问仍须重新鉴权。若证据与索引共用底层值，须独立保护实际证据
数据，不因此保留整代查询结构。普通固定读取仍不承诺重现原外部观察。

### 缓存与成本

正文缓存身份须区分实际存储来源、仓、commit 与读取单元。结果复用仍受当前授权和 Dataset 文件范围
约束，限定视图不能借完整仓缓存补齐。旧 commit 与最新 commit 都可按容量和访问价值缓存。

状态摘要首次计算仍可能读取所选完整 Unit；固定 commit 也不自动带来缓存命中。优化须计入摘要、依赖
固定与回执保存的新增成本，再核对减少了多少回源或提交，不把语义正确当作性能收益。

head 缓存会改变“最新”的含义，采用前须确定允许陈旧的上限、写后读和外部写入可见性，并处理失效后
旧请求回填。批量读取、并发和缓存按实际回源成本选择；没有收益证据不引入，不阻塞正确性修复。

## 历史与差异

### 历史与连续扫描

历史按仓、固定引用的 first-parent 链记录值、声明和 Unit 构成变化。相邻等状态可以折叠，但引入点须由
真实状态切换或历史起点证明；扫描窗口的最老提交不必然是引入点。跨仓保留各来源历史，不合成全局顺序。

存储提交分页、扫描预算和返回的对象修订条数是三个限制，不能互相代替。只返回已证明引入点的修订；
预算耗尽时保留未完成状态段与继续依据，本页可以没有修订。成功续页须推进扫描位置，即使仍无修订；
无法取得进展时明确报错，不能无限返回相同空页。只有证明历史终点才结束，读取失败不能伪装预算耗尽。

续页能独立恢复原对象、范围、来源绑定、固定坐标与扫描进度，不重新解析最新版本；若调用方附带坐标，
必须与原依据匹配。每页重新检查当前权限。扫描预算须约束实际回源工作与请求时间，具体数值按测量确定。

端点 diff 只比较两版状态，不能用来跳过历史区间：A → B → A、删除后原样重建的两端都可能相同。
区间跳过必须有覆盖整段且不漏变化的证据；任何加速与逐提交遍历在修订、删除和引入点上等价，派生索引
可以重建。不能据扫描窗口位置推定作者和时间。

A → B → A 时，仍存在且兼容的成员产物可以按[构建身份](index-physical.md#构建身份)复用，但历史修订
身份和本次来源依据不能随产物复用。

### 历史权限

来源仓历史使用[仓的历史授权](permissions.md#三种资源)。Dataset 消费权只交付其发布版本，选中仓根目录
也不授予此前历史；带 Dataset 坐标查询来源历史，仍须单独验证来源仓历史权限，并在每页重新检查。
文件切片继续拒绝通过该视图查询来源历史；有仓历史权限的维护者可改用明确的仓范围。

例如 c1 的订单服务记录内部方案，c2 改成公开方案，Dataset 只发布 c2。消费者不能因此查看 c1 的
存在状态、提交坐标或摘要。两份合法发布版本之间的内容比较则分别按 Dataset 消费授权成立。

### 两版对象比较

比较的两侧分别固定单仓提交、Dataset 发布版或完整读取依据，并匹配同一对象及选择规则。两边独立
打开合法视图，只比较本地 Unit，不调用外部取值，不读取区间历史。

同范围且双方完整时才能判断整体状态是否相等；范围不同则报告范围变化及共同部分的差异，不能给出
全对象相等结论。保留双侧坐标，区分值变化、声明变化、Unit 加入或移除，以及选择范围带来的进入或离开。
Unit 拆分表现为旧地址移除、新地址加入，同一单元也可同时值变和声明变。

这些差异只说明所比较范围内的变化。文件从公开目录移到未交付目录，可见端只证明它离开了交付范围，
不能断言源仓删除；同地址换仓也须保留双侧来源。选择规则和内容同时变化时，只报告能由两个合法视图
证明的差异，不为确定原因读取范围外内容。任一侧无权、读取失败或组成不完整时比较明确失败。

## Dataset 的版本关系

Dataset 还交付纯文件，继续以来源 commit 固定内容；对象状态摘要由交付范围内的 Unit 派生，
不替代来源坐标，也不成为发布前必须保存的全对象清单。

Dataset 改交付路径或元数据也会形成新版，因此不同发布版可能使用相同来源 commit，对象状态摘要也
可能相同。对象比较保留各自文件范围与独立消费授权；Dataset 的指针与元数据差异由
[Dataset](dataset.md#版本) 自己的版本比较负责，不要求读取对象正文。发布和版本分配规则仍归该篇。

## 接口与实施边界

采用上述状态比较、完整固定依据、无变化结果和连续历史的语义。精确接口在公开 Go API、包 README
和 Conformance 中落定；本篇不复制协议字段、错误码或命令参数。HTTP 与 CLI 必须能够完成同一条
使用路径，不能只增加响应信息而没有复用它的输入。

| 使用路径 | 必须交付的结果 |
|---|---|
| 读取后按原依据回读 | 原对象、范围、候选来源与解释依赖保持固定；重新鉴权；原依据不可用则明确失败 |
| 比较两版对象 | 双侧固定视图、范围差异及本地 Unit 差异；与目录发布预览区分 |
| 条件写入后查询或重放命令 | 保留原条件相等关系；可靠区分仓变更、已接受的无变化和待恢复结果 |
| 目录零差异发布 | 服务端核验可复核的原始意图与基准，不能退化为空批次成功 |
| 历史首页与续页 | 固定原依据、另验历史权限、有界扫描、真实引入点及可推进的继续位置 |

实施核对入口：[Object SDK](../../object/client/requests.go)、[HTTP 路由](../../server/service_routes.go)、
[CLI 定义](../../object/cli/commands.go)、[回执模型](../../object/receipt.go)及
[Writer 合同](../../object/writer/README.md)。具体候选形状、兼容策略、故障测试与成本目标由
`OBJECT-VERSIONING-01` 维护。
