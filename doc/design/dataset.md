# Dataset：交付

Dataset 是多团队协作里的交付单元：为某个用途从多个团队的仓里挑选内容、把每个来源固定到确定的
提交、单独授权给使用者。用户用的是对象，找的是 Dataset：Dataset 决定这一次能看到什么、看到哪一版、
凭什么有权看。它停在文件层，没有对象层也能独立使用。

Dataset 是安装里与仓并列的一等实体，不是某个仓的附属视图：名称在整个安装内唯一，使用者不必先
知道内容在哪个仓就能按名称找到它。它的内容是一组指针（交付路径加来源）加描述元数据，不复制字节。
实例：交易团队仓里的 `services/orders/`、支付团队仓里的 `services/payments/`，与这两者所在的仓
并列在安装顶层。

Dataset 只做三件事：可见范围、固定版本、消费权限。它不负责把对象拼完整（同一 ID 的方面由对象层
自然归到一起，见[对象](object.md)）。对象层在它上面附加检索：选进的索引声明
决定怎么检索，由部署里装的插件解释；声明本身是普通文件，Dataset 不绑定插件，见[发现](discovery.md)与
[插件](plugins.md)。
拿 Spring 类比，它更像发布用的 BOM，而不是容器。

## 目标

- 可发现：按 Dataset 名称在整个安装内找到内容，不用先知道它在哪个仓、哪个目录。
- 可复现：每个版本不可变，`vN` 永远解析到同一批指针，不管来源仓后来怎么变。审计要能用一个版本号
  指认“当时用的是哪版内容”。
- 受治理的共享：通过 Dataset 授权，与来源仓权限无关。
- 按用途组合，不复制来源仓的布局，也不复制字节。
- 发布时固定每个来源的版本。来源后来改了不影响已发布版本；再发一版，新请求才使用新版。
- 来源按分支登记，发布时固定到提交：用户写分支，不用查提交号；每个版本指向确定的提交，可以复现。
  Dataset 本身没有分支，测试与生产分开就建两个 Dataset，各自登记不同的来源分支。
- 版本号 `v1`、`v2` 单调递增，系统生成，永不复用；`latest` 指向最新发布版，是消费方的默认取值。
- 有自己的消费权限。能消费 Dataset 不等于能读来源仓，能读来源仓也不等于能消费某个 Dataset。
- 消费方日常只用名称和 `latest`，不必自己跟踪来源仓；需要复核时，结果里带着具体依据。
- Dataset 是搜索的唯一范围，也是检索空间。跨仓、跨类型的发现靠组合进同一个 Dataset；调用者先从
  库存里按消费权限选出 Dataset，再在里面搜。消费权限是整体的，能消费就能读清单里的全部内容。

## 例子

运维组发布 `oncall`：

| 来源 | 交付位置 |
|---|---|
| 交易团队仓的 `services/orders/` | `services/orders/` |
| 支付团队仓的 `services/payments/` | `services/payments/` |
| SRE 团队仓的 `runbooks/common.yaml` | `runbooks/common.yaml` |

值班 Agent 只有 `oncall` 的消费权。它看到统一的目录，每个文件仍能追溯原仓、版本和原路径。

## 组合规则

- 可以选目录，也可以选单个文件；目录保持内部的相对布局，单文件要明确交付位置。
- 同一个交付文件只能有一个来源，冲突时拒绝，不按顺序覆盖。不同仓的同名文件可以放在不同位置或改名交付。
- 目录结构也是发布内容，只调整交付路径也要发新版。
- 不拼接文件、不改写文件里的标识或相对引用，交付路径不是对象身份。对象身份只看 `object_id`。
- 同一对象的同一方面来自两个来源仓时，拒绝发布，指出冲突的对象、方面和来源。
- 空清单不是“整个仓”；未选中的相邻文件不能被读取或列出。
- 可选的自定义键值元数据随发布保存，改元数据也要发新版，不扩大范围、不改变授权。

## 版本

三个坐标要分清，它们粒度不同、用途不同。

| 名称 | 是什么 | 用途 |
|---|---|---|
| `vN` | Dataset 的不可变版本号，`v1`、`v2` 单调递增，系统生成，永不复用 | 审计指认“当时用的是哪版内容”；固定消费 |
| `latest` | 指向最新发布版 | 消费方默认取值，不必自己跟踪来源仓 |
| 来源提交 | 版本内每个来源固定到的那次提交 | 复核单份内容、解释跨仓引用 |

- `vN` 永远解析到同一批指针。版本一旦发布，指针、交付路径和元数据都不再改写；要改就发下一个版本。
- 版本号由系统生成，不接受调用方指定。`kc dataset define` 拿到的号来自服务端，不是请求里的入参。
- 新版本的号必须大于当前版本，否则非快进拒绝。同一个版本重复提交完全相同的定义按幂等处理。
- `latest` 只在发布被接受之后才前移，所以它永远指向一个已经准备好的版本。
- 消费方写 `latest` 与写 `vN` 走同一条读取路径，区别只在版本从哪里来。一次请求解析一次版本，
  之后的读取、列目录和翻页都用这个版本；`latest` 在请求开始时已经解析成具体版本号，不会读到一半换版。
- 固定版本读不比 `latest` 慢，它少一次版本解析。所以固定版本是常规能力，不是低频例外。
- 需要跨仓一致的一组内容时，固定同一个 Dataset 版本的各来源提交就是那一组；不要用各仓自己的 head。

接口上，版本用两种写法：写 `latest` 表示最新发布版，写 `vN`（或版本号）表示固定版本。省略版本
等于 `latest`。两个已发布版本之间可以对比，输出交付项与元数据的变化；对比只看指针，不读来源字节。

### 元数据

Dataset 的可选描述元数据随版本保存，改元数据要发新版本。元数据是给人看和筛选用的，不参与范围
计算，也不改变授权。

- 部署可以定义安装级的元数据键：键名、类型（字符串、枚举、数字、布尔、日期）、是否必填、
  允许的取值、是否允许多值。键在创建 Dataset 之前定义好。
- 必填键在每次创建和发布时都要有值。新增一个必填键不会追溯否定已有版本，但下一次发布必须补上。
- 元数据键的定义属于部署治理，和对象 Schema 是两回事：前者约束 Dataset 条目，后者约束对象内容。

## 发布

发布是一次可恢复的采用决定：先固定候选版本，检查范围、路径冲突和发布权限，再接受一条不可变
记录并切换当前版本。

- 消费方只能看到已接受的记录，看不到准备到一半的。
- 两个维护者并发发布时，不会覆盖对方的历史，也不会让当前版本退回旧版。
- 发布中途失败，来源仓的提交仍然成立，原有发布版继续服务。
- 选入每个来源需要该来源的内容发布许可；只有 Dataset 管理权的人不能借此选入自己无权的私有来源。
- 选进了索引声明且部署装了对应插件时，按冻结的来源版本和这些声明准备索引，准备好之后才切换；
  准备失败保留旧版。
  这是对象层附加的条件，纯文件发布不需要。
- 选入的单元引用了未选入仓里的 Schema 或取值描述时，准备按引用 ID 找到唯一持有它的仓，把那个仓
  当时的提交作为依赖版本一起固定。依赖版本只用来解释引用：不进入文件列表、对象列表和搜索，
  消费者也不因此获得那个仓的读权。依赖仓前进不触发跟随，下一个版本重新固定。找不到持有者或持有者
  不止一个时，准备不通过。

## 跟随

每个来源登记有跟随方式，默认是“跟随”：

| 方式 | 来源分支前进后 |
|---|---|
| 跟随 | 系统用服务身份自动发一个新版本，按来源差异准备，准备好再切换 |
| 手动 | 不动，等维护者发新版本 |

- 自动发布和手动发布是同一条发布路径：同样固定候选版本、检查范围与冲突、准备索引、接受后切换。
- 分支连续前进时只追最新的提交。正在准备的旧目标作废，不为每个中间提交发一版。
- 自动发布失败时当前版本继续服务；状态列出失败原因、落后的来源和提交。来源再前进时重新尝试。
- 选进的索引声明在分支上改了，同样随新版本生效，不绕过版本直接改变检索。
- 自动发布不扩大权限：每次都检查每个来源的内容发布许可。许可撤销后该 Dataset 停止跟随并报出原因，
  不再自动发布，当前版本照常按消费权限服务。
- 有一个来源是手动，就只在它的冻结提交上组合；跟随的来源照常前进。
- 只跟随快进。分支被重置到不包含当前冻结提交的位置，或分支被删除，停止跟随并报出原因，不把
  Dataset 悄悄退回旧内容；维护者处理后（手动发布或恢复分支）再继续。
- 多个仓的配套改动不保证同时到达，系统也不做跨仓事务。准备时按冻结的组合校验跨仓引用（对象
  采用的 Schema、索引声明指向的字段、取值描述）；校验不通过就不接受，当前版本继续服务，状态写明
  卡住的组合与原因。任一来源再前进时自动重试，所以配套改动都到齐后会自然通过。
- 相邻两次自动发布之间有最小间隔，由部署设定，间隔内的前进合并到下一次。
- 准备必须完成才接受新版本，所以索引重建期间，只读文件的使用方也拿不到新内容。状态列出落后的
  来源与提交、卡在哪一步。需要文件及时、检索可以滞后时，拆成两个 Dataset。

## 消费

- 一次请求只解析一次 Dataset 版本，后续的读取、列目录和翻页都用同一范围和版本。
- 客户端带来的版本坐标只是坐标，不是授权；撤权后下一次请求就拒绝。
- 已发布版本引用的来源版本必须保留；来源版本不可用时明确报错，不自动改读最新版。
- 退役 Dataset、退役版本、移除登记成员、删除来源文件是不同操作。

## 版本保留与退役

版本有两件事分开管：能不能读，能不能搜。

- 当前版本必须可读可搜，不能退役。要停用它，就发新版本或退役整个 Dataset。
- 检索保留：维护者在 Dataset 上声明“至少保留多长时间，且至少保留几个版本”，两者都满足才回收，
  默认至少 24 小时、至少 2 个版本。系统按声明执行，不按“最近有没有人用”自动决定，也不因为有任务
  固定在某个版本上而延长。被替换的版本另有一段续页宽限，期内续页可用，过期要求重新开始。
  涉及外部观察的续页还须满足[原观察代的有效期](index-physical.md#查询路径)，两种宽限不相互延长。
  只按数量保留时，跟随频繁的 Dataset 会在几分钟内把长任务固定的版本挤出去，所以时间下限是必须的。
- 超出检索保留的版本仍可按固定版本读取；在上面搜索明确报“该版本的检索已不可用”，提示改用当前
  版本，不当作零命中。
- 退役版本是生命周期操作：已退役版本的读取和搜索都拒绝。发布记录不删，标为已退役，审计仍可追溯；
  不删除来源仓内容，也不改写它的历史。
- 使用记录公开每个版本最近的访问和所占空间，作为数据给维护者调整保留策略或退役，系统不据此自动退役。

## 来源提交保留

版本能读，取决于它固定的来源提交还在。lakeFS 的垃圾回收会删掉分支上已不可达的提交，分支重置或
删除后尤其如此，所以“已发布版本引用的来源版本必须保留”要有机制保证：

- 每个未退役的版本对它固定的每个来源提交持有保留，版本退役或 Dataset 退役时释放。超出检索保留
  不释放，因为这些版本仍然可读。
- 部署检查确认 lakeFS 的回收规则不会越过这些保留；不满足时拒绝启动，不在读取失败时才发现。
- 来源提交仍然丢失（例如在系统之外被清除）时，引用它的版本读取明确报来源版本不可用，不改读最新。

## 配额

部署按 Dataset 设上限：索引体积、向量成员数、保留的版本数。准备超出上限时不接受新版本，当前版本
照常服务，状态说明超出哪一项。配额同时约束手动和自动发布。

## 紧急清除

敏感内容误进来源仓时，只退役版本不够：访问挡住了，数据还在索引和证据里。清除按以下顺序：

1. 维护者从来源仓删除内容，发布不含它的新版本（跟随的 Dataset 会自动发布）。
2. 退役所有含该内容的旧版本，并要求清除。系统在有界时间内物理删除这些版本独占的索引数据；与保留
   中的版本共用的物理索引，按受影响的对象重写。证据里这些对象的观察值替换为“已清除”标记，保留
   摘要和访问记录。清除进度和完成时间可查。
3. 来源仓历史里的这份内容不在本系统范围内，由仓的所有者按 lakeFS 运维处理。处理后引用那些提交的
   版本按上一节报来源版本不可用。

## 交付方式

| 方式 | 适用 |
|---|---|
| 服务端读取与目录分页 | 默认方式，按需读单个文件，也适合在采用前挑选和核对材料 |
| 只读挂载 `kcfs` | 本机放得下的 Dataset；Linux FUSE；挂载点必须不存在或为空；不自动跟随新版 |
| 对象层消费 | 在 Dataset 范围内读对象、搜索，继承同一范围和版本；搜索只在 Dataset 里进行 |

挂载不是编辑入口。修改要回到具体的来源仓，经 Writer 提交，再发布新版 Dataset。写回多个仓时
是多次单仓提交，第二个失败不回滚第一个，系统如实报告部分完成。

## 用例

场景树按 `dataset#U<编号>` 关联验证入口和缺口，见 [测试](../engineering/testing.md)。

### U1：把两个来源组合给使用者

发布者选择两个仓的文件，使用者只得到选中的范围。同名文件映射到不同目标位置，并保留各自来源；
没选入的相邻文件不能通过补读出现。

### U2：源更新之后发布新版

源仓已经更新，使用者仍读当前发布版。新布局冲突、来源版本不可用或发布未被接受时，继续保留
当前版；新版被接受后，新请求用新版，已经打开的视图不漂移。

### U3：撤权以后继续使用旧 pin

使用者保留了旧文件清单和版本坐标。撤权后的新读取必须拒绝，不能因为版本不可变就绕过当前授权；
已经交付到客户端的字节不承诺能远程收回。

### U4：退役与来源保留

维护者停用 Dataset 或移除某个来源登记，系统按当前生命周期拒绝不再允许的消费，
但不因此删除源仓内容或改写它的历史。

### U5：两个发布者并发发布

其中一次发布被接受后，另一方不能覆盖同一版本号、回退当前版本，或让使用者看到半份清单。
准备工作可以重试，已接受的发布必须保留。

### U6：只发布目录中的部分文件

目录里有公开说明和没选中的内部文件。使用者只能枚举和读取选中的内容，即使某个已交付文件
引用了内部文件，也不自动补上；路径中间的父目录跳转同样不能越过范围。

### U7：没有对象层也能交付文件

来源只有普通文本、图片或代码，没有 Schema，也没有索引。发布和文件读取照样成立，交付的字节
保持原样；文件里含 URL 或声明文本，读取时也不触发解析、外部请求或内容改写。

### U8：把 Dataset 接入已有项目

使用者得到明确版本的只读视图，原项目文件保持原状。新发布到来后，已有挂载继续用原版；
采用更新、隐藏界面入口和撤销权限分别是不同的操作结果。

### U9：从多个仓挑选子目录，交付统一目录树

维护者发布 Dataset，使用者在新目录位置枚举并读取所选内容。一个仓的两个片段可以出现在
不同位置，来源身份与版本仍可追溯。上游其他目录不可见，源布局不变。调整交付路径后发布新版，
已打开的旧视图继续按旧路径工作。

### U10：挑选零散文件放到同一个交付目录

维护者从不同仓选几个文件，分别指定目标文件名。使用者只看到选中的文件，不带出来源文件夹里的
其他内容；目标冲突明确拒绝。发布、目录枚举、文件读取与授权要一起成立，`kc dataset clone`
能把交付目录物化为普通本地目录。

### U11：来源分支前进，Dataset 自动跟随

跟随的来源连续提交三次，Dataset 只为最新提交发一个新版本，准备好之后新请求才用它；准备期间与准备
失败时当前版本照常服务，状态列出原因和落后的提交。手动来源不动。选进的索引声明在分支上改了，随新
版本生效。撤销某来源的发布许可后停止跟随并报出原因，不再自动发布。分支被重置到更早的提交或被删除，
停止跟随，不退回旧内容。Schema 在 A 仓改、实例在 B 仓配套改，只有 A 前进时准备校验失败、当前版本
不变；B 也前进后自动通过。

### U12：版本的检索保留与退役

Dataset 声明至少保留 1 小时、至少 2 个版本。一小时内连续发布 4 版，旧版本都还能搜；过了一小时只剩
最近 2 版能搜，第 2 版仍可读，搜索报检索已不可用。被替换的版本在续页宽限内续页可用，过期要求重新
开始。任务固定在第 2 版上，同样报检索已不可用并提示改用当前版本。退役第 3 版后读取和搜索都拒绝，
发布记录仍可查；退役当前版本被拒。使用记录列出每个版本最近的访问与所占空间，系统不据此自动退役。

### U13：来源提交不被回收

保留中的版本固定的提交，在来源分支重置并运行 lakeFS 回收后仍可读；版本退役后保留释放。lakeFS 回收
规则会越过保留时部署拒绝启动。来源提交在系统外被清除后，引用它的版本读取报来源版本不可用。

### U14：配额

Dataset 的向量成员超出配额时，准备不接受新版本，当前版本照常服务，状态指出超出的项；自动发布同样
受限。

### U15：紧急清除

一条含敏感内容的对象进入了版本 3 和 4。删除后发布版本 5，退役 3、4 并要求清除：有界时间内两版的
读取和搜索都拒绝，版本 5 搜不到该内容，共用物理索引里的该对象已重写，证据里它的观察值显示“已清除”
而摘要和访问记录还在，清除进度可查。

### U16：版本号不可变、latest 指向最新发布版

同一 Dataset 连续发布三次，得到 `v1`、`v2`、`v3`，号由服务端生成且单调递增，调用方不能指定。
拿 `v1` 按名称重新读取，得到的交付路径、来源提交和元数据与发布时完全一致；期间来源仓已前进，
`v1` 不变。`latest` 解析成 `v3`。再发一次与 `v3` 完全相同的定义，按幂等处理，既不产生 `v4`，
也不改写 `v3`。尝试发布小于等于当前号的版本被拒且当前版本不后退。一个请求开始时把 `latest` 解析
成具体版本号，请求内的读取、列目录和翻页都用这个号，中途发生新发布也不换版。

### U17：对比两个已发布版本

发布 `v1` 后增删改若干交付项与元数据，再发布 `v2`。对比两个版本，输出新增、移除、修改过的交付项
及其来源提交变化，以及元数据变化。对比不读取来源字节，只比较两个版本的指针和元数据；来源提交
已不可用时仍然能给出指针层面的差异，并标明该来源版本不可用。
