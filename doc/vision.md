# 愿景

## 一句话

Knowledge Catalog 是一个面向 Agent 的对象环境，可以理解为 Agent 的 Spring Boot：多个团队在同一个
生产环境里发布和维护自己的业务对象，Agent 能发现它们（discover）、看懂怎么用、获准后访问（access），
每次使用都留下可以复核的依据。让对象执行操作（wield）是后续方向。

## 两个前提：多团队协作，面向生产

我们不是给一个人或一个团队整理资料的工具。设计上始终假设：

- 对象由很多团队分别维护。每个团队有自己的仓、自己的发布节奏、自己的权限边界，没有一个统一的发布时刻。
- 系统跑在生产里。并发修改不能互相覆盖，失败和重启后要能恢复到原来的结果，每次访问都要经得起审计。

所以下面四块不是附加功能，而是地基：

| 地基 | 解决什么 |
|---|---|
| Snapshot（仓与版本） | 每个团队独立维护，修改形成不可变版本，并发提交互不覆盖，历史可追溯 |
| Dataset（组合交付） | 按用途从多个团队的仓里挑选内容、固定版本，交付给使用者，不复制、不合并来源 |
| 权限 | 谁能维护哪个仓、谁能消费哪份交付、谁能看到什么，分开授予，每次请求重新检查 |
| 有作用域的插件 | 搜索、外部取值等能力按团队的仓启用，成本、失败和权限都留在所属团队内 |

## 要解决的问题

一个组织里，关于“某个服务是什么、谁负责、出了问题怎么办、现在状态如何”的信息散落在
各团队的文档、代码仓、表格和运行系统里。今天的 Agent 想用这些信息，会碰到四个问题：

1. 找不到。不知道有哪些对象，也不知道该去哪个系统找。
2. 看不懂。拿到一堆文件，不知道哪些是同一个对象，字段是什么意思，能做什么操作。
3. 用不了或乱用。要么没有权限，要么权限给得过大，直接拿走整个仓或机器凭证。
4. 说不清依据。回答引用了什么版本、什么时间的状态，事后无法复核；发现资料过时也没有
   回到维护者手里的路径。

## 心智模型：Agent 的 Spring Boot

Spring Boot 让程序员只声明组件，由容器负责发现、装配和横切关注点。Knowledge Catalog 把同一套
面向对象的思路延伸到组织里：团队声明业务对象，环境负责登记、装配插件、检查权限和留证。
区别在于，访问对象的不再是编译好的程序，而是在运行时读说明、按意图挑选对象的 Agent。

熟悉 Spring Boot 的人可以按下表猜出大部分设计。

| Spring Boot | Knowledge Catalog | 作用与差异 |
|---|---|---|
| ApplicationContext（IoC 容器） | KC Server 与装配 | 托管插件实例的装配、启停和释放。差异：容器托管的是对象的定义和版本，不是内存里的对象实例 |
| `@Component` 与 Bean 定义 | 对象注册：Entity、Schema、Affordance，经 Writer 发布 | 声明身份、结构和能做什么。差异：说明要同时让代码和模型读懂；每次修改形成新版本 |
| 组件扫描 | discover：发现与声明式索引 | Spring 启动时按包扫描一次；KC 在运行时按意图搜索，结果受权限限制 |
| 依赖注入 | 对象引用加依据 | Spring 把依赖推给程序；Agent 自己发现后拿到对象引用，再按同一版本读取。没有隐式注入 |
| Bean Scope | 仓、Dataset 与固定版本 | 决定一次请求能看到什么、看到哪一版 |
| 字段读取与懒加载代理 | access：固定读取与 LiveAccess | 声明为外部值的字段由 LiveAccess 透明取回，类似 Hibernate 的懒加载代理 |
| 方法调用 | wield：执行对象的操作 | 当前不做，见下文 |
| AOP | 插件 | 横切能力不写进对象。切点来自 Schema 里的声明，织入由仓决定，见[插件](design/plugins.md) |
| `@Transactional` | Writer 的条件提交与幂等重试 | 基于哪一版修改就只能在那一版上提交；重复提交同一命令只生效一次 |
| ApplicationEvent | 发布后的变化通知与 Hook | 新版本发布触发索引维护；Hook 在动作前后调用外部流程 |
| Starter 与自动配置 | 插件的默认启用 | 装了插件、Schema 有声明就自动生效，仓可以关闭 |
| Actuator | 访问证据、来源、运行状态 | 差异：证据是产品的一部分，每次结果都带着 |
| 自描述的基础设施 Bean | `kc help` 与平台自描述仓 `kr://kc/system` | KC 自己也按这套规范实现，见下文 |

Spring 里没有、但我们必须有的东西：调用方是会犯错的模型，所以说明必须让模型读懂；
对象由不同团队维护，权限和版本都按团队划分；权限每次都查，说明某个能力不等于发权；
每次结果都要能回答依据哪一版。

## 三个动作：discover、access、wield

| 动作 | 回答什么 | 订单服务例子 | 当前 |
|---|---|---|---|
| discover | 有哪些对象，哪个适合这个任务，它能做什么 | 搜到订单服务，读到它的说明 | 专注 |
| access | 这个对象的内容和当前状态是什么 | 读值班说明，取当前健康状态 | 专注 |
| wield | 让对象做一件事 | 让订单服务执行一次限流 | 暂不做 |

现阶段只做 discover 和 access。wield 涉及外部系统的副作用、执行授权和失败恢复，合同等真实需求
出现再定；在那之前，Agent 能读到“怎么操作”，但真正的操作仍走外部系统自己的入口。

## 系统自身也是对象

KC 自己按同一套规范实现。`kc` 命令行就是 KC 的 Affordance：`kc help` 说明系统有哪些模块、
每个命令做什么、需要什么条件、有什么效果；平台自描述仓 `kr://kc/system` 把模型、命令和能力说明
作为对象发布。Agent 认识 KC 和认识订单服务，走的是同一条 discover、access 路径。KC 也是这套规范
的第一个用户。

## 一条贯穿全书的任务

> 订单服务告警了。Agent 需要读取订单服务的定义和值班说明，找到负责团队，查看订单服务当前
> 的健康状态，按步骤处理，并在处理记录里写明依据了哪一版说明、哪一刻的状态。处理中发现值班
> 说明有一步已经过时，反馈给交易团队；交易团队修订发布后，下一次告警自动使用新版。

| 环节 | 任务里的动作 | 用到的能力 |
|---|---|---|
| 供给 | 交易团队发布订单服务、团队和“负责”关系；SRE 团队为订单服务补充监控方面 | Snapshot、Object、Schema、Writer |
| 交付 | 运维组把多个团队的值班相关内容组合成一份交付 | Dataset|
| 发现 | Agent 搜索“订单 告警”，定位到订单服务 | discover：声明式索引 |
| 理解 | Agent 读到订单服务能“查询健康状态” | discover：Affordance |
| 获准 | 系统核对 Agent 是否有这份交付的消费权 | 权限 |
| 使用 | 读取值班说明，取得当前健康状态 | access：固定读取、LiveAccess |
| 留证 | 记录用到的版本和状态观察时间 | 依据与证据 |
| 修订 | 反馈过时步骤，团队修订后发布新版 | 反馈、Writer、治理 |

## 三类用户

| 用户 | 想做什么 | 产品给他什么 |
|---|---|---|
| 接入方（供给团队） | 发布并维护自己的对象，决定分享给谁 | 自助申请仓、发布与修订、启用插件、分享与撤销，不用找部署方代办 |
| 消费方（人、应用、Agent） | 按任务找到并使用对象，结果可复核 | 发现、读取、外部取值、只读挂载，每次结果都带依据 |
| 部署方（平台） | 一次性搭好服务，之后不参与日常 | 一套服务、托管存储、准入策略、运维与观测 |

## 成功的样子

- 接入方从登录到发布第一版对象，只用客户端，不需要部署方介入。
- 两个团队同时修改，不会覆盖对方；服务重启或网络中断后，重试得到原来的结果。
- 消费方只知道一个 Dataset 名称就能开始工作；需要复核时，依据就在结果里。
- Agent 只从 `kc help` 出发，就能认识对象模型并完成上面那条任务。
- 任何一次读取都能回答：读的是哪个对象、哪一版、来自哪个仓、凭什么有权读。
- 没有权限、能力未启用、索引未就绪、确实没有匹配，这四种情况能明确区分，不混成“空结果”。
- 资料过时能回到维护者手里，修订发布后被后续任务采用。

## 不做什么

- 不是检索应用。检索是发现对象的手段之一，不是产品本身。
- 不是数据仓库或数据湖。文件的保存和版本交给 lakeFS，我们组织的是对象和交付。
- 不托管审批流程。申请和业务批准走组织已有的流程，我们负责批准后的发权和每次使用时的权限检查。
- 不让推断自动变成对象。反馈和模型推断必须经过正常发布，才能成为别人可以使用的对象。
- 不替外部系统执行权限。能读到“怎么操作某系统”的对象，不等于能操作那个系统。
- 不做跨仓事务。多个团队的修改各自提交，组合靠固定的版本组合，不靠一次全局提交。
- 不保证零延迟的实时状态，也不自动保存全部历史状态。
