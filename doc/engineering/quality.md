# 工程质量闭环

代码腐化是趋势问题，不是单点检查能拦住的。提交前检查拦得住明确违规，拦不住“合规但变烂”的改动：
复制粘贴式重复、绕过既有抽象的新特例、迎合实现的断言、只增不减的分支和参数。本篇说明质量控制分几层、
看到的问题往哪里去。

## 六层

| 层 | 回答什么 | 在哪里 |
|---|---|---|
| 防 | 这次改动要达到什么，触碰哪些合同 | `AGENTS.md` 的交付要求与本目录的设计文档 |
| 拦 | 有没有明确违规 | 编译、合同、架构守卫，见[测试与验证](testing.md) |
| 闸 | 这次有没有比上次更烂 | `make quality`；`scripts/coupling -strict` 卡传播成本、不稳定度漂移和新单元 |
| 审 | 合规的改动是不是坏改动 | 提交前复核：重复、新特例、断言迎合实现、公开形状因便利扩张 |
| 观 | 哪里在腐化 | 变更频率乘以复杂度的热点；耦合与分层度量 |
| 沉 | 看到但不马上修的问题去哪 | 债务登记，过渡期记在 `TASK.md` 或交付说明 |

增量门禁只卡新增和变更的代码，基线只紧不松，收紧要显式执行 `-write-baseline` 并在 `TASK.md` 记录。
存量不追，增量不欠。

## 三个出口

每个看到的质量信号，判定（真问题、设计使然、误报）之后只有三个去处：

1. 当场修：本次范围内能安全修掉的，不留给下一轮。
2. 登记为债：写清位置、信号、判定、处置和触发条件。不允许“看到了但没记录”。
3. 升级为自动检查：同类信号出现两次以上，就变成守卫、合同或脚本，不靠人记。

误报要回喂成更准的规则或显式豁免；设计使然要写回对应的设计文档。

## Agent 协作下为什么腐化更快

| 原因 | 对策 |
|---|---|
| Agent 没有跨会话记忆，容易重复造轮子 | 写下来的合同和文档就是外部记忆 |
| 只追求当前任务通过，容易绕抽象、加特例、断言迎合实现 | 守卫不可削弱，不用 skip；断言先红后绿 |
| 写的速度远超审查带宽 | 小改动；提交前先做一轮信号复核 |
| 对硬门禁的服从远高于口头约定 | 能自动化的信号尽快升级为门禁 |

## 耦合度量

| 层次 | 指标 | 状态 |
|---|---|---|
| 布尔边界 | 依赖方向、闭集、无环 | `internal/arch` 守卫 |
| 结构 | 传入、传出依赖，不稳定度，传播成本 | `scripts/coupling -strict`，进入 `make quality` |
| 行为 | 共同变更率 | `scripts/coupling -cochange`，只读观测 |
| 抽象与内聚 | 抽象度、主序列距离、公开面密度 | 只读观测，确认后才进门禁 |

读法：命令行、装配入口这类边缘单元不稳定度接近 1 是正常的；`kernel`、`snapshot`、`object` 这类核心
低且被依赖也是正常的。依赖方向必须从不稳定指向稳定。不设普适阈值，以 `scripts/coupling/baseline.json`
为基线，盯离群单元和突变。目录组织调整时，用同一工具和口径重算改前改后，再显式收紧基线。
