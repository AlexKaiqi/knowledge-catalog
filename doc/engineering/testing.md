# 测试与验证

本篇说明怎样证明一项改动成立：有哪些验证入口，用例放在哪里，证据怎样判读。具体用例库存由代码
和场景清单生成，不在文档里手工维护“当前全绿”。

## 原则

- 代码修改必须通过测试。交付前把受影响的测试和门禁跑到绿，并补必要的回归测试。
- 交付说明写清实现范围和已验证范围，不把“实现完成”写成“验收通过”。
- 用户要求验证时，先跑出会失败的证据，再改代码，再跑到绿。
- 不删除或削弱合同、Conformance、架构守卫的断言，不用 skip 换绿。
- 失败路径的断言要钉住具体错误码或状态，`err != nil` 只用于确实无法判定码的边界。判断标准：删掉被测行为后断言是否仍可能通过。
- 定向 `go test` 只证明所选范围，不代替完整合同或真实部署验收。

## 验证入口

| 命令 | 证明什么 |
|---|---|
| `make check-docs` | 文档链接与文档关系 |
| `make quality` | gofmt、tidy、vet、staticcheck，圈复杂度、文件体积、重复与耦合门禁 |
| `make test` | lakeFS 进程内夹具上的普通与索引场景，使用真实 OpenSearch |
| `make deploy-local-scenes` | 独立的真实 lakeFS 部署验收，需要已有的本地测试栈 |
| `make test-contracts` | 组件、架构与应用合同组合 |
| `make test-all` | 夹具、真实部署、混合合同、插件与其它入口 |
| `make test-race`、`make test-cover` | 并发路径；覆盖率最低阈值 |

lakeFS 夹具与真实部署是不同入口，不因缺少部署配置而要求重建用例环境。真实部署验收按各自合同
单独进行，不为验证以外的目的启动服务或容器。

## 用例放在哪里

| 位置 | 内容 |
|---|---|
| `.data/scenes/` | 协议旅程场景树：每个节点是一个前态，叶子是操作与断言；规范见 `.data/scenes/README.md` |
| 场景节点的 `_materials/` | 走查用的领域材料，例如清河茶铺的表、作业、语义和 SQL |
| `.data/scale/` | 压测场景树、环境配置模板、指标登记表与生成器；规范见 `.data/scale/scenes/README.md` |
| 各包的 `_test.go` | 单元、合同与 Conformance |
| `internal/arch/` | 架构守卫：依赖方向、闭集、无环 |

场景不能只写“命令成功”，要写前态、动作和可观察的后态。改压测用例后要跑 `perf_tree.py --check`。
不要在仓库根加 `tests/`、`collectors/` 或业务故事包。

## 产品价值的验证

协议合同检查身份、版本、范围、授权和失败语义；任务验证检查这些保证是否真的降低了供给和使用成本。
两种证据分别成立，命令退出成功或模型回答流畅都不等于任务正确。

| 阶段 | 要看到的结果 | 必须同时覆盖的反例 |
|---|---|---|
| 发布并复用 | 接入方发布带模型和来源的对象，两个消费者独立使用 | 需要管理员逐仓改配置；消费者拿到存储凭证 |
| 按任务交付 | 多个来源组成 Dataset，身份、范围、版本仍可区分 | 未选文件被补入；同名对象被覆盖；组合取得整仓权限 |
| 完成任务 | 找到定义和关系，取得有依据的内容或观察 | 搜索与回读混版；缺能力当零命中；旧观察冒充当前状态 |
| 修订与采用 | 反馈关联依据，修订发布，新任务用新版，旧任务可复核 | 反馈直接变成对象；撤权后旧引用仍放行 |
| 故障后续用 | 服务替换、响应丢失或索引故障后恢复原范围和结果 | 重试重复提交；缓存丢失补建空权威；派生失败撤销提交 |

## 规模

规模结论只来自可重复的实测：从基线开始逐档扩量，记录维护成本、瓶颈、备份与恢复结果，限定最大
通过范围。不从存储组件名称或小规模点读外推容量。执行合同见 `.data/scale/CASES.md`。
