# 核心概念

读懂这套文档只需要下面这些概念。按“存放 → 组织 → 扩展 → 使用”的顺序排列。

## 存放与交付

| 概念 | 是什么 | 订单服务例子 |
|---|---|---|
| Repository（仓） | 一个团队维护的一组文件，也是维护权限的边界。每次修改形成不可变的版本 | 交易团队的仓 `kr://acme/services` |
| Commit（版本） | 仓在某一时刻的完整内容，一经形成不再改变 | 交易团队发布值班说明后得到的那一版 |
| Object Version（对象版本） | 明确读取范围内，由固定的来源坐标及所需解释依赖坐标确定的对象内容。跨仓是一组坐标，不代表全局时刻 | 交易团队某次提交的值班说明，按固定版本的 Schema 解释 |
| 状态摘要 | 对明确范围内完整维护单元的值、本地声明与单元构成计算的摘要，用于比较本地状态；不作为读取坐标或修订身份 | 只改同仓的支付服务，订单服务的状态摘要不变 |
| 对象修订 | 单仓历史中的一次对象状态切换，按真实引入点区分；不同修订可能具有相同状态摘要 | 值班说明从 A 改为 B 再恢复 A，恢复后的修订不同于最初的 A |
| Dataset（数据集） | 与仓同级的一等实体：从一个或多个仓里选出部分文件、把每个来源固定到确定的提交，组合成一份交付。自己不复制字节，存的是一组指针加描述元数据。有自己的消费权限和不可变版本 | 运维组的 `oncall`，包含各团队的服务定义和值班说明 |
| 接受（Accepted） | 一次发布决定的成立：候选被提交为不可变版本，文件读取立即按该版本生效 | 维护者发布 `oncall` 的 `v7`，`v7` 的文件马上可读 |
| 就绪（Ready） | 同一版本上的第二个状态：该版本的检索语料已构建完成，可以按它搜索。与接受各自独立、都可查 | `v7` 已接受但检索还在追；这段时间搜到的仍是 `v6` |

Dataset 和仓并列在安装顶层，名称全安装唯一，消费方不用先知道数据在哪个仓。每次发布产生一个
不可变版本，编号 `v1`、`v2` 单调递增，系统生成、永不复用；`vN` 永远解析到同一批内容。`latest`
指向最新接受版，是消费方的默认取值。来源仓后来改了，已发布版本不会变；维护者再发一版，新请求
才用新版。能消费 Dataset，不等于能读整个来源仓。

接受与检索就绪分开：版本被接受，文件读取就用新版本；检索另有一个"最新就绪版本"，构建追上来之前
仍服务上一个就绪版本。接受不会因检索未就绪而撤销，`latest` 也不因未就绪而回退。显式指定一个未就绪
的版本去搜索会明确报未就绪，不静默退回上一版。

比较状态摘要前，须确认对象与逻辑范围相同，且范围内本地状态完整。部分读取只代表所选范围；
无权、失败或冲突不能当作缺失忽略。固定对象版本也不固定外部当前值，外部值另有观察依据。

## 组织业务对象

| 概念 | 是什么 | 订单服务例子 |
|---|---|---|
| Object（对象） | 有稳定身份的业务对象，统一称为 Entity（实体）。身份是带命名空间的 `object_id`，不带仓；文件改名、移动或换仓都不改变身份 | `trade/order-service`、`trade/payments-team` |
| Namespace（命名空间） | `object_id` 的第一段，表示对象语义上的归属。常和仓名重复，但不是仓 | `trade`、`dw.ods` |
| Aspect（方面） | 同一对象的一个方面，可单独维护和读取。同一对象的不同方面可以由不同团队在各自的仓里发布 | 订单服务的 `definition`（定义）和 `runbook`（值班说明），SRE 团队发布的 `monitoring` |
| Member（成员） | 某个方面里一组带键的成员，可单独寻址和更新 | 订单服务“接口”方面里的每个接口 |
| Relation（关系） | 对象之间有业务含义的关联，有自己的身份和版本 | 订单服务“由交易团队负责” |
| Schema | 约定某类对象或方面的字段、类型和约束。Schema 本身也是对象，随仓发布；不写插件声明 | `schema/service.definition` 规定服务定义有名称和用途 |
| 对象引用 | 读写对象时使用的统一地址：对象 URN 加上定位到哪一部分 | 指向“订单服务的值班说明” |
| 形状 | 读取时请求方写出的结果结构，沿用 GraphQL selection set，只取对象的一部分 | 只要订单服务的定义和两个接口的路径 |
| Writer | 发布对象的唯一入口。检查 Schema、身份和并发冲突后才形成新版本 | 交易团队修订值班说明走 Writer |
| 来源（Provenance） | 一个对象的内容从哪里来、怎样变化 | 值班说明由谁在哪一版修改了哪一步 |

引用关系不会自动授予端点的读权限，也不会把端点自动加入 Dataset。

## 扩展能力

| 概念 | 是什么 | 订单服务例子 |
|---|---|---|
| 插件 | 横切大量对象的额外能力，是某类声明的解释器。声明是经 Writer 发布的方面或成员，部署装了插件就自动解释；没装时只是普通内容 | 交易团队声明服务名称进索引、订单服务的健康状态由 LiveAccess 取值 |
| 索引声明 | 一个对象的 `index` 方面，选进 Dataset 才生效。每个成员写一个检索字段：用定位符指向的一个或多个 Schema 字段，以及能力清单内的构建方式 | 运维组为 `oncall` 声明服务名称可全文检索、名称加值班说明拼成语义字段 |
| 能力清单 | 插件实例公开的、带版本的可配置项：构建方式、取值范围、改了是否重建、上限 | OpenSearch 实例支持的分词器和向量模型 |
| 声明式索引 | 按索引声明为对象维护可搜索的副本。副本可以重建，不是内容本身 | 让“订单 告警”能搜到订单服务 |
| 取值描述 | 说明一个外部系统怎么访问的对象：`origin`、取值协议和操作。方面或成员按 ID 引用它 | SRE 团队发布的监控系统取值描述 |
| LiveAccess | 按方面或成员上的取值来源，经取值描述向外部系统取当前值 | 取订单服务当前的健康状态 |
| Affordance（可供性） | 对象和系统告诉使用者“能做什么、需要什么条件、会有什么效果”的说明。KC 自己的 Affordance 就是 `kc help` | 订单服务说明自己可以读值班说明、可以查健康状态 |

说明某个能力，不等于这个能力已经装好、现在可用或你有权使用。系统在每次实际调用时都会核对。

## 三个动作

| 动作 | 是什么 | 当前 |
|---|---|---|
| discover | 找到对象并读懂它的说明：搜索、浏览、读 Affordance | 专注 |
| access | 读取对象内容，以及经 LiveAccess 取得的外部当前值 | 专注 |
| wield | 让对象执行有副作用的操作 | 暂不做 |

## 使用与追溯

| 概念 | 是什么 | 订单服务例子 |
|---|---|---|
| 身份（Principal） | 发起请求的用户或 Agent，在系统里是一个稳定的用户名 | `kaiqidong` |
| 授权 | 某个身份对某个仓或 Dataset 能做哪些动作。每次请求都重新检查 | Agent 有 `oncall` 的消费权，没有交易团队仓的写权 |
| 依据 | 一次结果所用的对象身份、仓和版本；涉及外部状态时再加上观察时间和来源 | “依据 `oncall` 第 12 版的值班说明，10:03 观察到的健康状态” |
| 观察 | 从外部系统取到的一次值，带取值时间和来源 | 10:03 的健康状态为降级 |
| 反馈 | 使用者对某个对象提出的具体问题，或对一次搜索命中是否采纳的评价，附带依据。反馈本身不会改变对象 | “值班说明第 2 步已过时”；采纳了搜到的订单服务 |
| 工作分支 | 需要评审的修改先写到非默认分支，校验后由 Writer 条件合并到目标分支 | 交易团队在 `review/oncall` 分支修订值班说明 |
| Hook | 在某个动作前后调用外部脚本或服务；`writer.merge` 的前置 Hook 可否决合并，审批归业务 | 合并前由业务脚本检查值班说明格式 |

## 不用的词

| 不用 | 改用 |
|---|---|
| Catalog（作为可创建的对象） | 服务、登记空间。一套服务只有一个登记空间 |
| Knowledge Set、知识集 | Dataset |
| Dolt、Gitea、filegit | 存储只用 lakeFS；登录只用 KC 自身身份（local、Taihu） |
| 投影（对外） | 索引。投影只在实现里使用 |
| Interface（对外） | 插件。处理器合同只是插件内部机制；对象方法属于 wield |
| Knowledge、知识（指对象） | 对象 |
