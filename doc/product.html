KNOWLEDGE CATALOG

把业务对象说明白，
让人和 Agent 找得到、看得懂、用得上。

Knowledge Catalog 让多个团队分别维护业务对象，再按用途把内容组合成 Dataset。使用者从一份交付出发，找到定义、说明和关联材料，按权限读取，并保留所用的对象与版本依据。需要搜索或外部当前状态时，再接入相应能力。

认识同一个对象身份、说明和关系一起维护 交付一份 Dataset选定范围、固定版本、单独授权 AI 友好接上已有 Agent从帮助逐步发现、理解和使用 使用按依据读取核对内容、来源与版本 持续维护变化有据可查反馈、修订、采用与复核
第一部分 · 理解产品
01

把分散资料组织成对象

从一个常见问题开始订单服务告警了。服务定义在交易团队的文档里，活动安排在市场组，值班手册又是另一个文件。人和 Agent 都需要先弄清：说的是哪个服务，哪份说明有效，当前状态去哪里查。

给需要反复找到、使用和引用的东西一个稳定身份，把关于它的说明分成方面，再连接相关对象。团队继续维护自己的内容，使用者通过 Dataset 取得获准的一组材料。

身份稳定service/qinghe.order-service 指向下单服务。移动文件或更换来源仓不必更换对象身份；实际读取仍受范围、权限和版本可用性约束。
说明可以分工定义、值班手册、监控是不同方面，可以由不同团队维护。读取时只组装当前范围中选入的方面。
关系带着业务含义服务由哪个团队负责、受哪次活动影响、可以用哪个工具查询，都能作为有身份、有版本的关系发布。

可以登记什么

对象登记的内容对使用者的价值
服务与告警用途、负责人、接口、处置手册、告警条件找到同一服务的说明，知道接下来查什么、找谁处理
业务概念、表与指标概念含义、字段、作业、计算口径和生效日查询数据前先确定对象和口径；实际计算仍需要获准的数据入口
商品、活动与素材商品信息、活动安排、素材文件与使用限制把业务背景和具体材料一起交付，复核当时采用的说明
CLI、MCP 服务、Skill用途、取得方式、运行条件和操作说明发现适合的工具，再按 Agent 的支持能力与外部系统权限安装或连接

Schema 用来约束内容的结构：采用了 Schema，发布时就按它校验；没有采用时可以先保存普通说明。结构校验不能代替业务事实核实。

图片、视频、CSV、代码和文档也可以按原字节交付。只分享文件时无需先登记对象；需要让人和 Agent 理解它们时，再补身份、说明和关系。文件规模和性能取决于具体部署及实测范围。

谁来维护

供给团队维护来源仓和对象，Dataset 发布者选择交付范围，授权管理者给实际使用身份发权。这些角色可以由同一人承担，也可以分工。

谁来使用

人、应用和能调用 kc 的 Agent 共用公开入口。部署方提供服务地址、登录方式和可用能力，日常内容由团队自行维护。

02

值班场景：下单服务告警了

清河茶铺秋季上新，值班同事问：“下单服务告警了，我该先看什么？”这个场景展示内容怎样被供给、交付、使用和修订。

环节谁做什么留下什么依据
准备交易组发布服务、处置手册、告警和工具说明；市场组发布活动首日提示各自在来源仓形成独立版本
交付发布者把值班需要的文件选入 store-oncall，取得各来源发布许可，并给值班身份消费权一个固定来源版本组合的 Dataset 版本
读取值班同事或 Agent 固定该修订，读取告警、服务手册和活动提示；有可用索引时也可先搜索对象身份、所读方面、来源仓和版本
判断发现活动期间预计流量上升，先核对当前流量、错误率和适用阈值，再提出处置建议说明来自交付；当前运行数据须从获准的监控入口另取，带观察时间
改进使用者反馈手册过时；维护者核实、修改并发布，再由发布者交付新修订反馈关联旧依据，后续读取可采用新版，已有处理记录保留原依据

例子中的事实边界：随项目提供的清河茶铺材料里，健康状态是登记时的静态快照；order-cli 是工具交付示例，没有连接真实订单服务。读到这些材料可以理解处理步骤，不能据此断言现在的线上状态。

一份有用的回答会同时说清：采用哪版手册、活动提示改变了哪一步判断、哪些当前数据已经核实、哪些仍需查询。登记和引用让依据可追踪，业务结论还需要使用者核实。

同一方式，也适用于其他场景

销售分析 · qinghe-analysis

表、字段、作业和 GMV 口径帮助分析者确定该查什么。比较口径修订可以解释统计范围变化；判断销售额为什么下降，还需查询实际订单数据并计算，不能只凭口径说明得出原因。

素材使用 · autumn-launch-kit

成片、封面、字幕和渠道限制一起交付。更正字幕后发布新修订，已下发物料仍可按原修订核对。是否还能投放，要结合说明中的有效日期与实际授权判断。

清河茶铺是示例世界。只有部署方已发布这些 Dataset、且当前身份可消费时，后面的示例读取才成立；以目标服务返回的库存和修订为准。

03

仓、对象与 Dataset 怎样配合

先区分三个角色：仓是团队维护来源的边界；对象把内容解释为业务事物；Dataset 从来源文件中选择范围、固定版本并交付。Dataset 不依赖对象登记。

正式五层：所有 KC 请求经服务；对象解释和插件按需要使用
仓团队怎样维护

来源文件和提交历史保存在仓里。团队按读者、维护权限和发布节奏划分仓；一个团队可以管理多个仓，不要求一团队恰好一仓。

对象内容怎样被理解

对象身份不带仓，方面可以由多个团队维护。对象层只解释本次允许读取的文件，并记录每个方面的来源。对象发布经 Writer 校验；原始文件交付走文件路径，不要求先变成对象。

Dataset使用者拿到什么

选择一个或多个仓的目录、文件，映射成一份交付，发布时固定各来源版本。只交付文件也成立；交付对象时，应明确选入所需的方面与材料，关系不会自动把端点或其他方面补进来。

插件需要时怎样增强

部署安装插件，团队发布声明。索引声明随 Dataset 选入而生效，取值来源随方面或成员读取而生效。插件不发权、不改写来源；声明、能力可用与调用获权分别检查。

服务与入口每次访问怎样受控

使用者通过统一服务发起请求，由服务确定身份、范围与版本，检查权限并执行。命令行和 HTTP 共用动作语义；只读挂载提供文件视图，不是跨仓写入口。

回到值班例子：交易组维护服务与手册，市场组维护活动；store-oncall 选入所需文件。值班同事有这份交付的消费权，不因此得到两组来源仓的维护权。只交付文件时，仍经过同一服务的范围与权限检查。

接下来先以消费方身份读一份已有交付，再走供给方的首次发布路径。分层职责详见架构。

第二部分 · 从读取到交付
04

AI 友好：让已有 Agent 从帮助开始

把 KC 接到你已经使用、能够执行命令并阅读结果的 Agent。KC 提供可逐步发现的帮助、业务说明和版本依据，让 Agent 按当前需要学习怎么用，再读取内容、形成判断。

第一次，只需交代入口和目标

先在 Agent 实际运行的环境中准备好 kc、服务地址与登录会话，并给实际请求身份授予所需权限。用户提供业务问题，Agent 从 kc help 开始；不必预先把每个对象、文件路径和命令参数都写进提示词。

给 Agent 的起始说明 · 环境已准备好
本机有 kc，已配置服务并登录。先运行 kc help 了解用法。
请从可访问的内容中查明：下单服务告警后，应该先看什么？
说明采用的资料与版本，以及还需要核实的信息。
发现怎么用根帮助提供入口，功能组帮助串起流程；执行前阅读叶子命令帮助，核对参数、前提、效果和失败处理。
理解有什么查看当前服务的库存，沿交付导读、Schema、对象说明和关系理解业务；需要扩展能力时，再读访问概览和插件帮助。
按依据使用选定范围与修订，读取材料并保留来源。需要当前数据时沿获准入口查询；缺内容、未就绪或无权时如实说明。

这条路径既服务人，也服务 Agent。已有首次读取指南与 kc help consume 衔接读取；准备发布自己的内容时，再沿 kc help write 进入首次发布指南。

Skill：熟悉以后，按需沉淀

首次使用可以从这段引导直接开始，无需先创建 KC Skill。经常使用时，团队可以提供一份轻量的引导 Skill，记录何时使用 KC、从哪份帮助开始，以及团队要求的引用和输出方式；具体命令仍以当前 kc help 为准。

也可以让 Agent 把实际验证过的重复流程起草成 Skill，经使用者确认后，按该 Agent 支持的机制保存和复用。Skill 不存登录凭证，也不把一次读取的业务事实固化为长期规则；业务内容和版本仍在使用时从 KC 取得。

怎样确认 Agent 已经用起来：在一个新会话里，只给入口、已有身份和业务问题，观察它能否找到相关帮助、读到获准内容，并给出可核对的答案。AI 友好描述的是这条可发现、可理解的使用路径；实际效果需要在选定的 Agent 和部署上验证。

CLI 自说明的设计见Affordance。下面展开同一套消费流程，便于人或 Agent 逐步核对。

05

先消费一份已有交付

先准备能运行 kc 的环境、服务地址、受支持的登录方式和消费权限。人和 Agent 共用以下入口；示例中的内容须由目标服务提供。

1

登录，确认正在用谁的身份

从部署方取得 kc 可执行文件并放入 PATH，把下面的示例地址换成实际服务地址。登录模式以该服务为准。

消费方 · 连接服务
export KC_SERVER_URL=https://kc.example.com
kc help login
kc login

Taihu 登录若返回授权链接，先在浏览器完成授权，再按返回提示执行 kc login --wait。登录完成后用 kc whoami 核对身份；登录成功不等于已获业务权限。

2

选一份交付，固定修订再读

用库存了解有哪些交付及其用途，再核对所选 Dataset 的消费权。下面以部署已公开的 store-oncall 第 2 版为例，其中已交付更新后的手册与活动首日提示；选定修订后，后续读取沿用同一个修订。

消费方 · 读取同一版
kc help consume
kc show
kc dataset show store-oncall --revision 2
kc files list --dataset store-oncall --revision 2 --path services
kc read 'urn:kc:object:service/qinghe.order-service#/runbook' --dataset store-oncall --revision 2
kc read 'urn:kc:object:campaign/qinghe.autumn-2026' --dataset store-oncall --revision 2

已知对象可以直接读；想查看原始文件，沿 kc files list 返回的路径使用 kc files read。搜索需要另外确认该 Dataset 的索引能力与就绪状态，见按需扩展。

核对结果读到第 2 版手册和活动说明：先核对首日流量、适用延迟阈值和错误率，不能仅因延迟升高就重启。保留返回的对象、来源与版本；无权、版本不可用或缺少能力时先处理原因，不把它当成空内容。

3

核对答案与实际读取依据

回到告警问题，检查回答是否引用了刚读取的手册与活动说明，并区分静态快照和当前运行数据。交给 Agent 执行时，可使用上一节的起始说明；检查标准仍是实际读到的内容与依据。

KC 检查经过服务的每次访问；人或 Agent 下载工具后对外部系统的调用，还需遵守那个系统的身份与权限要求。

06

发布自己的内容，并交给使用者

消费路径跑通后，再准备自己的来源和交付。下面连接现有公开指南：每步说明由谁做、需要什么、怎样确认完成。尖括号中的值必须替换为自己的实际值。

1

来源维护者：确定自己的目标仓

先确认已有仓及相应维护权。需要新仓时查看 kc help create；服务已能连接、但尚未登记的仓再查看 kc help attach。不要把公开例子的 store-ops 当成自己的写目标，也不要因看不到它就重复创建。

了解仓的准备方式
kc help repository
kc help create
kc help attach

得到自己的来源仓身份、可维护分支，以及本次发布和回读所需权限。

2

来源维护者：选择文件或对象的供给路径

只交付文件

已有普通文件仓、且维护者具备 lakeFS 原生写入权限时，用来源工具提交视频、CSV、代码等文件。KC 维护权不代替原生写入凭证；尚无这条供给路径时，先与来源负责人确认。取得仓、分支、路径和提交版本后，到第 4 步组合 Dataset；对象目录发布命令不负责上传任意原始文件。

发布对象说明

先从公开 Dataset 取得完整的对象文件及匹配的 Schema，再整理自己的身份、正文与来源。首次发布指南已提供下载与复用路线；不要把读取响应信封或 Schema 展示结果直接当成发布文件。

打开已有的首次发布指南
kc help write
kc read 'urn:kc:object:kc/guide/first-publication#/guide' --repo kr://kc/system
kc help writer commit

服务需已出版系统指南。也可阅读随项目提供的首次发布领域对象：其中用公开商品样例演示“固定修订下载 Schema 和实例，再发布到自己的仓”。值班手册沿同一路径准备，所需类型与内容以自己的材料为准。

得到一份输入完整的对象草稿，或一个已提交原始文件的来源版本。示例只用于学习格式，不替代自己的业务事实。

3

对象维护者：发布，并按本次回执读回

仅对象路径需要这一步。按指南把文件放入 ./drafts，取得当前基点后预览、提交；下面的对象 URN 要换成自己草稿中的身份。

对象发布 · 先替换实际值
kc writer head --repo <your-repo>
kc diff --repo <your-repo> --base <base-commit> --dir ./drafts
kc writer commit --command-id <new-command-id> --repo <your-repo> --base <base-commit> --dir ./drafts
kc writer receipt --command-id <new-command-id>
kc read <your-object-urn> --repo <your-repo> --commit <new-commit>

base-commit 来自 writer head；new-commit 来自提交回执的 result.newCommit，查回执时在 receipt.result.newCommit。响应丢失先查原命令标识；相同请求重试沿用原标识，修改内容后的新提交使用新标识。

核对结果回读来自自己的仓和本次接受的提交，内容、身份与 Schema 匹配。预览成功不能代替发布成功。

4

Dataset 发布者：选择范围，发布交付

先取得 Dataset 管理权和每个来源的发布许可。打开向消费者交付 Dataset，按交付用途挑选目录或文件。对象的方面、关联材料和使用说明需要明确选入，引用不会扩大交付范围。

进入组合指南
kc read 'urn:kc:object:kc/guide/share-a-dataset#/guide' --repo kr://kc/system
kc help compose
kc help dataset define
kc help recipe

最小例子：把来源仓中实际存在的一个目录交付到 reference/。替换来源仓、分支和目录；第 1 版只用于自己的全新 Dataset，后续修订应使用更大的版号。

选择目录 · 无需另造配方文件
kc dataset define <your-dataset> --revision 1 \
  --source '<your-repo>=refs/heads/<source-branch>@reference@<source-directory>'
kc dataset show <your-dataset> --revision 1

对象跨多个目录时，按 kc help recipe 提供的完整配方继续选择所需范围。核对返回的来源提交、交付路径与修订号；需要固定预先核对的来源提交时，按帮助设置配方的版本条件。

得到一份已经接受、范围明确的交付。发布失败先核对已接受结果和原因，不能假定全部操作都回滚了。

5

授权管理者：把消费权给实际使用身份

使用者先用 kc whoami 确认用户名。下面由有权管理这份 Dataset 授权的人执行；查看库存或交付定义还需相应库存权限，已有权限无需重复授予。

授权给实际消费者
kc grant add --dataset <your-dataset> --principal <consumer-username> \
  --action dataset.resolve,file.read

得到消费者可以读取这份交付，不因此取得来源整仓的读取权、维护权或重新发布权。

6

消费者：用自己的身份完成交接验证

消费者在自己的已登录会话里读取发布者提供的修订。下面从刚才映射的 reference/ 开始；遇到目录就沿其路径继续列举，选择文件条目的 entries.path。下载目标必须是尚不存在的本地文件。

消费者自己的会话
kc whoami
kc files list --dataset <your-dataset> --revision 1 --path reference
kc files read --dataset <your-dataset> --revision 1 --path <entries.path> --out <new-local-file>

交付包含对象时，再按前面的对象读取例子核对所需方面。对照双方约定的文件范围，确认应交付的内容可读、未选入的已知文件不能通过这个 Dataset 读取；不要用发布者的会话代替这一步。

完成交接消费者读到了约定范围和修订，保存了来源依据，并知道反馈应交给谁。

07

更新、反馈与复核

一次内容更新有三个时刻：来源提交、Dataset 接受新修订、消费者采用新版。把它们分开，才知道别人究竟用到了哪一版。

1. 来源仓发布维护者核实反馈，修改并提交。对象修改经 Writer 校验；基点已经变化时，重新读取和核对，避免覆盖他人的改动。
2. 交付接受新版本发布者把更新后的来源交付成新版，并核对接受结果。来源提交不会改写已有 Dataset 版本。
3. 消费者采用不指定修订的新请求使用当前已发布版；已固定修订的读取、已下载的文件或挂载不会因此自动换版，应明确采用更新。

自动跟随的设计也是“产生并接受新修订”，不会改写旧版；是否已在目标部署提供，应先确认。上面的接入流程使用显式发布，不把来源提交成功当成已交付。自动跟随及修订管理的能力进展见路线。

把问题带着依据交回维护者

反馈应包含对象、方面、所用 Dataset 版本或来源提交，以及具体问题。反馈本身不修改对象；维护者核实后再发布。需要评审时先在工作分支修订，校验和业务审核完成后再合并。

复核时区分内容版本和外部观察

静态内容按原版本读取，但仍检查当前权限与版本可用性。LiveAccess 的固定版本保存的是取值声明，不会把外部系统冻结在过去；复核当次状态应查原观察与证据，重新查询可能得到新值。证据保留与历史可用范围以部署策略为准。

通过访问记录了解使用情况

有审计权限的人可以按对象或追踪标识查经过 KC 服务的访问、来源和执行结果。记录帮助复核实际使用，不保证 Agent 的回答正确，也不覆盖绕过 KC 的底层访问和外部工具调用。

按需增加搜索、实时值与工具

先完成基础交付，再增加实际需要的能力。部署方安装插件，团队发布声明；插件未安装、配置不支持、索引未就绪和实际无命中应分别处理。

搜索：让使用者在交付范围里找对象

索引声明描述要检索的字段及构建方式，选进哪个 Dataset，就为哪个范围提供检索依据。声明可被解析、插件可用、索引已就绪之后才能搜索；对象登记或 Dataset 发布本身不能代替这些条件。

先读部署提供的插件说明
kc help plugin
kc help search

从当前范围的访问概览取得实际插件名称，再用 kc plugin <名称> help 了解该实例支持的声明。搜索和回读应沿用同一个 Dataset 版本。声明形式、能力与交付状态以目标服务说明为准；设计与进展分别见发现和路线。

LiveAccess：按权限读取外部当前值

健康状态、表行数等变化频繁的值，可以由方面或成员引用一份取值描述。部署具备相应能力时，平台读取外部系统返回的获准结果，并保留观察依据；某个值失败应单独说明，不能用旧快照冒充当前值。

谁负责接入工作
外部系统团队按支持的取值协议提供入口，执行来源权限，返回值及观察依据
内容维护者按插件帮助发布取值描述，再让相应方面或成员引用它
部署方装配能力、确认可信目标和认证传递规则，并明确证据保留策略
消费者在获准的 Dataset 中读取，核对观察时间与逐值结果

源库无需全量搬迁，查询结果会进入 KC 并返回使用者。当次采用的值或失败可按证据策略保存；只有明确声明结果可共享的外部值，才允许用于共享索引。凭证只传给部署信任的目标，不写入对象、索引或日志。接入前应确认这些条件符合来源系统要求。

完整声明与身份规则见LiveAccess；可复制的实际输入以当前插件公开指南为准。

CLI、MCP 服务和 Skill：登记工具，再按条件使用

CLI说明与脚本可一起交付。使用者下载固定修订的文件，核对运行环境、帮助、配置与认证后调用。
MCP 服务登记用途、地址、传输与连接条件。Agent 是否支持动态添加、如何授权，由该 Agent 和服务的接入方式决定。
Skill交付技能说明与配套文件。使用者按目标 Agent 的技能机制安装，再核对脚本依赖和权限。

工具登记和文件交付提供了发现与取得的路径，不等于平台已经完成安装、连接或业务调用。清河茶铺的 order-cli 下载并加执行权限后，可以先运行 ./order-cli --help 离线查看版本、用法与配置要求。执行查询前需设置 ORDER_SERVICE_URL；材料不预置真实订单服务或业务认证配置。工具自己的版本、认证和执行后果由工具及外部系统负责。

插件与业务工具是两类扩展：插件由部署方装配，为对象提供横切能力；业务工具作为内容发布。新增插件类型的开放范围、KC 自身的 MCP 入口等进展统一见路线。

09

权限与分享

维护来源、组合交付、消费交付分别授权。范围和版本决定读什么，当前权限决定这次能不能读。

看得到仓或 Dataset，就能读内容吗？

不能这样推断。库存可见与内容可读是不同能力；实际读取仍检查当前授权。部署可以把某些 Dataset 声明为已认证用户默认可读，这不开放来源整仓或写权限。

别人怎样把我的内容交付给他的用户？

他需要 Dataset 管理权，并取得你对所选来源的发布许可。消费权按整份 Dataset 生效，发布者应先明确哪些文件可以交付，不能依赖来源仓的直读限制来隐藏已经选入的敏感内容。

同一个对象的一部分是敏感信息，怎么办？

把读者或维护权限不同的方面放到受限仓，发布 Dataset 时只选入允许交付的文件。Dataset 没选入的方面属于范围之外，不会从来源仓自动补齐。按仓范围读取时，无法读取的来源会在结果中说明，具体粒度以返回信息为准。

撤回发布许可，等于收回已交付内容吗？

不等于。来源发布许可控制后续发布；已有 Dataset 版本仍按其消费权限服务。要阻止后续读取，还需处理相应消费权限或交付的可用状态。已经下载到客户端的字节不能远程收回。

撤销消费权以后，旧版本还能读吗？

后续请求重新检查当前权限，旧版本坐标不提供通行权。已下载文件的本地副本与服务端的新读取是两回事。

Agent 用谁的身份，外部系统认谁？

KC 使用请求携带且经服务验证的身份；共享你的会话时就是你的身份，专用 Agent 身份需另行授权。LiveAccess 按目标规则传递认证，外部系统执行自己的权限。工具绕过 KC 的直接调用也由外部系统负责。

谁能查看访问记录，权限又向谁申请？

查看访问记录需要对应审计权限。业务申请走组织现有流程；可用 kc admission show 查看自身权限和部署提供的申请入口，平台不代替业务审批。

边界与下一步

  • 搜索用于发现对象；实际业务分析还需要事实数据、适用口径与计算依据。
  • 文件与版本由 lakeFS 和对象存储承载。容量、吞吐、长历史与恢复能力应按具体部署验证。
  • 多个团队各自提交，不做跨仓事务；Dataset 固定的是一组来源版本。
  • 反馈和 Agent 推断不会自动成为权威内容，须经维护者核实并正常发布。
  • 外部当前值有观察时间、来源权限与保留边界，不保证零延迟，也不自动保存全部历史。
  • 当前专注发现与读取。对象可以说明怎样操作，实际操作通过外部系统自己的入口完成。
